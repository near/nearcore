# Stateless validation

> Protocol version: 88 (stable) · Release: 2.14.0 · Derived from commit: bc4e9e8 · Generated: 2026-11-03
> Primary crates/files: `core/primitives/src/stateless_validation/`, `chain/chain/src/stateless_validation/`, `chain/chain/src/signature_verification.rs`, `chain/client/src/stateless_validation/`

## Role

Stateless validation (NEP-509) is how the protocol verifies a chunk's state transition without every validator holding the full shard state. After a chunk producer applies a chunk, it packages the *recorded* trie reads (a Merkle proof) together with the transactions and source receipts into a **`ChunkStateWitness`**. The witness is compressed, Reed-Solomon erasure-coded, and distributed part-by-part to the chunk's assigned **chunk validators**. Each validator reconstructs the witness, re-applies the chunk against the partial trie (no full state needed), checks the replayed `ChunkExtra` / outgoing-receipts root against the chunk header, and emits a signed **`ChunkEndorsement`**. A chunk may be included in a block only once endorsements covering > 2/3 of the chunk-validator stake are collected. This component sits downstream of [sharding-chunks](sharding-chunks.md) (which produces the chunk) and [runtime-execution](runtime-execution.md) (which is replayed during validation against a partial trie from [state-storage](state-storage.md)); chunk-validator assignment comes from [epoch-validators-staking](epoch-validators-staking.md); witnesses/endorsements travel over [networking-p2p](networking-p2p.md); endorsements gate chunk inclusion in [chain-block-processing](chain-block-processing.md).

**What changed at v87/v88.** `EarlyKickout` activated at 87 (`core/primitives-core/src/version.rs:639`), which flips every producer-signed witness/contract-distribution message from its V1 wire form to a **V2** form carrying the chunk's parent and **grandparent anchor**, and switches chunk-producer resolution from the epoch height sampler to an anchored `DBCol::ChunkProducers` lookup. At v86 the V2 variants existed but were inert; from v87 V1 is rejected and V2 is mandatory.

**v88 adds no protocol feature that touches this component** — the features that activate at 88 (`UniversalAccounts`, `RefundRepeatedUniversalStateInitDeposit`, `CanonicalUniversalStateInit`) are account/runtime-level. The one change in the 2.14.0 release that does touch this component is **ungated**: a chunk producer may now answer one `ContractCodeRequest` with **several** `ContractCodeResponse` messages, and the requester accumulates them until the requested hash set is complete (#16421, step 6). No new wire variant and no new borsh discriminant was introduced — `ContractCodeResponse` is still `V1 = 0` / `V2 = 1` (`core/primitives/src/stateless_validation/contract_distribution.rs:374`) — so the change is in *how many* messages of an existing shape travel and how the receiver folds them together. Separately, `ReceiptPromiseInputSizeLimit`, which the rc build had stable at 87, was **de-stabilized to nightly (157)** before this release (`core/primitives-core/src/version.rs:653`), so the promise-input bound is no longer part of the witness-growth story at 87/88; `EnforceStorageProofLimitForAllActions` stays at 87 and is now the only *new-at-87* bound on witness growth.

## Behavior

### 1. Witness production (chunk producer, after applying its chunk)

`Client::send_chunk_state_witness_to_chunk_validators` (`chain/client/src/stateless_validation/state_witness_producer.rs:15`) drives production for a newly produced chunk:

1. Early-return if `ProtocolFeature::Spice` is enabled (`:23`) — SPICE has its own path (nightly-only, not enabled at v88).
2. Require a local validator signer (`:44`, else `Error::NotAValidator`), then build the witness via `ChainStore::create_state_witness` (`chain/chain/src/stateless_validation/state_witness.rs:45`).
3. If `save_latest_witnesses` is set, persist it for debugging (`:53`).
4. **Self-endorse shortcut**: if the producer is itself in the chunk-validator set for `(epoch, shard, height)`, it endorses immediately (bypassing validation, since it just applied the chunk) by calling `send_chunk_endorsement_to_block_producers` and feeding the returned self-endorsement to its own endorsement tracker (`:57`–`:72`).
5. Send a `DistributeStateWitnessRequest` to the `PartialWitnessActor` (`:74`).

`create_state_witness` (`state_witness.rs:45`) assembles the witness:
- `collect_state_transition_data` (`:100`) walks backwards from `chunk_header.prev_block_hash()` to the block at `prev_chunk_header.height_included()` (exclusive), reading each block's stored `StateTransitionData` as an *implicit transition* (one per missing chunk, plus an extra one when a resharding shard-id change happens between blocks, `:132`). Transitions are collected newest-first then `reverse()`d to forward order (`:165`). The **main transition** is the last new chunk's transition (`:168`), read via `get_state_transition` (`:194`) from `DBCol::StateTransitionData` keyed by `(block_hash, shard_id)`, with `post_state_root` taken from that block's `ChunkExtra` (`:231`). Genesis prev-chunk uses `get_genesis_state_transition` with empty base state (`:238`).
- `collect_source_receipt_proofs` (`:264`) gathers all incoming receipts for the *previous* chunk and their proofs (so the witness self-proves which receipts to apply), converting from `[block_hash -> Vec<ReceiptProof>]` to `[chunk_hash -> ReceiptProof]` (`:316`); a duplicate chunk proof is an error (`:331`). Genesis prev-chunk yields an empty map (`:270`).
- The witness carries `prev_chunk.to_transactions()` as `transactions` and the current `chunk.to_transactions()` as `new_transactions` (`:89`, `:91`).

Contract code is **not** in the witness: `ContractUpdates` (accessed code-hashes and newly deployed code) is returned alongside it in `CreateWitnessResult` (`state_witness.rs:34`) and distributed separately (step 6).

### 2. Encoding and distribution (`PartialWitnessActor`)

`handle_distribute_state_witness_request` (`chain/client/src/stateless_validation/partial_witness/partial_witness_actor.rs:254`) first resolves the epoch protocol version (`:289`) and the parent/grandparent anchors once — `prev_block_hash` from the chunk header (`:294`) and `prev_prev_block_hash` from `EpochManagerAdapter::grandparent_anchor` (`:296`, `chain/epoch-manager/src/adapter.rs:560`), defaulting to `CryptoHash::default()` when the chunk has no real grandparent. The producer has already processed the parent (it built on it), so this lookup cannot miss. It then sends three streams in priority order (`:298`–`:343`):

1. **Contract accesses first** (only if contracts were accessed): `send_contract_accesses_to_chunk_validators` (`:1007`) sends a signed `ChunkContractAccesses` (code-hashes only, not code) to chunk validators *except* chunk producers tracking the same shard (`:1026`), so validators can request missing code while witness parts are still in flight. The anchors and `protocol_version` are threaded in so `ChunkContractAccesses::new` emits V2 at v87/v88.
2. **Witness parts** (compression/encoding moved to `witness_creation_spawner` to avoid blocking the actor, `:320`): `compress_and_distribute_witness` (`:347`) compresses (`compress_witness`, `:1378`), then `send_state_witness_parts` (`:419`) → `generate_state_witness_parts` (`:1332`) erasure-codes the compressed bytes into **one part per chunk validator** using a Reed-Solomon encoder sized to `chunk_validators.len()` with `WITNESS_RATIO_DATA_PARTS = 0.6` (`partial_witness/encoding.rs:6`). Part `i` is signed and addressed to chunk validator `i` (the part owner); all parts of one distribution share a wire version. Sent as `NetworkRequests::PartialEncodedStateWitness` (`:479`); the witness is recorded in `ChunkStateWitnessTracker` for round-trip-time metrics (`:471`).
3. **Contract deploys** (lower priority): `send_chunk_contract_deploys_parts` (`:1053`) compresses newly-deployed code and erasure-codes it via `generate_contract_deploys_parts` (`:375`) to non-producer validators, who will need it in later turns.

### 3. Part forwarding and reconstruction (chunk validator)

- A part owner receives its part via `handle_partial_encoded_state_witness` (`:484`). The shard-id metric label is bucketed through `shard_id_metric_label` (`:101`) so an off-layout `shard_id` off the wire collapses to `"unknown"` instead of minting an unbounded Prometheus child (`:88`). The part is then version-gated: `witness_version_mismatch` (`:81`, over `version_mismatch` at `:73`) drops a V1 part at/after `EarlyKickout` and a V2 part before it; an unresolvable epoch version is *not* treated as mismatch (`:509`).
- **Producer resolution** (`:527`): V1 uses the epoch height sampler `get_chunk_producer_info`; V2 uses `get_chunk_producer_info_anchored` on the signed grandparent (`:536`), which reads `DBCol::ChunkProducers` and therefore resolves even when the part races its parent block. `ChunkProducerNotInDB`/`MissingBlock` on an anchored message means this node is ≥2 blocks behind and the part is dropped quietly (`:546`).
- The part is validated on `partial_witness_spawner` (`validate_partial_encoded_state_witness`, `validate.rs:65`). **Only the part's designated owner re-broadcasts it** (`my_part_ord` computed at `:566`, checked at `:590`): producer-signed parts for other ordinals are still stored but not forwarded, so a single injected message cannot fan out across the validator set. Forwarding targets all chunk validators except the producer and self (`NetworkRequests::PartialEncodedStateWitnessForward`, `:599`); the part is stored locally either way (`:615`).
- Forwarded parts arrive at `handle_partial_encoded_state_witness_forward` (`:651`) with the same metric-label bucketing and version gate (`:677`), are validated and stored (`:704`). `DBNotFoundErr` (node behind) and an `EpochOutOfBounds` whose parent block is unknown are dropped quietly (`:717`, `:726`); anything else logs as invalid (`// TODO: ban sending peer`, `:738`).
- `PartialEncodedStateWitnessTracker` (`partial_witness_tracker.rs:542`) accumulates parts per **`WitnessCacheKey` = (chunk key, anchor)** in a per-shard `ShardWitnessTracker` (`:471`) holding an LRU `parts_cache` of `WITNESS_PARTS_CACHE_SIZE = 5` (`:41`) and a `processed_witnesses` LRU of 50 (`:46`). `store_partial_encoded_state_witness` builds the key from `prev_prev_block_hash()` (`:581`). `process_witness_part` (`:214`) feeds a `ReedSolomonPartsTracker`; when enough data parts arrive it decodes (`InsertPartResult::Decoded`, `:280`).
- **Eviction prefers off-chain anchors**: when the cache is full, `maybe_insert_new_entry_in_parts_cache` (`:875`) first drops the least-recently-used entry whose anchor is *not* the block our chain has at that height (`is_anchor_on_our_chain`, `:851`), so an anchor flood cannot push out the entry we actually need.
- `try_finalize` (`:423`) waits for **both** the witness parts (decoded) and the accessed-contract state to be ready; `AccessedContractsState::Unknown` counts as ready (`:434`) — the chunk may have no contracts, or the accesses message was lost (best-effort). A `Requested` entry that is still incomplete is *not* ready and blocks finalization until one of the two deadlines fires (see step 6) — `contract_request_expired` (`:402`), `expire_contract_request` (`:415`), swept in `expire_stale_contract_requests` (`:506`), after which the entry drops back to `Unknown` and the witness is validated without the code.
- Entry size accounting (`CacheEntry::total_size`, `:177`) now also counts the codes already delivered towards an **incomplete** request (`:188`); at BASE a `Requested` entry contributed 0. This feeds only the `PARTIAL_WITNESS_CACHE_SIZE` metric (`:642`), not eviction.
- On finalize, `deliver_witness` (`:757`) decodes, checks the decoded witness's `chunk_production_key` matches the cache key (`:800`), **extends** the main transition's `base_state` `TrieValues` with the separately-fetched contract codes (`:811`), and sends a `ChunkStateWitnessMessage` to the `ChunkValidationActor` (`:825`).

### 4. Validation (`ChunkValidationActor`)

`process_chunk_state_witness_message` (`chunk_validation_actor.rs:525`):
1. Reject if this node is not a validator (`:532`, `Error::Other`); send a `ChunkStateWitnessAck` back to the chunk producer for RTT metrics (`send_state_witness_ack`, `:194`) — the producer is resolved from the parent block (`get_chunk_producer_info_from_prev_block`) and falls back to the canonical sampler when the parent is absent, and a failure only logs, never aborts processing.
2. If the witness's prev block is not yet known, park it as an **orphan** in `OrphanStateWitnessPool` — only if `head_distance` is within `ALLOWED_ORPHAN_WITNESS_DISTANCE_FROM_HEAD = 2..6` (`:46`, `:251`) and under `max_orphan_witness_size` (`:265`); reprocessed when the block arrives via `process_ready_orphan_witnesses` (`:287`). The pool keys on `(ChunkProductionKey, chunk_hash)` (`chunk_validator/orphan_witness_pool.rs:20`), so two competing witnesses for the same chunk key coexist instead of evicting each other.
3. Otherwise `process_chunk_state_witness` (`:335`), which re-checks `chunk_header.prev_block_hash() == prev_block.hash()` (`:351`) → `start_validating_chunk` (`:371`).

`start_validating_chunk` (`:371`):
1. Confirm the witness `epoch_id` equals `get_epoch_id_from_prev_block` (`:397`).
2. `pre_validate_chunk_state_witness` (`chain/chain/src/stateless_validation/chunk_validation.rs:313`) — synchronous, cheap checks (below), producing a `PreValidationOutput` (struct `:82`).
3. **Chunk-extra shortcut**: if the validator already has the prev block's `ChunkExtra` on disk (e.g. it produced/tracked the shard), it validates the header directly via `validate_chunk_with_chunk_extra_and_roots` (`chain/chain/src/validate.rs:100`) and endorses without replaying (`:439`–`:452`).
4. Otherwise spawn the heavy `validate_chunk_state_witness` on `validation_spawner` (`:485`); on `Ok`, call `send_chunk_endorsement_to_block_producers` (`:500`).

`pre_validate_chunk_state_witness` (`chunk_validation.rs:313`):
- Check the chunk header version is allowed at the epoch's protocol version (`:323`) and that every `new_transaction` is valid for that protocol version (`:328`, else `Error::InvalidChunkStateWitness`).
- `get_state_witness_block_range` (`:145`) walks backwards from the witness's prev block, classifying each block by `num_new_chunks_seen` for the shard: 0 → contributes an `ApplyOldChunk` implicit transition; 1 → contributes a source-receipt block; 2 → stop. Resharding boundaries inject a `Resharding` implicit transition (`get_resharding_transition`, `:259`), keyed to the split's `left_child_shard`/`right_child_shard` and **now also carrying the boundary block hash** (`:296`, `:303`) — see step 4.3 below.
- `validate_source_receipt_proofs` (`:452`) extracts the receipts to apply from the proofs, validating each proof's `from_shard_id`/`to_shard_id` and Merkle path against the source chunk's outgoing-receipts root (`validate_receipt_proof`, `:532`), filtering for the target shard (`:504`) and shuffling into application order (`:511`). It also rejects extraneous proofs (`:522`). The hash of the ordered receipts must equal `applied_receipts_hash()` (`:364`), and the witness's `transactions` must merklize to the last new chunk's `tx_root` (`:371`/`:378`).
- Builds `MainTransition::Genesis` (`:411`) or `MainTransition::NewChunk` (`:425`) with `StorageDataSource::Recorded(PartialStorage { nodes: base_state })` — i.e. the runtime will read from the recorded proof, not a full trie (`:435`).

`validate_chunk_state_witness_impl` (`chunk_validation.rs:568`) — the consensus-critical re-execution:
1. **Main transition**: replay the last new chunk via `apply_new_chunk` (`:608`) against the recorded partial storage with `MaybePinnedMemtrieRoot::no_memtries()` (`:615`), producing a `ChunkExtra` and outgoing receipts. (Genesis skips replay, `:605`; a per-shard LRU cache of size `NUM_WITNESS_RESULT_CACHE_ENTRIES = 20` can short-circuit repeats, `:99`.)
2. Check the resulting `state_root` equals `main_state_transition.post_state_root` (`:625`) — an early debug check; the binding check is the chunk header at the end.
3. **Implicit transitions**: the count must equal `state_witness.implicit_transitions().len()` (`:665`, error at `:669`). For each, replay an old chunk (`apply_old_chunk`, `:699`) or apply a resharding split (`:711`) against that transition's recorded `base_state`. For the resharding case the parent and child **shard layouts are resolved from the locally determined boundary block hash**, not from the witness-supplied `block_hash` (`:727`, `:731`) — the boundary block is the last block of the old epoch, and resolving it locally matches what the producer did; child congestion info is recomputed from the parent trie before `retain_split_shard` (`:733`, `:743`). State root and congestion info are then updated (`:749`) and each is checked against the transition's `post_state_root` (`:751`, debug-only); the error message reports the boundary block hash for resharding transitions and the witness-supplied `block_hash` otherwise (`transition_block_hash`, `:680`).
4. **Final binding checks** (in parallel via `rayon::join`, `:765`): merklize the outgoing-receipt hashes and call `validate_chunk_with_chunk_extra_and_receipts_root` to bind `chunk_extra` (state root, gas, congestion) and the outgoing-receipts root to the **witness chunk header** (`:768`); and check `new_transactions` merklize to the header `tx_root` (`:778`, else `Error::InvalidTxRoot`) and the encoded-merkle-root via `validate_chunk_with_encoded_merkle_root` (`:780`).

On any failure `Error::InvalidChunkStateWitness` is returned; if `save_witness_if_invalid` is set the witness is cloned and persisted for debugging (`validate_chunk_state_witness`, `:795`, storing at `:826`).

**Missing contract code is a validation failure, not a no-op.** When replaying under `ApplyChunkReason::ValidateChunkStateWitness`, a `FunctionCall` to an account that commits to a code hash whose body is available from no source (in-chunk deploy record, recorded partial state, compiled-contract cache) returns `StorageError::MissingTrieValue` instead of the `CodeDoesNotExist` nop outcome (`runtime/runtime/src/function_call.rs:301`). Block production (`UpdateTrackedShard`) is unchanged, since a full node always resolves the body from its own trie. Without this a validator would recompute and endorse the wrong (no-op) transition.

### 5. Endorsement creation, gossip, aggregation

- `send_chunk_endorsement_to_block_producers` (`chain/client/src/stateless_validation/chunk_validator/mod.rs:22`) builds a `ChunkEndorsement::new` (`:62`) and sends it to the next `NUM_NEXT_BLOCK_PRODUCERS_TO_SEND_CHUNK_ENDORSEMENT = 5` unique block producers (`:16`, `:47`) — covering the case where the height-`h` block producer is skipped. If the signer is itself one of those producers, the endorsement is returned for immediate local processing (`:63`–`:72`).
- A block producer validates and stores received endorsements in `ChunkEndorsementTracker::process_chunk_endorsement` (`chain/client/src/stateless_validation/chunk_endorsement.rs:43`): dedup per validator (`:50`), `validate_chunk_endorsement` (relevance + both signatures, `validate.rs:168`), then cache by `ChunkProductionKey` in a 100-entry LRU (`:19`, `:60`).
- When producing a block, `collect_chunk_endorsements` (`:82`) filters cached endorsements to those whose `chunk_hash` matches the header (`:109`), then `compute_endorsement_state` decides inclusion: a chunk is includable iff `is_endorsed` (> 2/3 stake). The ordered signature vector (or empty) is what goes into the block body.
- `validate_chunk_endorsements_in_block` (`chain/chain/src/stateless_validation/chunk_endorsement.rs:19`) re-validates at block processing: chunk count == endorsement-vector count (`:24`); for each new chunk, the signature list length equals the ordered chunk-validator count (`:74`), each present signature verifies via `ChunkEndorsement::validate_signature` over bytes **rebuilt from the header's `chunk_hash`** (`:93`), > 2/3 stake is endorsed (`:113`), and the header's endorsement **bitmap** is consistent (length `:121`, bit-per-signature `:130`, trailing zeros `:141`). Old chunks (`height_included != block height`) must carry empty endorsements (`:50`). `validate_chunk_endorsements_in_header` (`:187`) checks the bitmap shape against the chunk mask; `validate_spice_chunk_endorsements_in_header` (`:158`) requires an all-empty bitmap under nightly SPICE.

### 6. Contract-code distribution (avoid shipping code in every witness)

Contract code is excluded from the witness and distributed out-of-band:
- Producer sends `ChunkContractAccesses` (hashes) to validators (step 2.1).
- Validator, in `handle_chunk_contract_accesses` (`partial_witness_actor.rs:915`), drops the message if its wire version is wrong for the epoch (`should_drop_for_version`, `:898`), validates it (`validate_chunk_contract_accesses`, `validate.rs:194` → `validate_witness_contract_accesses_signature`, `:380`, where V2 resolves the producer through the anchor at `:391`), filters out hashes already in its compiled-contract cache (`:969`), stores the missing set in the tracker **under the message's anchor** (`store_accessed_contract_hashes`, `:981`), and sends **one** signed `ContractCodeRequest` to a *random* chunk producer for the shard (`:986`–`:999`). A request is never retried.
- Producer answers in `handle_contract_code_request` (`:1162`): validates and dedups per `(key, requester)` (`:1175`), caps the hash count at `MAX_CONTRACTS_PER_REQUEST = 1282` (`:1185`), re-derives the `MainTransitionKey` from its own chain (`derive_main_transition_key`, `:1087`) and requires it to equal the requested one (`:1193`), confirms each requested hash was actually accessed in that transition's stored `contract_accesses` (`:1217`, `:1230`), and reads the raw code from the trie (`:1239`).

  **Changed in 2.14.0 (#16421), ungated.** The codes are collected into a `BoundedContractCodes` (`:1228`). If the running total passes `MAX_UNCOMPRESSED_CONTRACT_CODE_PER_REQUEST_SIZE` (256 MiB) the producer logs "requested contract code exceeds the per-request cap, not serving" and answers **nothing at all** (`:1243`–`:1252`). Otherwise the set is cut by `split_contracts_for_response` into groups that each fit `MAX_UNCOMPRESSED_CONTRACT_CODE_RESPONSE_SIZE` (64 MiB), and **one `ContractCodeResponse` is sent per group** (`:1269`–`:1275`). Each response is encoded independently by `ContractCodeResponse::encode` — **V2 (signed) iff `SignedContractCodeResponse` is enabled, else V1 (unsigned)** (`contract_distribution.rs:380`, gate at `:386`); enabled at 87/88, so every response is signed by the answering producer. At BASE the producer always sent exactly one response, with no size check at all, so a set over 64 MiB produced a message the requester could not decompress; `encode_response_contracts` (`:548`) now rejects that case at the producer instead. With `max_contract_size = 4 MiB`, splitting begins at ~16 maximal contracts and the per-request refusal at ~64.
- Validator stores each received response (`handle_contract_code_response`, `:1280` → `store_accessed_contract_codes`, `:1292`), which hashes the bytes locally (`CodeBytes::hash`, `partial_witness_tracker.rs:603`) and routes them to every cache entry under that chunk key whose outstanding request **covers** those hashes (`find_pending_contracts`, `:492`; `is_awaiting_contracts`, `:390` — a *subset* test since 2.14.0, where BASE required set equality). `validate_contract_code_response` requires and verifies the responder signature whenever `SignedContractCodeResponse` is enabled (`validate.rs:229`, `:237`, `:406`), and additionally requires the responder to be a chunk producer for the shard (`:418`) — applied to each response independently.
- `set_received_contracts` (`partial_witness_tracker.rs:310`) folds a response into the entry:
  1. If the response carries **any** hash that was not requested, the whole response is dropped (`:324`–`:335`).
  2. Otherwise codes are merged into `received` by hash, first writer wins (`:337`–`:339`). If the merge added at least one new hash, `last_progress_at` is advanced (`:342`); a response that only repeats known codes does not, so a responder cannot hold the entry open by resending.
  3. If the accumulated uncompressed size passes the 256 MiB per-request cap the whole request is **given up on**: the state resets to `Unknown`, freeing the codes, and the witness is validated best-effort without them (`:345`–`:352`, `:369`–`:373`).
  4. If `received` still has fewer hashes than requested the entry stays `Requested` and nothing finalizes (`:353`).
  5. Only when every requested hash is in does the state become `Received` (`:356`, `:386`), with the request-latency metric measured from `requested_at` (`:378`).
- **Two deadlines** bound the wait (`contract_request_expired`, `:402`), and neither counts before the witness parts have decoded: `ACCESSED_CONTRACTS_REQUEST_TIMEOUT = 2 s` (`:53`) measured from **`last_progress_at`** — i.e. an idle timeout, reset by every response that delivers a new code — and the new absolute ceiling `ACCESSED_CONTRACTS_REQUEST_MAX_TOTAL = 6 s` (`:57`) measured from `requested_at`, documented as the block producer's maximum wait for a block, past which an endorsement for the chunk can no longer land. At BASE there was a single 2 s deadline measured from `requested_at`; the worst-case hold on a decoded witness therefore rises from 2 s to 6 s.
- Newly-deployed contracts ride the separate `PartialEncodedContractDeploys` erasure-coded path (`handle_partial_encoded_contract_deploys`, `:759`; version-gated at `:764`, producer resolved through the anchor for V2 in `validate_partial_encoded_contract_deploys`, `validate.rs:139`; deployed code is precompiled once decoded, `:869`) so future-turn validators have them ahead of time. This path is unchanged in 2.14.0.
- **Global contracts** are distributed by the global-contract mechanism, not by `contract_deploys` (`core/store/src/contract.rs:109`), but from v87 (hence at v88) their distribution also calls `record_global_contract_deploy` so a same-chunk call can find the code without relying on a warm compiled-contract cache (`runtime/runtime/src/global_contracts.rs:221`, gated at `:219`).

**Mixed-version interoperability.** Contract-distribution messages are peer-to-peer and are *not* protected by epoch activation, so a 2.14.0 node and a 2.14.0-rc.1 node exchange them directly. Because #16421 added no wire variant and no new field, both directions parse:
- *TARGET producer → BASE requester*: identical to BASE whenever the requested set fits one response, which `split_contracts_for_response` guarantees by returning a single group (`contract_distribution.rs:563`). When the set does **not** fit, the TARGET producer sends N > 1 responses; the BASE requester's `set_received_contracts` demanded the received hash set equal the requested set exactly, so each partial response matches no entry in `find_pending_contracts` and is dropped with "received contract codes nothing is waiting for". The BASE node then times out at 2 s and validates without the code, which fails on a `FunctionCall` whose body is missing, so it does not endorse. This is a loss relative to a working fetch, but not a regression: at BASE the producer would have sent one over-cap response that the BASE requester could not decompress either.
- *BASE producer → TARGET requester*: the single response carries the complete set, so the subset test matches the entry (`is_awaiting_contracts`, `partial_witness_tracker.rs:390`), the `received.len() < contract_hashes.len()` branch is not taken on the first fold (`:353`) and the entry finalizes exactly as before (`:356`). An over-cap BASE response still fails to decompress at the TARGET requester, as at BASE.
- No consensus artifact is derived from the response shape — the response feeds only the local witness base state, which `deliver_witness` extends with the fetched codes before validation (`partial_witness_tracker.rs:811`) — so a node on either build reaches the same endorsement decision whenever it obtains the code at all. Nothing here needs to be ordered against the 87 or 88 activation votes.

### 7. Anchored producer resolution (shared V2 machinery)

`resolve_and_verify_anchored_producer` (`chain/chain/src/signature_verification.rs:190`) is the single entry point used by the witness, contract-accesses and contract-deploys receive paths:
1. `resolve_anchored_producer` (`:161`) calls `EpochManagerAdapter::get_chunk_producer_info_anchored` (`chain/epoch-manager/src/adapter.rs:594`), which reads `DBCol::ChunkProducers` keyed by the anchor when `EarlyKickout` is on and the anchor is in the chunk's epoch, and falls back to the canonical height sampler otherwise (feature off, no anchor, or a cross-epoch anchor in the first ≤2 blocks of an epoch). Outcomes are counted by `ANCHORED_CHUNK_PRODUCER_LOOKUP_TOTAL` (`chain/chain/src/metrics.rs:544`).
2. `verify_anchored_chunk_key` (`:87`) cross-checks the *signed* `(epoch_id, height_created, prev_prev_block_hash)` against what the parent block implies, when the parent is known. When the parent is absent, only the anchor constrains the chunk: the height must equal `anchor.height + CHUNK_GRANDPARENT_ANCHOR_HEIGHT_OFFSET` (2, `chain/epoch-manager/src/adapter.rs:35`) — a lower height is an error, a higher one is deferred as `DBNotFoundErr` (the chunk sits on a skipped slot and is re-checked once the parent lands). A default (genesis) anchor is only allowed up to `genesis_height + 1`.

## Invariants & failure modes

- **> 2/3 stake to endorse.** `has_enough_stake` requires `endorsed_stake >= total_stake*2/3 + 1` (`validator_assignment.rs:18`/`:22`); below threshold `compute_endorsement_state` clears the signature vector (`:82`) so the chunk cannot be included. Re-checked at block processing (`chain/chain/src/stateless_validation/chunk_endorsement.rs:113`).
- **Endorsement signed bytes are canonical.** Both the receive path and the consensus path derive the signed bytes from `chunk_hash` via `endorsement_signed_bytes` (`chunk_endorsement.rs:143`); the wire `signature_differentiator` is never read back. Before this fix a peer could pick the signed bytes through that field and pass `verify` while failing `validate_signature` at block validation.
- **State-root binding.** Final validation binds the replayed `ChunkExtra` and outgoing-receipts root to the witness chunk header (`chunk_validation.rs:768`); the intermediate `post_state_root` checks (`:625`, `:751`) are explicitly described in-code as debug aids, not the authoritative check.
- **Resharding layouts come from the local boundary block.** Both parent and child shard layouts for a `Resharding` implicit transition are resolved from `boundary_block_hash` recorded by the local `get_resharding_transition` (`:727`, `:731`), not from the witness-supplied `transition.block_hash`; a producer cannot steer layout resolution.
- **Receipts/transactions are self-proving.** `applied_receipts_hash` must match the receipts extracted from proofs (`:364`); `transactions` must merklize to the last new chunk's `tx_root` (`:378`); each source-receipt proof's shard ids and Merkle path are verified (`validate_receipt_proof`, `:532`); extraneous proofs are rejected (`:522`). Mismatch → `Error::InvalidChunkStateWitness`.
- **Implicit-transition count must match** between recomputed range and witness (`:665`), preventing a producer from hiding or inventing missing-chunk transitions.
- **Missing contract code fails validation** rather than replaying a `CodeDoesNotExist` no-op (`runtime/runtime/src/function_call.rs:301`).
- **Signature provenance.** Witness parts, contract accesses/requests/responses, and endorsements are all signed; validation rejects on bad signature or wrong signer (`validate.rs`, `chunk_endorsement.rs`). For V2 messages the producer is resolved from the signed grandparent anchor and the signed chunk key is cross-checked against the parent block (`signature_verification.rs:87`). A contract-code responder must be a chunk producer for the shard (`validate.rs:418`).
- **Only the designated part owner forwards.** A validator re-broadcasts a witness part only when `part_ord == my_part_ord` (`partial_witness_actor.rs:589`); other valid parts are stored but not fanned out.
- **Cache keys include the anchor.** `WitnessCacheKey` (`partial_witness_tracker.rs:68`) prevents a second, differently-anchored-but-validly-signed producer for the same chunk key from colliding with the entry we need; eviction prefers entries anchored off our chain (`:875`).
- **Metric labels are bounded.** `shard_id` off the wire is bucketed to `"unknown"` when outside the epoch's shard layout before being used as a Prometheus label (`partial_witness_actor.rs:101`, `:88`), so a peer cannot grow the registry with fresh label values.
- **Received contract code is content-addressed, not sender-trusted.** The requester hashes the bytes itself (`store_accessed_contract_codes`, `partial_witness_tracker.rs:603`) and accepts a code only if that hash is in the set it requested; any unrequested hash drops the whole response (`set_received_contracts`, `:328`). This was already true at BASE but becomes load-bearing in 2.14.0, because an answer is now assembled from several messages and nothing pins them to a single responder — each is independently required to be a signing chunk producer for the shard (`validate.rs:406`, `:418`), but different producers may each contribute a subset.
- **One request is bounded in total, not just per message** (new in 2.14.0). The producer refuses to serve past `MAX_UNCOMPRESSED_CONTRACT_CODE_PER_REQUEST_SIZE` = 256 MiB (`BoundedContractCodes::push`, `contract_distribution.rs:528`; enforced at `partial_witness_actor.rs:1243`) and the requester gives the request up past the same cap (`partial_witness_tracker.rs:346`). Memory may transiently exceed it by at most one response's worth, since the check runs after the merge. Each individual message still must fit the 64 MiB decompression cap, which the producer now enforces at encode time (`encode_response_contracts`, `contract_distribution.rs:548`) rather than leaving the requester to fail decompression.
- **A slow answer cannot pin a cache entry open indefinitely** (changed in 2.14.0). The 2 s deadline is now an *idle* timeout from `last_progress_at`, which only a response delivering a **new** hash advances (`partial_witness_tracker.rs:342`), and it is capped by an absolute `ACCESSED_CONTRACTS_REQUEST_MAX_TOTAL = 6 s` from `requested_at` (`:57`, `:410`). A responder replaying known codes makes no progress and cannot extend the wait. The weakening to record: a decoded witness can now be held up to 6 s instead of 2 s before best-effort validation.
- **An incomplete contract set never reaches the runtime.** `try_finalize` treats `Requested` as not-ready (`:425`–`:435`); the entry either completes (`Received`, every requested hash present) or is reset to `Unknown` by a deadline or the per-request cap, in which case the witness is validated with *no* fetched code rather than a partial set. A partial set would otherwise look like witness incompleteness and fail unpredictably (`runtime/runtime/src/function_call.rs:301`).
- **Relevance gating drops, not errors.** `validate_chunk_relevant` (`validate.rs:280`) returns `TooLate` (height ≤ final head, `:309`), `TooEarly` (> head + `MAX_HEIGHTS_AHEAD = 5`, `:23`/`:320`), or `UnknownEpochId` (`:338`); these are dropped silently, while `NotAChunkValidator` (`:266`) / `InvalidShardId` (`:295`) / bad-signature are hard errors (potential malicious behavior, `// TODO: ban sending peer`, `partial_witness_actor.rs:635`).
- **Node-behind is not malice.** `DBNotFoundErr` (anchor/parent not processed) and an `EpochOutOfBounds` whose parent block is unknown are dropped quietly on the witness, contract-accesses and contract-deploys paths (`partial_witness_actor.rs:628`, `:717`, `:726`, `:781`, `:792`, `:939`, `:950`). V2 parts are never retransmitted, so the chunk recovers via the orphan-witness path or the producer's endorsement quorum instead.
- **Contract-fetch wait is bounded.** A `ContractCodeRequest` with no new code for 2 s, or open for 6 s in total, after the witness parts decoded is abandoned and the witness is validated best-effort without the code (`partial_witness_tracker.rs:53`, `:57`, `:402`, `:506`). The request itself is never retried.
- **Orphan witnesses** outside `2..6` of head or over `max_orphan_witness_size` are not stored (`chunk_validation_actor.rs:251`/`:265`).
- **Size caps** reject oversized parts (`encoded_length` `validate.rs:84`, `part_size` `:102`) as `InvalidPartialChunkStateWitness`; decode failures surface as the same error ("failed to reed solomon decode witness parts, maybe malicious or corrupt data", `partial_witness_tracker.rs:776`), as does a decoded witness whose key disagrees with the part key (`:800`).

## Open questions

- The `ChunkStateWitnessV2.chunk_header` field is still marked `// TODO(stateless_validation): Deprecate this field in the next version of the state witness` (`state_witness.rs:113`) — it remains load-bearing for endorsement (the validator must know the chunk hash it signs), so removal is not realized at v88.
- `store_accessed_contract_codes` (`partial_witness_tracker.rs:597`) takes only a `ChunkProductionKey`, with no anchor and no responder identity, so one response is applied to **every** cache entry under that chunk key whose request covers its hashes (`find_pending_contracts`, `:492`). That was already the case at BASE, but the 2.14.0 subset test widens the match. The codes are content-verified by hash, so correctness is not at stake; whether a cross-anchor or cross-responder merge can slow a legitimate fetch (by consuming `received` slots an entry on our chain is waiting for) was not traced here.
- When `set_received_contracts` gives up on the per-request cap it resets the state to `Unknown` (`:372`), which is the same state the entry had before the accesses message arrived. A second `ChunkContractAccesses` for the same entry would therefore be able to re-open the request (`set_requested_contracts`, `:293`). Whether a duplicate accesses message can reach that path in practice was not determined.
- The per-request cap of 256 MiB is reachable: `MAX_CONTRACTS_PER_REQUEST = 1282` hashes at `max_contract_size = 4 MiB` is ~5 GiB. A chunk genuinely accessing more than ~64 maximal contracts can no longer have its code served at all, and its validators fall back to best-effort validation that will fail on the first missing body. Whether such a chunk is constructible given per-receipt gas and storage-proof limits was not established.
- Neither `ContractCodeRequest` nor `ContractCodeResponse` has an anchored V2 form, so neither is gated by `EarlyKickout`, and `ContractCodeRequest` is never retried. The recovery path when all responses to a request are lost is therefore the 2 s/6 s give-up plus a failed endorsement, not a retry; whether a retry was deliberately omitted was not determined from code.
- The resharding-boundary caveat on `collect_source_receipt_proofs` (`state_witness.rs:260`, "generates invalid proofs on resharding boundaries") is still an open TODO; the post-verification filtering it describes (via `filter_incoming_receipts_for_shard` at validation time, `chunk_validation.rs:504`) was not traced end-to-end across a live split here. The v87 fix (#16123) addressed *layout resolution* for the resharding implicit transition, not this proof-filtering TODO.
- `EarlyKickout` currently only persists and reads chunk-producer assignments; the kickout/blacklist consumer is noted as future work in the adapter docstring ("once dynamic sampling ships and the DB may diverge from computation", `chain/epoch-manager/src/adapter.rs:591`). The witness path's dependence on `DBCol::ChunkProducers` is therefore a hard dependency on a column whose semantics may still change.
- `PartialEncodedContractDeploys` V2 is emitted at v87/v88 but the deploy-distribution target set excludes all chunk producers, so on small networks the stream can be empty by construction (`partial_witness_actor.rs:384`); no protocol-level consequence was traced, but validators on such networks rely entirely on the accesses/request path.
