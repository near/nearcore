# Stateless validation

> Protocol version: 87 (stable) · Release: 2.14.0-rc.1 · Derived from commit: 233252e · Generated: 2026-09-14
> Primary crates/files: `core/primitives/src/stateless_validation/`, `chain/chain/src/stateless_validation/`, `chain/chain/src/signature_verification.rs`, `chain/client/src/stateless_validation/`

## Role

Stateless validation (NEP-509) is how the protocol verifies a chunk's state transition without every validator holding the full shard state. After a chunk producer applies a chunk, it packages the *recorded* trie reads (a Merkle proof) together with the transactions and source receipts into a **`ChunkStateWitness`**. The witness is compressed, Reed-Solomon erasure-coded, and distributed part-by-part to the chunk's assigned **chunk validators**. Each validator reconstructs the witness, re-applies the chunk against the partial trie (no full state needed), checks the replayed `ChunkExtra` / outgoing-receipts root against the chunk header, and emits a signed **`ChunkEndorsement`**. A chunk may be included in a block only once endorsements covering > 2/3 of the chunk-validator stake are collected. This component sits downstream of [sharding-chunks](sharding-chunks.md) (which produces the chunk) and [runtime-execution](runtime-execution.md) (which is replayed during validation against a partial trie from [state-storage](state-storage.md)); chunk-validator assignment comes from [epoch-validators-staking](epoch-validators-staking.md); witnesses/endorsements travel over [networking-p2p](networking-p2p.md); endorsements gate chunk inclusion in [chain-block-processing](chain-block-processing.md).

**What changed at v87.** `EarlyKickout` activated at 87 (`core/primitives-core/src/version.rs:626`), which flips every producer-signed witness/contract-distribution message from its V1 wire form to a **V2** form carrying the chunk's parent and **grandparent anchor**, and switches chunk-producer resolution from the epoch height sampler to an anchored `DBCol::ChunkProducers` lookup. At v86 the V2 variants existed but were inert; at v87 V1 is rejected and V2 is mandatory.

## Key data structures

- **`ChunkStateWitness`** — `core/primitives/src/stateless_validation/state_witness.rs:97` — versioned enum, only live variant `V2(Box<ChunkStateWitnessV2>) = 1` (V1 removed). `ChunkStateWitnessV2` (`:105`) fields: `epoch_id` (the epoch of the block *after* the chunk's prev block); `chunk_header` (the `ShardChunkHeader` being attested, kept so the validator knows what it endorses); `main_state_transition: ChunkStateTransition` (the new-chunk transition of the *last new chunk* of this shard); `source_receipt_proofs: HashMap<ChunkHash, ReceiptProof>` (a non-strict superset of the receipts to apply, with proofs against outgoing-receipt roots); `applied_receipts_hash` (redundant hash of the ordered `Vec<Receipt>` to apply, for diagnosis); `transactions` (the transactions the last new chunk converted to receipts); `implicit_transitions: Vec<ChunkStateTransition>` (one per missing chunk between the last new chunk and this chunk, forward chronological); `new_transactions` (transactions in *this* chunk).

## Behavior

### 1. Witness production (chunk producer, after applying its chunk)

`Client::send_chunk_state_witness_to_chunk_validators` (`chain/client/src/stateless_validation/state_witness_producer.rs:15`) drives production for a newly produced chunk:

1. Early-return if `ProtocolFeature::Spice` is enabled (`:23`) — SPICE has its own path (nightly-only, not enabled at v87).
2. Require a local validator signer (`:44`, else `Error::NotAValidator`), then build the witness via `ChainStore::create_state_witness` (`chain/chain/src/stateless_validation/state_witness.rs:45`).
3. If `save_latest_witnesses` is set, persist it for debugging (`:53`).
4. **Self-endorse shortcut**: if the producer is itself in the chunk-validator set for `(epoch, shard, height)`, it endorses immediately (bypassing validation, since it just applied the chunk) by calling `send_chunk_endorsement_to_block_producers` and feeding the returned self-endorsement to its own endorsement tracker (`:57`–`:72`).
5. Send a `DistributeStateWitnessRequest` to the `PartialWitnessActor` (`:74`).

`create_state_witness` (`state_witness.rs:45`) assembles the witness:
- `collect_state_transition_data` (`:100`) walks backwards from `chunk_header.prev_block_hash()` to the block at `prev_chunk_header.height_included()` (exclusive), reading each block's stored `StateTransitionData` as an *implicit transition* (one per missing chunk, plus an extra one when a resharding shard-id change happens between blocks, `:132`). Transitions are collected newest-first then `reverse()`d to forward order (`:165`). The **main transition** is the last new chunk's transition (`:168`), read via `get_state_transition` (`:194`) from `DBCol::StateTransitionData` keyed by `(block_hash, shard_id)`, with `post_state_root` taken from that block's `ChunkExtra` (`:231`). Genesis prev-chunk uses `get_genesis_state_transition` with empty base state (`:238`).
- `collect_source_receipt_proofs` (`:264`) gathers all incoming receipts for the *previous* chunk and their proofs (so the witness self-proves which receipts to apply), converting from `[block_hash -> Vec<ReceiptProof>]` to `[chunk_hash -> ReceiptProof]` (`:316`); a duplicate chunk proof is an error (`:331`). Genesis prev-chunk yields an empty map (`:270`).
- The witness carries `prev_chunk.to_transactions()` as `transactions` and the current `chunk.to_transactions()` as `new_transactions` (`:89`, `:91`).

Contract code is **not** in the witness: `ContractUpdates` (accessed code-hashes and newly deployed code) is returned alongside it in `CreateWitnessResult` (`state_witness.rs:34`) and distributed separately (step 6).

### 2. Encoding and distribution (`PartialWitnessActor`)

`handle_distribute_state_witness_request` (`chain/client/src/stateless_validation/partial_witness/partial_witness_actor.rs:253`) first resolves the epoch protocol version (`:288`) and the parent/grandparent anchors once — `prev_block_hash` from the chunk header and `prev_prev_block_hash` from `EpochManagerAdapter::grandparent_anchor` (`:295`, `chain/epoch-manager/src/adapter.rs:560`), defaulting to `CryptoHash::default()` when the chunk has no real grandparent. The producer has already processed the parent (it built on it), so this lookup cannot miss. It then sends three streams in priority order (`:296`–`:341`):

1. **Contract accesses first** (only if contracts were accessed): `send_contract_accesses_to_chunk_validators` (`:1006`) sends a signed `ChunkContractAccesses` (code-hashes only, not code) to chunk validators *except* chunk producers tracking the same shard (`:1026`), so validators can request missing code while witness parts are still in flight. The anchors and `protocol_version` are threaded in so `ChunkContractAccesses::new` emits V2 at v87.
2. **Witness parts** (compression/encoding moved to `witness_creation_spawner` to avoid blocking the actor, `:319`): `compress_and_distribute_witness` (`:346`) compresses (`compress_witness`, `:1361`), then `send_state_witness_parts` (`:418`) → `generate_state_witness_parts` (`:1315`) erasure-codes the compressed bytes into **one part per chunk validator** using a Reed-Solomon encoder sized to `chunk_validators.len()` with `WITNESS_RATIO_DATA_PARTS = 0.6` (`partial_witness/encoding.rs:6`). Part `i` is signed and addressed to chunk validator `i` (the part owner); all parts of one distribution share a wire version. Sent as `NetworkRequests::PartialEncodedStateWitness` (`:478`); the witness is recorded in `ChunkStateWitnessTracker` for round-trip-time metrics (`:470`).
3. **Contract deploys** (lower priority): `send_chunk_contract_deploys_parts` (`:1052`) compresses newly-deployed code and erasure-codes it via `generate_contract_deploys_parts` (`:374`) to non-producer validators, who will need it in later turns.

### 3. Part forwarding and reconstruction (chunk validator)

- A part owner receives its part via `handle_partial_encoded_state_witness` (`:483`). The shard-id metric label is bucketed through `shard_id_metric_label` (`:100`) so an off-layout `shard_id` off the wire collapses to `"unknown"` instead of minting an unbounded Prometheus child (`:88`). The part is then version-gated: `witness_version_mismatch` (`:80`, over `version_mismatch` at `:72`) drops a V1 part at/after `EarlyKickout` and a V2 part before it; an unresolvable epoch version is *not* treated as mismatch (`:508`).
- **Producer resolution** (`:526`): V1 uses the epoch height sampler `get_chunk_producer_info`; V2 uses `get_chunk_producer_info_anchored` on the signed grandparent (`:535`), which reads `DBCol::ChunkProducers` and therefore resolves even when the part races its parent block. `ChunkProducerNotInDB`/`MissingBlock` on an anchored message means this node is ≥2 blocks behind and the part is dropped quietly (`:545`).
- The part is validated on `partial_witness_spawner` (`validate_partial_encoded_state_witness`, `validate.rs:65`). **Only the part's designated owner re-broadcasts it** (`my_part_ord` computed at `:565`, checked at `:589`): producer-signed parts for other ordinals are still stored but not forwarded, so a single injected message cannot fan out across the validator set. Forwarding targets all chunk validators except the producer and self (`NetworkRequests::PartialEncodedStateWitnessForward`, `:598`); the part is stored locally either way (`:614`).
- Forwarded parts arrive at `handle_partial_encoded_state_witness_forward` (`:650`) with the same metric-label bucketing and version gate (`:676`), are validated and stored (`:703`). `DBNotFoundErr` (node behind) and an `EpochOutOfBounds` whose parent block is unknown are dropped quietly (`:716`, `:725`); anything else logs as invalid (`// TODO: ban sending peer`, `:737`).
- `PartialEncodedStateWitnessTracker` (`partial_witness_tracker.rs:472`) accumulates parts per **`WitnessCacheKey` = (chunk key, anchor)** in a per-shard `ShardWitnessTracker` (`:402`) holding an LRU `parts_cache` of `WITNESS_PARTS_CACHE_SIZE = 5` (`:38`) and a `processed_witnesses` LRU of 50 (`:43`). `store_partial_encoded_state_witness` builds the key from `prev_prev_block_hash()` (`:511`). `process_witness_part` (`:197`) feeds a `ReedSolomonPartsTracker`; when enough data parts arrive it decodes (`InsertPartResult::Decoded`, `:263`).
- **Eviction prefers off-chain anchors**: when the cache is full, `maybe_insert_new_entry_in_parts_cache` (`:807`) first drops the least-recently-used entry whose anchor is *not* the block our chain has at that height (`is_anchor_on_our_chain`, `:783`), so an anchor flood cannot push out the entry we actually need.
- `try_finalize` (`:353`) waits for **both** the witness parts (decoded) and the accessed-contract state to be ready; `AccessedContractsState::Unknown` counts as ready (`:363`) — the chunk may have no contracts, or the accesses message was lost (best-effort). A contract request that goes unanswered for `ACCESSED_CONTRACTS_REQUEST_TIMEOUT = 2 s` (`:48`) after the parts decoded is given up on (`contract_request_expired`, `:335`; `expire_contract_request`, `:345`; swept in `expire_stale_contract_requests`, `:436`) and the witness is validated without the code.
- On finalize, `deliver_witness` (`:689`) decodes, checks the decoded witness's `chunk_production_key` matches the cache key (`:734`), **extends** the main transition's `base_state` `TrieValues` with the separately-fetched contract codes (`:743`), and sends a `ChunkStateWitnessMessage` to the `ChunkValidationActor` (`:757`).

### 4. Validation (`ChunkValidationActor`)

`process_chunk_state_witness_message` (`chunk_validation_actor.rs:525`):
1. Reject if this node is not a validator (`:532`, `Error::Other`); send a `ChunkStateWitnessAck` back to the chunk producer for RTT metrics (`send_state_witness_ack`, `:194`) — the producer is resolved from the parent block (`get_chunk_producer_info_from_prev_block`) and falls back to the canonical sampler when the parent is absent, and a failure only logs, never aborts processing.
2. If the witness's prev block is not yet known, park it as an **orphan** in `OrphanStateWitnessPool` — only if `head_distance` is within `ALLOWED_ORPHAN_WITNESS_DISTANCE_FROM_HEAD = 2..6` (`:46`, `:251`) and under `max_orphan_witness_size` (`:265`); reprocessed when the block arrives via `process_ready_orphan_witnesses` (`:287`). The pool keys on `(ChunkProductionKey, chunk_hash)` (`chunk_validator/orphan_witness_pool.rs:20`), so two competing witnesses for the same chunk key coexist instead of evicting each other.
3. Otherwise `process_chunk_state_witness` (`:335`), which re-checks `chunk_header.prev_block_hash() == prev_block.hash()` (`:351`) → `start_validating_chunk` (`:371`).

`start_validating_chunk` (`:371`):
1. Confirm the witness `epoch_id` equals `get_epoch_id_from_prev_block` (`:397`).
2. `pre_validate_chunk_state_witness` (`chain/chain/src/stateless_validation/chunk_validation.rs:313`) — synchronous, cheap checks (below), producing a `PreValidationOutput` (struct `:82`).
3. **Chunk-extra shortcut**: if the validator already has the prev block's `ChunkExtra` on disk (e.g. it produced/tracked the shard), it validates the header directly via `validate_chunk_with_chunk_extra_and_roots` (`chain/chain/src/validate.rs:100`) and endorses without replaying (`:439`–`:452`).
4. Otherwise spawn the heavy `validate_chunk_state_witness` on `validation_spawner` (`:485`); on `Ok`, call `send_chunk_endorsement_to_block_producers` (`:500`).

`pre_validate_chunk_state_witness` (`chunk_validation.rs:313`):
- Check the chunk header version is allowed at the epoch's protocol version (`:323`) and that every `new_transaction` is valid for that protocol version (`:328`, else `Error::InvalidChunkStateWitness`).
- `get_state_witness_block_range` (`:145`) walks backwards from the witness's prev block, classifying each block by `num_new_chunks_seen` for the shard: 0 → contributes an `ApplyOldChunk` implicit transition; 1 → contributes a source-receipt block; 2 → stop. Resharding boundaries inject a `Resharding` implicit transition (`get_resharding_transition`, `:259`), keyed to the split's `left_child_shard`/`right_child_shard` and **now also carrying the boundary block hash** (`:296`, `:303`) — see step 4.3 below.
- `validate_source_receipt_proofs` (`:452`) extracts the receipts to apply from the proofs, validating each proof's `from_shard_id`/`to_shard_id` and Merkle path against the source chunk's outgoing-receipts root (`validate_receipt_proof`, `:532`), filtering for the target shard (`:504`) and shuffling into application order (`:511`). It also rejects extraneous proofs (`:522`). The hash of the ordered receipts must equal `applied_receipts_hash()` (`:364`), and the witness's `transactions` must merklize to the last new chunk's `tx_root` (`:371`/`:378`).
- Builds `MainTransition::Genesis` (`:411`) or `MainTransition::NewChunk` (`:425`) with `StorageDataSource::Recorded(PartialStorage { nodes: base_state })` — i.e. the runtime will read from the recorded proof, not a full trie (`:435`).

`validate_chunk_state_witness_impl` (`chunk_validation.rs:568`) — the consensus-critical re-execution:
1. **Main transition**: replay the last new chunk via `apply_new_chunk` (`:608`) against the recorded partial storage with `MaybePinnedMemtrieRoot::no_memtries()` (`:615`), producing a `ChunkExtra` and outgoing receipts. (Genesis skips replay, `:605`; a per-shard LRU cache of size `NUM_WITNESS_RESULT_CACHE_ENTRIES = 20` can short-circuit repeats, `:99`.)
2. Check the resulting `state_root` equals `main_state_transition.post_state_root` (`:625`) — an early debug check; the binding check is the chunk header at the end.
3. **Implicit transitions**: the count must equal `state_witness.implicit_transitions().len()` (`:665`, error at `:669`). For each, replay an old chunk (`apply_old_chunk`, `:699`) or apply a resharding split (`:711`) against that transition's recorded `base_state`. For the resharding case the parent and child **shard layouts are resolved from the locally determined boundary block hash**, not from the witness-supplied `block_hash` (`:727`, `:731`) — the boundary block is the last block of the old epoch, and resolving it locally matches what the producer did; child congestion info is recomputed from the parent trie before `retain_split_shard` (`:733`, `:743`). State root and congestion info are then updated (`:749`) and each is checked against the transition's `post_state_root` (`:751`, debug-only); the error message reports the boundary block hash for resharding transitions and the witness-supplied `block_hash` otherwise (`transition_block_hash`, `:680`).
4. **Final binding checks** (in parallel via `rayon::join`, `:765`): merklize the outgoing-receipt hashes and call `validate_chunk_with_chunk_extra_and_receipts_root` to bind `chunk_extra` (state root, gas, congestion) and the outgoing-receipts root to the **witness chunk header** (`:768`); and check `new_transactions` merklize to the header `tx_root` (`:778`, else `Error::InvalidTxRoot`) and the encoded-merkle-root via `validate_chunk_with_encoded_merkle_root` (`:780`).

On any failure `Error::InvalidChunkStateWitness` is returned; if `save_witness_if_invalid` is set the witness is cloned and persisted for debugging (`validate_chunk_state_witness`, `:795`, storing at `:826`).

**Missing contract code is a validation failure, not a no-op.** When replaying under `ApplyChunkReason::ValidateChunkStateWitness`, a `FunctionCall` to an account that commits to a code hash whose body is available from no source (in-chunk deploy record, recorded partial state, compiled-contract cache) returns `StorageError::MissingTrieValue` instead of the `CodeDoesNotExist` nop outcome (`runtime/runtime/src/function_call.rs:301`). Block production (`UpdateTrackedShard`) is unchanged, since a full node always resolves the body from its own trie. Without this a validator would recompute and endorse the wrong (no-op) transition.

### 5. Endorsement creation, gossip, aggregation

- `send_chunk_endorsement_to_block_producers` (`chain/client/src/stateless_validation/chunk_validator/mod.rs:22`) builds a `ChunkEndorsement::new` (`:62`) and sends it to the next `NUM_NEXT_BLOCK_PRODUCERS_TO_SEND_CHUNK_ENDORSEMENT = 5` unique block producers (`:16`, `:47`) — covering the case where the height-`h` block producer is skipped. If the signer is itself one of those producers, the endorsement is returned for immediate local processing (`:63`–`:72`).
- A block producer validates and stores received endorsements in `ChunkEndorsementTracker::process_chunk_endorsement` (`chain/client/src/stateless_validation/chunk_endorsement.rs:43`): dedup per validator (`:50`), `validate_chunk_endorsement` (relevance + both signatures, `validate.rs:168`), then cache by `ChunkProductionKey` in a 100-entry LRU (`:19`, `:60`).
- When producing a block, `collect_chunk_endorsements` (`:82`) filters cached endorsements to those whose `chunk_hash` matches the header (`:109`), then `compute_endorsement_state` decides inclusion: a chunk is includable iff `is_endorsed` (> 2/3 stake). The ordered signature vector (or empty) is what goes into the block body.
- `validate_chunk_endorsements_in_block` (`chain/chain/src/stateless_validation/chunk_endorsement.rs:19`) re-validates at block processing: chunk count == endorsement-vector count (`:24`); for each new chunk, the signature list length equals the ordered chunk-validator count (`:74`), each present signature verifies via `ChunkEndorsement::validate_signature` over bytes **rebuilt from the header's `chunk_hash`** (`:93`), > 2/3 stake is endorsed (`:113`), and the header's endorsement **bitmap** is consistent (length `:121`, bit-per-signature `:130`, trailing zeros `:141`). Old chunks (`height_included != block height`) must carry empty endorsements (`:50`). `validate_chunk_endorsements_in_header` (`:187`) checks the bitmap shape against the chunk mask; `validate_spice_chunk_endorsements_in_header` (`:158`) requires an all-empty bitmap under nightly SPICE.

### 6. Contract-code distribution (avoid shipping code in every witness)

Contract code is excluded from the witness and distributed out-of-band:
- Producer sends `ChunkContractAccesses` (hashes) to validators (step 2.1).
- Validator, in `handle_chunk_contract_accesses` (`partial_witness_actor.rs:914`), drops the message if its wire version is wrong for the epoch (`should_drop_for_version`, `:897`), validates it (`validate_chunk_contract_accesses`, `validate.rs:194` → `validate_witness_contract_accesses_signature`, `:380`, where V2 resolves the producer through the anchor at `:391`), filters out hashes already in its compiled-contract cache (`:968`), stores the missing set in the tracker **under the message's anchor** (`store_accessed_contract_hashes`, `:980`), and sends a signed `ContractCodeRequest` to a *random* chunk producer for the shard (`:985`–`:998`).
- Producer answers in `handle_contract_code_request` (`:1161`): validates and dedups per `(key, requester)` (`:1174`), caps at `MAX_CONTRACTS_PER_REQUEST` (`:1184`), re-derives the `MainTransitionKey` from its own chain (`derive_main_transition_key`, `:1086`) and requires it to equal the requested one (`:1192`), confirms each requested hash was actually accessed in that transition's stored `contract_accesses` (`:1216`, `:1229`), reads the raw code from the trie (`:1238`), and replies with `ContractCodeResponse::encode` — **V2 (signed) iff `SignedContractCodeResponse` is enabled, else V1 (unsigned)** (`contract_distribution.rs:378`, gate at `:384`); enabled at v87.
- Validator stores the received code (`handle_contract_code_response`, `:1263` → `store_accessed_contract_codes`, `:1275`), which the tracker merges into the witness base state at finalize (step 3). `validate_contract_code_response` requires and verifies the responder signature whenever `SignedContractCodeResponse` is enabled (`validate.rs:229`, `:237`, `:406`), and additionally requires the responder to be a chunk producer for the shard (`:418`).
- Newly-deployed contracts ride the separate `PartialEncodedContractDeploys` erasure-coded path (`handle_partial_encoded_contract_deploys`, `:758`; version-gated at `:763`, producer resolved through the anchor for V2 in `validate_partial_encoded_contract_deploys`, `validate.rs:139`; deployed code is precompiled once decoded, `:868`) so future-turn validators have them ahead of time.
- **Global contracts** are distributed by the global-contract mechanism, not by `contract_deploys` (`core/store/src/contract.rs:109`), but from v87 their distribution also calls `record_global_contract_deploy` so a same-chunk call can find the code without relying on a warm compiled-contract cache (`runtime/runtime/src/global_contracts.rs:221`, gated at `:219`).

### 7. Anchored producer resolution (shared V2 machinery)

`resolve_and_verify_anchored_producer` (`chain/chain/src/signature_verification.rs:190`) is the single entry point used by the witness, contract-accesses and contract-deploys receive paths:
1. `resolve_anchored_producer` (`:161`) calls `EpochManagerAdapter::get_chunk_producer_info_anchored` (`chain/epoch-manager/src/adapter.rs:594`), which reads `DBCol::ChunkProducers` keyed by the anchor when `EarlyKickout` is on and the anchor is in the chunk's epoch, and falls back to the canonical height sampler otherwise (feature off, no anchor, or a cross-epoch anchor in the first ≤2 blocks of an epoch). Outcomes are counted by `ANCHORED_CHUNK_PRODUCER_LOOKUP_TOTAL` (`chain/chain/src/metrics.rs:544`).
2. `verify_anchored_chunk_key` (`:87`) cross-checks the *signed* `(epoch_id, height_created, prev_prev_block_hash)` against what the parent block implies, when the parent is known. When the parent is absent, only the anchor constrains the chunk: the height must equal `anchor.height + CHUNK_GRANDPARENT_ANCHOR_HEIGHT_OFFSET` (2, `chain/epoch-manager/src/adapter.rs:35`) — a lower height is an error, a higher one is deferred as `DBNotFoundErr` (the chunk sits on a skipped slot and is re-checked once the parent lands). A default (genesis) anchor is only allowed up to `genesis_height + 1`.

## Invariants & failure modes

- **> 2/3 stake to endorse.** `has_enough_stake` requires `endorsed_stake >= total_stake*2/3 + 1` (`validator_assignment.rs:18`/`:22`); below threshold `compute_endorsement_state` clears the signature vector (`:82`) so the chunk cannot be included. Re-checked at block processing (`chain/chain/src/stateless_validation/chunk_endorsement.rs:113`).
- **Endorsement signed bytes are canonical.** Both the receive path and the consensus path derive the signed bytes from `chunk_hash` via `endorsement_signed_bytes` (`chunk_endorsement.rs:143`); the wire `signature_differentiator` is never read back. Before this fix a peer could pick the signed bytes through that field and pass `verify` while failing `validate_signature` at block validation.
- **State-root binding.** Final validation binds the replayed `ChunkExtra` and outgoing-receipts root to the witness chunk header (`chunk_validation.rs:768`); the intermediate `post_state_root` checks (`:625`, `:751`) are explicitly described in-code as debug aids, not the authoritative check.
- **Resharding layouts come from the local boundary block.** Both parent and child shard layouts for a `Resharding` implicit transition are resolved from `boundary_block_hash` recorded by the local `get_resharding_transition` (`:727`, `:731`), not from the witness-supplied `transition.block_hash`; a producer cannot steer layout resolution.
- **Receipts/transactions are self-proving.** `applied_receipts_hash` must match the receipts extracted from proofs (`:364`); `transactions` must merklize to the last new chunk's `tx_root` (`:378`); each source-receipt proof's shard ids and Merkle path are verified (`validate_receipt_proof`, `:532`); extraneous proofs are rejected (`:522`). Mismatch → `Error::InvalidChunkStateWitness`.
- **Implicit-transition count must match** between recomputed range and witness (`:665`), preventing a producer from hiding or inventing missing-chunk transitions.
- **Missing contract code fails validation** rather than replaying a `CodeDoesNotExist` no-op (`runtime/runtime/src/function_call.rs:301`).
- **Signature provenance.** Witness parts, contract accesses/requests/responses, and endorsements are all signed; validation rejects on bad signature or wrong signer (`validate.rs`, `chunk_endorsement.rs`). For V2 messages the producer is resolved from the signed grandparent anchor and the signed chunk key is cross-checked against the parent block (`signature_verification.rs:87`). A contract-code responder must be a chunk producer for the shard (`validate.rs:418`).
- **Only the designated part owner forwards.** A validator re-broadcasts a witness part only when `part_ord == my_part_ord` (`partial_witness_actor.rs:589`); other valid parts are stored but not fanned out.
- **Cache keys include the anchor.** `WitnessCacheKey` (`partial_witness_tracker.rs:59`) prevents a second, differently-anchored-but-validly-signed producer for the same chunk key from colliding with the entry we need; eviction prefers entries anchored off our chain (`:807`).
- **Metric labels are bounded.** `shard_id` off the wire is bucketed to `"unknown"` when outside the epoch's shard layout before being used as a Prometheus label (`partial_witness_actor.rs:100`, `:88`), so a peer cannot grow the registry with fresh label values.
- **Relevance gating drops, not errors.** `validate_chunk_relevant` (`validate.rs:280`) returns `TooLate` (height ≤ final head, `:309`), `TooEarly` (> head + `MAX_HEIGHTS_AHEAD = 5`, `:23`/`:320`), or `UnknownEpochId` (`:338`); these are dropped silently, while `NotAChunkValidator` (`:266`) / `InvalidShardId` (`:295`) / bad-signature are hard errors (potential malicious behavior, `// TODO: ban sending peer`, `partial_witness_actor.rs:635`).
- **Node-behind is not malice.** `DBNotFoundErr` (anchor/parent not processed) and an `EpochOutOfBounds` whose parent block is unknown are dropped quietly on the witness, contract-accesses and contract-deploys paths (`partial_witness_actor.rs:627`, `:716`, `:725`, `:780`, `:791`, `:938`, `:949`). V2 parts are never retransmitted, so the chunk recovers via the orphan-witness path or the producer's endorsement quorum instead.
- **Contract-fetch timeout is bounded.** A `ContractCodeRequest` that goes unanswered for 2 s after the witness parts decoded is abandoned and the witness is validated best-effort without the code (`partial_witness_tracker.rs:48`, `:335`, `:436`).
- **Orphan witnesses** outside `2..6` of head or over `max_orphan_witness_size` are not stored (`chunk_validation_actor.rs:251`/`:265`).
- **Size caps** reject oversized parts (`encoded_length` `validate.rs:84`, `part_size` `:102`) as `InvalidPartialChunkStateWitness`; decode failures surface as the same error ("failed to reed solomon decode witness parts, maybe malicious or corrupt data", `partial_witness_tracker.rs:708`), as does a decoded witness whose key disagrees with the part key (`:734`).

## Open questions

- The `ChunkStateWitnessV2.chunk_header` field is still marked `// TODO(stateless_validation): Deprecate this field in the next version of the state witness` (`state_witness.rs:113`) — it remains load-bearing for endorsement (the validator must know the chunk hash it signs), so removal is not realized at v87.
- The resharding-boundary caveat on `collect_source_receipt_proofs` (`state_witness.rs:260`, "generates invalid proofs on resharding boundaries") is still an open TODO; the post-verification filtering it describes (via `filter_incoming_receipts_for_shard` at validation time, `chunk_validation.rs:504`) was not traced end-to-end across a live split here. The v87 fix (#16123) addressed *layout resolution* for the resharding implicit transition, not this proof-filtering TODO.
- `EarlyKickout` currently only persists and reads chunk-producer assignments; the kickout/blacklist consumer is noted as future work in the adapter docstring ("once dynamic sampling ships and the DB may diverge from computation", `chain/epoch-manager/src/adapter.rs:591`). The witness path's dependence on `DBCol::ChunkProducers` is therefore a hard dependency on a column whose semantics may still change.
- `PartialEncodedContractDeploys` V2 is emitted at v87 but the deploy-distribution target set excludes all chunk producers, so on small networks the stream can be empty by construction (`partial_witness_actor.rs:385`); no protocol-level consequence was traced, but validators on such networks rely entirely on the accesses/request path.
