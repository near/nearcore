## Role

This component defines the shared wire/storage/consensus data structures of the protocol — blocks, chunks, transactions, receipts, actions, accounts, keys, hashes — and how they are serialized. It sits underneath essentially every other component: consensus and sync move `Block`/`BlockHeader`/`ShardChunkHeader`; the transaction pool and runtime move `SignedTransaction` and `Receipt`; state storage persists `Account`, `Receipt`, and trie values. The defining discipline here is **versioning by enum**: nearly every top-level type is an enum of `V0/V1/…` structs so the borsh wire format can evolve while old bytes remain parseable. This spec documents the *shape*, *versioning*, and *hashing* of these types; the algorithms that produce/consume them live in sibling specs — notably [consensus-finality](consensus-finality.md), [chain-block-processing](chain-block-processing.md), [sharding-chunks](sharding-chunks.md), [runtime-execution](runtime-execution.md), [state-storage](state-storage.md), and [accounts-keys](accounts-keys.md).

## Key data structures

### Hashing primitives

- **`CryptoHash`** — `core/primitives-core/src/hash.rs:26` — a `[u8; 32]` SHA-256 digest, the universal ID/commitment type. `hash_bytes` (`:36`) digests raw bytes; `hash_borsh` (`:46`) digests the borsh serialization of any `BorshSerialize` value; `hash_borsh_iter` (`:59`) prefixes a `u32` little-endian length then digests each item (equivalent to hashing a `Vec`). Serde renders it as base58 (`:137`), borsh as the raw 32 bytes.
- **`MerkleHash` / `StateRoot`** — `core/primitives-core/src/types.rs:9` and `core/primitives/src/types.rs:25` — both are type aliases for `CryptoHash`.
- **`merklize` / `combine_hash`** — `core/primitives/src/merkle.rs:47`, `:42` — `combine_hash` = `hash_borsh((h1, h2))`; `merklize` builds a binary Merkle tree over borsh-hashed leaves and returns `(root, per-leaf MerklePath)`. An empty array merklizes to `CryptoHash::default()`. `MerklePathItem` (`:18`) carries a sibling `hash` + `Direction::{Left,Right}` (`:37`); `MerklePath` (`:23`) is a `Vec` of them.
- **SHA3-256** is the second hash function in the protocol as of PV 87: it derives `0u` universal account ids (`core/primitives/src/utils.rs:502` — `derive_universal_account_id`) and ML-DSA-65 public-key handles. Keccak-256 (distinct from SHA3-256) derives `0s` deterministic account ids (`utils.rs:484` — `derive_near_deterministic_account_id`).

### Keys and signatures

- **`KeyType`** — `core/crypto/src/signature.rs:40` — `ED25519 = 0`, `SECP256K1 = 1`, `MLDSA65 = 2`. `is_post_quantum()` (`:50`) is an exhaustive match so a new scheme must make the choice explicitly.
- **`PublicKey`** — `:249` — `ED25519 | SECP256K1 | MLDSA65`; hand-written borsh (`:399`) writing a one-byte tag (`key_tag()`) then the raw key bytes.
- **`PublicKeyHandle`** — `:516` — the *on-trie* form: `ED25519 | SECP256K1 | MlDsa65(MlDsa65PublicKeyHandle)`, where the ML-DSA-65 arm stores the 32-byte SHA3-256 digest of the 1952-byte key rather than the key. `trie_id_len()` (`:544`) = 1 tag byte + handle bytes.
- **`KeyTag`** — `:353` — the shared, **reserved** borsh/`Hash` tag space for both enums: `Ed25519 = 0`, `Secp256k1 = 1`, `MlDsa65Full = 2`, `MlDsa65Hash = 3`. The two enums own disjoint subsets — `PublicKey` owns {0,1,2}, `PublicKeyHandle` owns {0,1,3} — and each deserializer matches `KeyTag` exhaustively and *rejects* the other's reserved tag with a named error ("borsh tag 3 is reserved for PublicKeyHandle (ML-DSA-65 hash); not a valid PublicKey" and the mirror image). This makes "a full ML-DSA-65 key in a handle-shaped slot" unrepresentable through any borsh round-trip. `PublicKeyHandle::full_pubkey()` was removed in this release; there is simply no way back from an ML-DSA-65 handle to its full key.
- **`Signature`** — `:1023` — `ED25519 | SECP256K1 | MLDSA65`. Its hand-written borsh (`:1130`, `:1150`) tags by `KeyType` (0/1/2), *not* `KeyTag`; there is no reserved tag 3 in the signature space.
- **Base58 parsing is bounded** — `core/crypto/src/signature.rs:1281` — `decode_bs58::<N>` decodes into a fixed `[u8; N]` and `decode_bs58_impl` (`:1287`) maps `bs58::decode::Error::BufferTooSmall` to `BadLength { received: expected + 1 }`, so parsing bails out as soon as the value outgrows its destination instead of decoding an attacker-sized string. `PublicKeyHandle::from_str` reaches this from untrusted JSON-RPC parameters (`after_key` on `view_access_key_list`, `chain/jsonrpc-primitives/src/types/view_access_key_list.rs:10`).

### Block header

- **`BlockHeader`** — `core/primitives/src/block_header.rs:803` — versioned enum `BlockHeaderV1..V7`. Each `BlockHeaderVN` (`:540`, …, `:710`) is `{ prev_hash, inner_lite, inner_rest, signature, #[borsh(skip)] hash }`. The `hash` field is `#[borsh(skip)]` and recomputed on deserialize via `#[borsh(init=init)]` (`:539`, `:557`).
- **`BlockHeaderInnerLite`** — `:30` — the light-client-facing half: `{ height, epoch_id, next_epoch_id, prev_state_root, prev_outcome_root, timestamp, next_bp_hash, block_merkle_root }`. Used by headers V1–V6.
- **`BlockHeaderInnerLiteV2`** — `:61` — **new in this release**, used only by `BlockHeaderV7` (spice, `:710`). - **`BlockHeaderInnerRest*`** — `:85` (V1) … `:399` (V7) — the remainder that gets hashed but is not shipped to light clients. - **`Approval` / `ApprovalInner`** — `:475`, `:466` — a block approval is `{ inner: Endorsement(prev_hash) | Skip(prev_height), target_height, signature, account_id }`. `approvals: Vec<Option<Box<Signature>>>` is embedded directly in `inner_rest`.

### Chunk

- **`ShardChunkHeaderInner`** — `core/primitives/src/sharding/shard_chunk_header_inner.rs:18` — versioned enum `V1..V6` (discriminants 0..5). The common fields are `prev_block_hash`, `prev_state_root`, `prev_outcome_root`, `encoded_merkle_root`, `encoded_length`, `height_created`, `shard_id`, `prev_gas_used`, `gas_limit`, `prev_balance_burnt`, `prev_outgoing_receipts_root`, `tx_root`, `prev_validator_proposals`.
- **`ChunkHash`** — `sharding.rs:39` — newtype over `CryptoHash`.
- **`ShardChunk`** (full/decoded chunk) — `:1105` — enum `V1 = 0 / V2 = 1`; `ShardChunkV2` (`:1094`) = `{ chunk_hash, header: ShardChunkHeader, transactions: Vec<SignedTransaction>, prev_outgoing_receipts: Vec<Receipt> }`.
- **`EncodedShardChunk`** — `:1327` — enum `V1 = 0 / V2 = 1`; the Reed-Solomon-erasure-encoded form. `TransactionReceipt(Vec<SignedTransaction>, Vec<Receipt>)` (`:1309`) is the payload that gets encoded.
- **`PartialEncodedChunk`** — `:790` — the gossiped form, `V1 = 0 / V2 = 1 / V3 = 2`. **`PartialEncodedChunkV3` (`:947`) is new in this release**: it adds `prev_prev_block_hash: CryptoHash` (the grandparent anchor, `parent.prev_hash()`, or `CryptoHash::default()` when the parent is genesis) and `epoch_id: EpochId` to V2's `{header, parts, prev_outgoing_receipts}`. Both new fields are attacker-controlled and documented as such (`:898`, `:907`): a forged value can resolve a *real* producer, so callers must cross-check them against the anchor/epoch implied by the parent block before trusting them. V3 is produced only when an anchor is supplied: `EncodedShardChunk::create_partial_encoded_chunk_with_arc_receipts` (`:1463`) takes an `anchor: Option<(CryptoHash, EpochId)>` and splits it into the two optional fields (`:1477`), and the `From<PartialEncodedChunkWithArcReceipts>` conversion (`:994`) emits V3 only when both are `Some`, falling back to V2 otherwise (`:1006`). The older `create_partial_encoded_chunk` (`:1436`) takes no anchor and only ever emits V1/V2. Each part carries a `merkle_proof` against `encoded_merkle_root` (`PartialEncodedChunkPart`, `:1069`); `ReceiptProof` (`:1042`) is `(Vec<Receipt>, ShardProof)`.

- **`Action`** — `core/primitives/src/action/mod.rs:375` — a `#[borsh(use_discriminant = true)]` enum whose tags are wire contract: `CreateAccount = 0`, `DeployContract = 1`, `FunctionCall = 2`, `Transfer = 3`, `Stake = 4`, `AddKey = 5`, `DeleteKey = 6`, `DeleteAccount = 7`, `Delegate = 8`, `DeployGlobalContract = 9`, `UseGlobalContract = 10`, `DeterministicStateInit = 11`, `TransferToGasKey = 12`, `WithdrawFromGasKey = 13`, `DelegateV2 = 14`, **`UniversalStateInit = 15` (new at PV 87)**. - **`UniversalStateInitAction`** — `:244` — `{ state_init: RawStateInit, deposit: Balance }`. The receiver id must equal `derive_universal_account_id(state_init)`; the deposit covers the new account's storage staking.
- **`Action::num_state_init_entries`** — `:515` — exhaustive (no wildcard arm) count of the storage entries an action makes its receipt prepay execution fees for: `DeterministicStateInit` counts `state_init.data().len()`, `UniversalStateInit` counts `state_init_counts(...).num_entries`, both `Delegate` variants recurse into their inner actions, everything else is 0.

### Universal accounts (`0u`)

- **`RawStateInit`** — `core/primitives-core/src/universal_state_init.rs:44` — a newtype over `Vec<u8>` holding the borsh of a `UniversalStateInit`. It is *the* protocol view of a state init, not a transport wrapper: the account id is SHA3-256 over exactly `self.0`, never over `borsh::to_vec(self)` (which would add a 4-byte length prefix). Serde renders it base64. It lives in the crypto-free core crate because the `near-vm-runner` host ABI forwards the bytes verbatim.
- **`UniversalStateInit`** — `core/primitives/src/universal_state_init.rs:51` — `V1(UniversalStateInitV1) = 0`, a discriminant-tagged enum. `UniversalStateInitV1` (`:68`) = `{ code: Option<GlobalContractIdentifier>, data: BTreeMap<Vec<u8>, Vec<u8>>, access_keys: BTreeSet<PublicKeyHandle> }`. Flat, not one variant per account kind: which fields are populated decides whether it is a key-only (EOA) or contract account. `BTree*` containers give the typed API a canonical encoding, but **decoding deliberately does not reject a non-canonical encoding of the same logical value** — such an encoding simply hashes to a different id, and canonicalization cannot be enforced end to end because contracts serialize their own nested state inside opaque storage values (`:12`–`:19`). `from_raw` (`:116`) rejects only malformed or trailing bytes.
- **`UniversalStateInitCounts`** — `core/primitives-core/src/universal_state_init.rs:56` — `{num_bytes, num_entries, num_keys}`, what the action is priced on. `state_init_counts` (`core/primitives/src/universal_state_init.rs:140`) takes `num_bytes` from the payload's own length (not the decoded form, since borsh drops duplicate storage keys on decode) and the other two from decoding; bytes that fail to decode yield zero entries and keys, a reachable and deliberately priced arm.
- **UAID address codec** — `core/primitives-core/src/universal_account_id.rs` — `UAID_PREFIX = "0u"` (`:20`), `UAID_DATA_SYMBOLS = 52` (`:22`), `UAID_LEN = 54` (`:24`). `encode_universal_account_id` (`:30`) emits `0u` + 52 lowercase Crockford-base32 symbols (`CROCKFORD = "0123456789abcdefghjkmnpqrstvwxyz"`, `:27` — `i l o u` excluded). `base32_encode` (`:44`) packs the 256 bits MSB-first; the 52nd symbol carries 1 hash bit plus 4 zero pad bits, so only two of the 32 symbols (`0` and `g`) can legally appear last. **There is no checksum** in the format. The base32 is hand-written rather than taken from a crate and was cross-checked against `data-encoding` over 40M random cases.
- **`AccountType::UniversalAccount`** — lives in the external `near-account-id` crate, bumped 2.0.0 → 3.0.0 in this release (`Cargo.toml:209`). It classifies an id as universal only when length, prefix, alphabet *and* the final-symbol padding rule all hold; anything else is a named account. Nearcore consumes it at e.g. `core/parameters/src/cost.rs:788` (transfer fee to a `0u` id).
- **`derive_universal_account_id`** — `core/primitives/src/utils.rs:502` — `encode_universal_account_id(sha3_256(state_init.0))`. It takes `RawStateInit`, not the typed value, precisely so re-serialization cannot change the id.

### Transaction

- **`Transaction`** — `core/primitives/src/transaction.rs:151` — enum `V0(TransactionV0) | V1(TransactionV1)` with a **hand-written** borsh impl (not a derived discriminant). `TransactionV0` (`:36`) = `{ signer_id, public_key, nonce: Nonce, receiver_id, block_hash, actions }`. `TransactionV1` (`:122`) replaces `nonce` with `TransactionNonce` (`:66`, either `Nonce` or a gas-key `{nonce, nonce_index}`) and adds `nonce_mode: NonceMode` (`:113`, `Monotonic`/`Strict`).
- **`Transaction::state_init_bootstrap`** — `:236` — **new in this release**. Recognizes a transaction shaped as a self-signed universal-account bootstrap: no gas-key nonce index, `signer_id == receiver_id`, and some top-level `Action::UniversalStateInit` whose `state_init` derives to that account id and whose `access_keys` contain the signing key's `PublicKeyHandle`. Matching on the *handle* is what makes it work for ML-DSA-65, where the trie stores only a hash. It deliberately does **not** look inside `Delegate` actions (a nested state init is validated against the delegate's receiver and runs in its own receipt) and it deliberately tolerates extra batched actions — safety comes from the runtime's uninitialized-account guard, not from restricting the action list. This is only the stateless half; existence/nonce are checked against state.
- **`SignedTransaction`** — `:453` — `{ transaction: Transaction, signature, #[borsh(skip)] hash, #[borsh(skip)] size }`; `hash`/`size` recomputed via `#[borsh(init=init)]` (`:452`, `:470`) from the borsh bytes of the inner `Transaction`. `get_size()` (`:484`) is the body-only length; `wire_size()` (`:494`) is the full borsh length including the signature — a ~3.3 KiB difference for ML-DSA-65. `size_for_limits` (`:504`) picks between them by protocol version. Serde ser/de is base64 of the borsh bytes.
- **`ValidatedTransaction`** — `:323` — newtype proving config checks *and* signature verification passed (`ValidatedTransaction::new`, `:327`; `check_valid_for_config`, `:348`).
- **`ExecutionOutcome`** — `:671` — `{ logs, receipt_ids, gas_burnt, #[borsh(skip)] compute_usage, tokens_burnt, executor_id, status: ExecutionStatus, metadata: ExecutionMetadata }`. `ExecutionStatus` (`:589`) is a discriminant enum `Unknown = 0 / Failure = 1 / SuccessValue = 2 / SuccessReceiptId = 3`; the comment on `status` notes it must stay last because light clients cannot parse `Failure`. `ExecutionMetadata` (`:711`) is `V1 = 0 / V2 = 1 / V3 = 2 / V4 = 3`; `ExecutionMetadataV4` (`:730`) is `{profile: ProfileDataV3, contracts: Vec<AccountContract>}`, one entry per action giving the contract attached to the receiver immediately before that action ran (`AccountContract::None` when the account did not yet exist). `ExecutionOutcomeWithId` (`:761`) pairs the outcome with its `id` (tx hash or receipt id).

### Account & access keys (shape only; semantics → [accounts-keys](accounts-keys.md))

- **`Account`** — `core/primitives-core/src/account.rs:81` — **restructured in this release** into two orthogonal axes. It is now `Uninitialized(UninitializedAccountV1) | Initialized(InitializedAccount)`, where `InitializedAccount` (`:89`) carries the old layout versioning `V1(AccountV1) | V2(AccountV2)`.
- **`UninitializedAccountV1`** — `:221` — `{amount, storage_usage, bootstrap_nonce: Nonce}`. Only a universal account can be uninitialized: it comes into existence when a transfer funds a `0u` id whose state init has not been applied yet. It has no contract, access keys or data. A deterministic `0s` account awaiting its state init is *not* this — it is an ordinary V1 account with no contract (`account.rs:317`). `bootstrap_nonce` is seeded exactly like a new access key, `(creation_block_height - 1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`, and is dropped by `Account::initialize` once the state init installs real access keys.
- **`AccountState`** — `:42` — `Initialized` (default) `| Uninitialized`; a serde-only projection so views can report the distinction. `InvalidAccountState` (`:63`) is the error for a change that does not fit the account's state ("account state has not been installed yet" / "account state has already been installed"); it is documented as unreachable on a healthy chain.
- **`Account` borsh** — `:737` (deser), `:764` (ser) — unchanged in shape, extended by one tag. `AccountV1` still serializes *unversioned* (legacy layout, no tag). Anything else is written as the `SERIALIZATION_SENTINEL` u128 (`= Balance::MAX`, `:252`) followed by a `BorshVersionedAccount` tag (`:731`): `V2(AccountV2) = 0`, **`Uninitialized(UninitializedAccountV1) = 1` (new)**. On deserialize the leading u128 is read and compared to the sentinel to disambiguate.
- **`AccountContract`** — `:139` — `None | Local(CryptoHash) | Global(CryptoHash) | GlobalByAccount(AccountId)`. Its predicates are now exhaustive matches rather than `matches!`, so a new variant forces a decision.
- **`AccessKey`** — `core/primitives-core/src/account.rs:801` — `{nonce: Nonce, permission: AccessKeyPermission}`. `AccessKeyPermission` (`:909`) = `FunctionCall | FullAccess | GasKeyFunctionCall(GasKeyInfo, FunctionCallPermission) | GasKeyFullAccess(GasKeyInfo)`; `GasKeyInfo` at `:880`.

### RPC/view shapes

Two new fields: `state: AccountState` (skipped when initialized) and `bootstrap_nonce: Option<Nonce>` — the only way a client can learn the nonce an uninitialized account's self-signed state init must carry, since there is no access key to query. **The `From<AccountView> for Account` conversions were removed**: a view can no longer be turned back into a state `Account`, because it cannot express the uninitialized variant faithfully.
- **`AccessKeyView`** — `:253` — `{nonce, permission}`, both now documented. **`AccessKeyList`** (`:334`) gained `last_key: Option<PublicKeyHandle>`, a pagination cursor; `view_access_key_list` takes matching `after_key`/`limit` request parameters.
- **`ActionView`** — `:1487` — a *separate* discriminant space from `Action`, also pinned with `#[borsh(use_discriminant = true)]` (`:1485`). Tags 0–8 coincide with `Action`'s, then the two spaces diverge: `ActionView` splits each global-contract variant into a by-hash / by-account-id pair, so `DeployGlobalContract = 9`, `DeployGlobalContractByAccountId = 10`, `UseGlobalContract = 11`, `UseGlobalContractByAccountId = 12`, `DeterministicStateInit = 13`, `TransferToGasKey = 14`, `WithdrawFromGasKey = 15` — each one or two higher than the `Action` tag for the same action. The only variant out of source order is `DelegateV2 = 16`, declared between `Delegate = 8` and `DeployGlobalContract = 9`; **`UniversalStateInit = 17` (new)** sits at the end. Do not assume `ActionView` tags match `Action` tags: e.g. `DeterministicStateInit` is `Action` tag 11 but `ActionView` tag 13, and `DelegateV2` is `Action` tag 14 but `ActionView` tag 16.
- **`ChunkHeaderView`** — `:1124` — `proposed_split: Option<Option<TrieSplit>>` (`:1157`). The outer `Option` distinguishes *absent* (a V4-or-earlier inner header) from *present-null* (a V5 inner header with no split), which selects the header version on the way back (`:1211`) and therefore changes the recomputed chunk hash. Since #16405 the field is decoded with `serde_with::rust::double_option::deserialize` so an explicit JSON `null` survives the round trip instead of collapsing to absent.
- **`BlockHeaderInnerLiteView`** — `:1049` — gained `chunk_execution_root: Option<CryptoHash>`. It is now built from `BlockHeader` accessors rather than from a borrowed `inner_lite`, since inner-lite is versioned.
- **`LightClientBlockView` / `LightClientBlockLiteView`** — `:2726`, `:2739` — **both lost their borsh derives** in this release. They are RPC response shapes; carrying a borsh derive meant they held two incompatible contracts at once (adding a serde field is free, adding a borsh field is a hard break). `LightClientBlockLiteView::hash()` now picks the inner-lite layout to hash by whether `chunk_execution_root` is present, so the header hash is reconstructed correctly for both pre-spice and spice headers.
- **`StoredLightClientBlock`** — `core/store/src/light_client_block.rs:22` — the new, frozen storage type for `DBCol::EpochLightClientBlocks`: `V1(StoredLightClientBlockV1) = 0` (`:27`) with `StoredBlockHeaderInnerLiteV1` (`:37`) whose `chunk_execution_root` is `Option<CryptoHash>`. The column is written once per epoch and never rewritten or garbage-collected, so rows outlive the binary that wrote them; giving it its own type means a later change to the view adds a variant instead of breaking stored rows. DB version is 51 (`core/store/src/db/metadata.rs:5`), with a 50→51 migration that reads either layout a version-50 binary could have written. Migration mechanics → [state-storage](state-storage.md).

## Behavior

### Serialization format selection

1. **Borsh** is used everywhere a byte layout must be *canonical* — hashing, consensus, storage, and the erasure-coded chunk payload. Borsh guarantees no two byte strings deserialize to the same value, which is why all hashed/committed types derive `BorshSerialize`/`BorshDeserialize` (see `docs/architecture/how/serialization.md`). Every such type also derives `ProtocolSchema` (`near_schema_checker_lib`) so a CI check catches accidental wire-format changes.
2. **Protobuf** is used only for the peer-to-peer transport envelope (`chain/network/src/network_protocol/network.proto`); the payloads it carries (blocks, chunks, txs) are borsh-encoded blobs inside proto fields. Network types are documented in [networking-p2p](networking-p2p.md).
3. **JSON** (serde) is the RPC/view representation. `CryptoHash` serializes as base58 (`hash.rs:137`); `SignedTransaction` serializes as base64 of its borsh bytes; `RawStateInit`, `DataReceipt.data` and global-contract `code` use base64 (`serde_as = Base64`). JSON is never hashed — with the single exception of `LightClientBlockLiteView::hash`, which re-serializes the view's inner-lite to borsh in order to recompute a header hash.

The distinction matters for hashing: only the borsh bytes are stable and canonical, so all commitments (block hash, chunk hash, tx hash, account id, receipt/outcome roots) are defined over borsh, never JSON. Where a view type must survive both worlds the two contracts are now split apart deliberately — see `StoredLightClientBlock` above.

### How IDs and hashes are derived

1. **Transaction hash** — `transaction.rs:144` `Transaction::get_hash_and_size` = `hash(borsh(transaction))`. `SignedTransaction.hash` caches this (`:470`). The signature is *not* part of the hash; the signature signs the hash bytes (`ValidatedTransaction::new`, `:339`).
2. **Block body hash** — `block_body.rs:220` `BlockBody::compute_hash` = `hash_borsh(self)` for V2/V3 (hashes the whole versioned enum including the discriminant); `BlockBodyV1` (`:24`) hashed the bare struct.
3. **Block header hash** — `block_header.rs:820` `compute_hash(prev_hash, inner_lite, inner_rest)` = `combine_hash(compute_inner_hash(inner_lite, inner_rest), prev_hash)`, where `compute_inner_hash` (`:814`) = `combine_hash(hash(inner_lite_bytes), hash(inner_rest_bytes))`. The two-part split lets light clients verify `inner_lite` without downloading `inner_rest`. `block_body_hash` lives inside `inner_rest` (from V4 on), so the body is committed transitively through the header hash. `compute_hash_and_sign` (`:1147`) is now generic over the inner-lite type `L: BorshSerialize`, because V7 hashes `BlockHeaderInnerLiteV2` instead.
4. **Block hash** — the block's hash *is* its header hash (`block.rs:603`).
5. **Chunk hash** — `sharding.rs:296` `ShardChunkHeaderV3::compute_hash(inner)` = `ChunkHash(combine_hash(hash(borsh(inner)), inner.encoded_merkle_root()))`. `ShardChunkHeaderV2` does the same (`:191`); `ShardChunkHeaderV1` (`:743`) is just `hash(borsh(inner))` with no combine. `ShardChunkHeader::compute_hash` (`:683`) dispatches. Because the hash is over the *versioned* inner enum, the inner version is load-bearing for the chunk hash — hence the `proposed_split` absent/null distinction in `ChunkHeaderView`.
6. **Receipt / data / action ids** — `core/primitives/src/utils.rs:353` `create_hash_index(base, block_height, salt)` = `hash(base || block_height.to_le_bytes() || salt.to_le_bytes())`. Receipt id from a tx uses salt 0 (`:295`); from a parent receipt uses the receipt index (`:303`); action hashes count *down* from `u64::MAX` to avoid colliding with receipt-id salts (`:312`); a receipt id from an action hash uses the receipt index again (`:324`). Block *height* (not hash) is the fork-uniqueness salt because optimistic blocks lack a hash at id-generation time (`:346`).
7. **Account ids that are hashes** — `0s` deterministic accounts are `"0s" + hex(keccak256(borsh(DeterministicAccountStateInit))[12..32])` (`utils.rs:484`); `0u` universal accounts are `UAID(sha3_256(raw_state_init_bytes))` (`utils.rs:502`). Both make the id a commitment to the account's initial state, which is what lets a self-signed bootstrap transaction be authorized by the id alone.
8. **Merkle roots in the header** — computed from the chunk headers via the `Chunks` view (`block.rs:822`–`:845`): `compute_state_root`, `compute_chunk_prev_outgoing_receipts_root`, `compute_chunk_headers_root` (over `ChunkHashHeight` pairs), `compute_chunk_tx_root`, `compute_outcome_root`, each a `merklize` over the corresponding per-chunk field.
9. **Outcome hashing for proofs** — `transaction.rs:792` `ExecutionOutcomeWithId::to_hashes` produces `[id, hash_borsh(PartialExecutionOutcome), per-log hashes]`; `PartialExecutionOutcome` (`:619`) excludes logs/metadata so light clients hash a stable subset.

### Versioned deserialization dispatch

Some types use bespoke borsh dispatch instead of a leading discriminant, relying on the fact that an `AccountId`'s borsh length prefix has a zero second byte:

1. **`Transaction`** (`transaction.rs:282`) — reads two bytes: `u2 == 0` ⇒ V0 (both bytes pushed back); `u1 == 1 && u2 != 0` ⇒ V1 (consume the `1` tag). Any other `u1` errors with "invalid transaction version tag" (`:314`).
2. **`Receipt`** (`receipt.rs:228`) — currently always V0; the same second-byte reservation is documented for a future V1.
3. **`ReceiptOrStateStoredReceipt`** (`receipt.rs:311`) — sniffs for the two `0xFF` sentinel bytes to distinguish a state-stored receipt from a plain receipt.
4. **`Account`** (`account.rs:737`) — reads the leading u128; sentinel ⇒ versioned `BorshVersionedAccount` (`V2 = 0`, `Uninitialized = 1`), otherwise legacy `AccountV1`.
5. **`PublicKey` / `PublicKeyHandle`** (`signature.rs:407`, `:681`) — read one byte, convert through `KeyTag` (`:360` `TryFrom<u8>`), and reject the *other* enum's reserved tag by name rather than falling through to a generic "unknown tag".
6. **`NonDelegateAction`** (`delegate.rs:434`) — reads the `Action` tag and rejects `8`/`14` before delegating to the derived variant deserializer.

For enum types that *do* use `#[borsh(use_discriminant = true)]` (Block, BlockBody, ShardChunkHeader, ShardChunkHeaderInner, PartialEncodedChunk, ReceiptEnum, Action, ExecutionStatus, ExecutionMetadata, UniversalStateInit, VersionedDelegateActionPayload, StoredLightClientBlock, …), the leading byte is the explicit variant tag pinned in the source, so those tags are part of the wire contract.

## Invariants & failure modes

- **Borsh canonicality:** every hashed/committed type round-trips through borsh with a unique byte representation; schema drift is caught by the `protocol-schema-check` CI (`docs/architecture/how/serialization.md`). Adding/reordering enum variants without a new versioned type can silently corrupt stored/consensus data.
- **Canonicality is *not* enforced for `RawStateInit`.** `UniversalStateInit::from_raw` accepts any well-formed borsh, including a non-canonical encoding of the same logical value; such an encoding is simply a different account (`core/primitives/src/universal_state_init.rs:12`–`:19`). The id commits to the exact bytes hashed, never to a re-serialization — which is why `derive_universal_account_id` takes `RawStateInit` (`utils.rs:502`). A corollary stated in-source: **a new `UniversalStateInit` variant must arrive behind a protocol feature**, because gas depends on what decodes and two nodes on one protocol version disagreeing about what decodes would charge different gas (`universal_state_init.rs:135`).
- **Key tags are disjoint:** borsh tag 2 (full ML-DSA-65 key) can never decode as a `PublicKeyHandle` and tag 3 (the 32-byte hash) can never decode as a `PublicKey` (`signature.rs:353`). Both deserializers match `KeyTag` exhaustively, so a future scheme cannot silently reuse a reserved tag.
- **Base58 parsing is bounded:** a 100k-character key string is rejected in microseconds because decoding targets a fixed-size buffer and `BufferTooSmall` is reported as `received = expected + 1` (`signature.rs:1287`).
- **`#[borsh(skip)]` cached fields must be recomputed:** `BlockHeaderVN.hash`, `SignedTransaction.{hash,size}`, and `ShardChunkHeaderV*.hash` are skipped on the wire and rebuilt by the `#[borsh(init=…)]` hook on deserialize (`block_header.rs:539`, `transaction.rs:452`, `sharding.rs:140`/`:154`/`:237`). `ExecutionOutcome.compute_usage` is skipped and is `None` after a DB read (`transaction.rs:683`).
- **Version-tag validity:** `Transaction::deserialize_reader` errors "invalid transaction version tag" on an unknown first byte (`transaction.rs:314`); `StateStoredReceipt::deserialize_reader` errors on a wrong sentinel or unknown version byte (`receipt.rs:264`); `PartialState::check_entry_limit` errors "unknown PartialState variant" / "state part entry limit exceeded" (`state.rs:56`, `:63`).
- **Chunk-header version must match the protocol version:** `ShardChunkHeader::validate_version` (`sharding.rs:616`) accepts only inner V4 unconditionally, V5 under `DynamicResharding`, V6 under `Spice`, and rejects V1/V2 headers and inner V1–V3 outright with `BadHeaderForProtocolVersionError`.
- **`PartialEncodedChunkV3`'s new fields are untrusted:** `prev_prev_block_hash` and `epoch_id` are attacker-controlled and a forged value resolves a real producer; they are only safe after the cross-check in `resolve_and_verify_anchored_producer` (`sharding.rs:898`, `:907`). → [sharding-chunks](sharding-chunks.md).
- **Delegate nesting is structurally impossible:** `NonDelegateAction`'s private constructor plus its hand-written deserializer (`delegate.rs:434`) mean a `Transaction`/`Receipt` containing a nested delegate cannot be serialized-then-deserialized, which several call sites rely on.
- **Block self-consistency:** `Block::check_validity` (`block.rs:617`) recomputes `prev_state_root` (skipped for spice blocks), receipts/headers/tx/outcome roots, and the `chunk_mask` from the embedded chunk headers and returns `BlockValidityError::{InvalidStateRoot, InvalidReceiptRoot, InvalidChunkHeaderRoot, InvalidTransactionRoot, InvalidChunkMask}` (`:41`) on mismatch.
- **New blocks are BlockV4:** `Block::new_block` panics ("attempted to include BlockBodyV1 in new protocol version") if constructed with a `BlockBodyV1` (`block.rs:105`).
- **Header build requires the endorsement bitmap:** `new_impl` panics if `chunk_endorsements` is `None` for V5+ headers (`block_header.rs:1021`), and under Spice also if `prev_last_certified_block_epoch_id`, `spice_chunk_endorsement_stats` or `chunk_execution_root` are absent (`:1027`–`:1035`). Spice blocks carry an *empty* endorsement bitmap per shard, since endorsements are not included in spice blocks (`block.rs:242`).
- **`merklize` of an empty slice** yields `CryptoHash::default()` (`merkle.rs:48`), so a block with no chunks has zero-valued roots.
- **UAID encoding is total and checked:** `encode_universal_account_id` `expect`s that its output parses as an `AccountId` (`universal_account_id.rs:38`); the emitted charset and 54-byte length always satisfy that. There is **no checksum**, so a UAID with a typo that still satisfies length/alphabet/padding is a valid id for a different (almost certainly non-existent) account.
