## Role

This component defines the shared wire/storage/consensus data structures of the protocol — blocks, chunks, transactions, receipts, actions, accounts, keys, hashes — and how they are serialized. It sits underneath essentially every other component: consensus and sync move `Block`/`BlockHeader`/`ShardChunkHeader`; the transaction pool and runtime move `SignedTransaction` and `Receipt`; state storage persists `Account`, `Receipt`, and trie values. The defining discipline here is **versioning by enum**: nearly every top-level type is an enum of `V0/V1/…` structs so the borsh wire format can evolve while old bytes remain parseable. This spec documents the *shape*, *versioning*, and *hashing* of these types; the algorithms that produce/consume them live in sibling specs — notably [consensus-finality](consensus-finality.md), [chain-block-processing](chain-block-processing.md), [sharding-chunks](sharding-chunks.md), [runtime-execution](runtime-execution.md), [state-storage](state-storage.md), and [accounts-keys](accounts-keys.md).

## Key data structures

### Hashing primitives

- **`CryptoHash`** — `core/primitives-core/src/hash.rs:26` — a `[u8; 32]` SHA-256 digest, the universal ID/commitment type. `hash_bytes` (`:36`) digests raw bytes; `hash_borsh` (`:46`) digests the borsh serialization of any `BorshSerialize` value; `hash_borsh_iter` (`:59`) prefixes a `u32` little-endian length then digests each item (equivalent to hashing a `Vec`). Serde renders it as base58 (`:137`), borsh as the raw 32 bytes.
- **`MerkleHash` / `StateRoot`** — `core/primitives-core/src/types.rs:9` and `core/primitives/src/types.rs:25` — both are type aliases for `CryptoHash`.
- **`merklize` / `combine_hash`** — `core/primitives/src/merkle.rs:47`, `:42` — `combine_hash` = `hash_borsh((h1, h2))`; `merklize` builds a binary Merkle tree over borsh-hashed leaves and returns `(root, per-leaf MerklePath)`. An empty array merklizes to `CryptoHash::default()`. `MerklePathItem` (`:18`) carries a sibling `hash` + `Direction::{Left,Right}` (`:37`); `MerklePath` (`:23`) is a `Vec` of them.
- **SHA3-256** is the second hash function in the protocol: it derives ML-DSA-65 public-key handles (live since PV 85) and `0u` universal account ids (`core/primitives/src/utils.rs:503` — `derive_universal_account_id`, live from PV 88). Keccak-256 (distinct from SHA3-256) derives `0s` deterministic account ids (`utils.rs:484` — `derive_near_deterministic_account_id`).

### Keys and signatures

- **`KeyType`** — `core/crypto/src/signature.rs:39` — `ED25519 = 0`, `SECP256K1 = 1`, `MLDSA65 = 2`. `is_post_quantum()` (`:49`) is an exhaustive match so a new scheme must make the choice explicitly.
- **`PublicKey`** — `:248` — `ED25519 | SECP256K1 | MLDSA65`; hand-written borsh (`:398`) writing a one-byte tag (`key_tag()`) then the raw key bytes.
- **`PublicKeyHandle`** — `:515` — the *on-trie* form: `ED25519 | SECP256K1 | MlDsa65(MlDsa65PublicKeyHandle)`, where the ML-DSA-65 arm stores the 32-byte SHA3-256 digest of the 1952-byte key rather than the key. `trie_id_len()` (`:543`) = 1 tag byte + handle bytes.
- **`KeyTag`** — `:352` — the shared, **reserved** borsh/`Hash` tag space for both enums: `Ed25519 = 0`, `Secp256k1 = 1`, `MlDsa65Full = 2`, `MlDsa65Hash = 3`. The two enums own disjoint subsets — `PublicKey` owns {0,1,2}, `PublicKeyHandle` owns {0,1,3} — and each deserializer matches `KeyTag` exhaustively and *rejects* the other's reserved tag with a named error ("borsh tag 3 is reserved for PublicKeyHandle (ML-DSA-65 hash); not a valid PublicKey" and the mirror image). This makes "a full ML-DSA-65 key in a handle-shaped slot" unrepresentable through any borsh round-trip. There is no `PublicKeyHandle::full_pubkey()`: there is simply no way back from an ML-DSA-65 handle to its full key.
- **`Signature`** — `:1022` — `ED25519 | SECP256K1 | MLDSA65`. Its hand-written borsh (`:1129`, `:1149`) tags by `KeyType` (0/1/2), *not* `KeyTag`; there is no reserved tag 3 in the signature space.
- **Base58 parsing is bounded** — `core/crypto/src/signature.rs:1280` — `decode_bs58::<N>` decodes into a fixed `[u8; N]` and `decode_bs58_impl` (`:1286`) maps `bs58::decode::Error::BufferTooSmall` to `BadLength { received: expected + 1 }`, so parsing bails out as soon as the value outgrows its destination instead of decoding an attacker-sized string. `PublicKeyHandle::from_str` reaches this from untrusted JSON-RPC parameters (`after_key` on `view_access_key_list`, `chain/jsonrpc-primitives/src/types/view_access_key_list.rs:10`).

### Block header

- **`BlockHeader`** — `core/primitives/src/block_header.rs:910` — versioned enum `BlockHeaderV1..V8`. It has **no** `#[borsh(use_discriminant = true)]`, so the tags are borsh's implicit declaration order: `BlockHeaderV1 = 0` … `BlockHeaderV7 = 6`, **`BlockHeaderV8 = 7` (new in this release)**. Each `BlockHeaderVN` (`:607`, `:638`, `:660`, `:689`, `:718`, `:747`, `:777`, `:807`) is `{ prev_hash, inner_lite, inner_rest, signature, #[borsh(skip)] hash }`. The `hash` field is `#[borsh(skip)]` and recomputed on deserialize via `#[borsh(init=init)]` (`:606`; the eight `init` bodies at `:624`, `:825`, `:835`, `:845`, `:855`, `:865`, `:875`, `:885`).
- **`BlockHeaderInnerLite`** — `:30` — the light-client-facing half: `{ height, epoch_id, next_epoch_id, prev_state_root, prev_outcome_root, timestamp, next_bp_hash, block_merkle_root }`. Used by headers **V1–V7**.
- **`BlockHeaderInnerLiteV2`** — `:61` — the same eight fields plus `chunk_execution_root: CryptoHash`, a Merkle root over the block's certified chunk execution results. Used by **`BlockHeaderV8` only** (`:807`). Because the *inner lite* half is versioned, there is no `BlockHeader::inner_lite()` accessor; the field is read through `BlockHeader::chunk_execution_root() -> Option<CryptoHash>` (`:1889`), which is `None` for V1–**V7** and `Some` only for V8.
- **`BlockHeaderV7` vs `BlockHeaderV8`** — `:777`, `:807` — V7 is `{ BlockHeaderInnerLite, BlockHeaderInnerRestV7 }`, V8 is `{ BlockHeaderInnerLiteV2, BlockHeaderInnerRestV8 }`. `BlockHeaderInnerRestV8` (`:466`) is **field-for-field identical** to `BlockHeaderInnerRestV7` (`:399`) — same names, same types, same order, so the same borsh bytes. It exists only so that a later change to V8 cannot perturb the V7 layout (doc comment at `:453`: "Same fields as `BlockHeaderInnerRestV7`, kept separate so that V8 changes do not change the V7 layout"). Verified field-for-field at this commit: `BlockHeaderV7` and `BlockHeaderInnerRestV7` are byte-identical to the same two types at tag `2.13.0`, and V7 keeps implicit tag 6 because V8 was appended after it. The *only* wire difference between a V7 and a V8 header is therefore the extra 32-byte `chunk_execution_root` in the inner lite, plus the enum tag. V7 is now a **dead version**: nothing produces it (`new_impl` emits V8 under Spice, `:1179`), `is_spice()` is false for it (`:1989`), and from PV 87 it is rejected outright in a pre-Spice epoch — see **Protocol-version-gated behavior**.
- **`BlockHeaderInnerRest*`** — `:85` (V1) … `:466` (V8) — the remainder that gets hashed but is not shipped to light clients. Version deltas, in order: V1→V2 drops `chunks_included` (`:127`); V2→V3 adds `block_ordinal`/`prev_height`/`epoch_sync_data_hash` and switches to the new `ValidatorStake` (`:170`); V3→V4 adds `block_body_hash` (`:225`); V4→V5 adds `chunk_endorsements: ChunkEndorsementsBitmap` (`:282`); V5→V6 adds `shard_split: Option<(ShardId, AccountId)>` and drops the deprecated `challenges_root`/`challenges_result` (`:341`); V6→V7 adds the spice fields `prev_last_certified_block_epoch_id` + `spice_chunk_endorsement_stats` (`:399`); V7→V8 changes nothing (`:466`).
- **`Approval` / `ApprovalInner`** — `:542`, `:533` — a block approval is `{ inner: Endorsement(prev_hash) | Skip(prev_height), target_height, signature, account_id }`. `approvals: Vec<Option<Box<Signature>>>` is embedded directly in `inner_rest`.

- **`ShardChunk`** (full/decoded chunk) — `:1105` — enum `V1 = 0 / V2 = 1`; `ShardChunkV2` (`:1094`) = `{ chunk_hash, header: ShardChunkHeader, transactions: Vec<SignedTransaction>, prev_outgoing_receipts: Vec<Receipt> }`.
- **`EncodedShardChunk`** — `:1327` — enum `V1 = 0 / V2 = 1`; the Reed-Solomon-erasure-encoded form. `TransactionReceipt(Vec<SignedTransaction>, Vec<Receipt>)` (`:1309`) is the payload that gets encoded.
- **`PartialEncodedChunk`** — `:790` — the gossiped form, `V1 = 0 / V2 = 1 / V3 = 2`. **`PartialEncodedChunkV3` (`:947`) is new in this release**: it adds `prev_prev_block_hash: CryptoHash` (the grandparent anchor, `parent.prev_hash()`, or `CryptoHash::default()` when the parent is genesis) and `epoch_id: EpochId` to V2's `{header, parts, prev_outgoing_receipts}`. ### Actions

- **`Action`** — `core/primitives/src/action/mod.rs:375` — a `#[borsh(use_discriminant = true)]` enum whose tags are wire contract: `CreateAccount = 0`, `DeployContract = 1`, `FunctionCall = 2`, `Transfer = 3`, `Stake = 4`, `AddKey = 5`, `DeleteKey = 6`, `DeleteAccount = 7`, `Delegate = 8`, `DeployGlobalContract = 9`, `UseGlobalContract = 10`, `DeterministicStateInit = 11`, `TransferToGasKey = 12`, `WithdrawFromGasKey = 13`, `DelegateV2 = 14`, **`UniversalStateInit = 15`** (the variant exists unconditionally; acceptance is gated on `UniversalAccounts`, **PV 88**). - **`UniversalStateInitAction`** — `:244` — `{ state_init: RawStateInit, deposit: Balance }`. The receiver id must equal `derive_universal_account_id(state_init)`; the deposit covers the new account's storage staking.
- **`Action::state_init_counts`** — `:518` — **renamed and widened in this release** (was `num_state_init_entries`, returning a bare `u64`). It now returns a `StateInitCounts` (`:568`) of `{entries, keys}`, because both limits need the same borsh decode of the payload and keeping them in one accessor is what stops them drifting apart. - **`Action::post_quantum_signatures_required`** — `:457` — likewise exhaustive; the `UniversalStateInit` arm decodes the state init **leniently** (`UniversalStateInit::from_raw_lenient`) and reports true if any access-key *handle* is post-quantum. - **Delegate actions** — `core/primitives/src/action/delegate.rs`. `SignedDelegateAction` (`:78`) wraps `DelegateAction` (`:46`); `VersionedSignedDelegateAction` (`:205`) wraps `VersionedDelegateActionPayload` (`:159`), an enum with a single `V2(DelegateActionV2) = 0` variant. **Both the `Action::DelegateV2` variant and `VersionedDelegateActionPayload` are retained at PV 87 even though `RejectDelegateV2` disables them**, so a future delegate version can reuse the tag and the payload enum (`core/primitives-core/src/version.rs:453`). `NonDelegateAction` (`:371`) enforces the no-nesting rule structurally: its hand-written borsh deserializer (`:434`) refuses any tag in `DELEGATE_VARIANT_NUMBERS = [8, 14]` (`:26`) with "DelegateAction mustn't contain a nested one".

### Universal accounts (`0u`)

- **`RawStateInit`** — `core/primitives-core/src/universal_state_init.rs:43` — a newtype over `Vec<u8>` holding the borsh of a `UniversalStateInit`. It is *the* protocol view of a state init, not a transport wrapper: the account id is SHA3-256 over exactly `self.0`, never over `borsh::to_vec(self)` (which would add a 4-byte length prefix). Serde renders it base64. It lives in the crypto-free core crate because the `near-vm-runner` host ABI forwards the bytes verbatim.
- **`UniversalStateInit`** — `core/primitives/src/universal_state_init.rs:60` — `V1(UniversalStateInitV1) = 0`, a discriminant-tagged enum (`:57`). `UniversalStateInitV1` (`:77`) = `{ code: Option<GlobalContractIdentifier>, data: BTreeMap<Vec<u8>, Vec<u8>>, access_keys: BTreeSet<PublicKeyHandle> }`. Flat, not one variant per account kind: which fields are populated decides whether it is a key-only (EOA) or contract account. The `BTree*` containers mean the typed API always emits sorted, duplicate-free borsh — the *canonical* encoding. Whether a non-canonical encoding of the same logical value is accepted is **version-dependent**; see `DecodeMode` below and the canonicality entry under **Invariants & failure modes**.
- **`DecodeMode`** — `core/primitives-core/src/universal_state_init.rs:78` — **new in this release**: `Lenient | Strict`. `DecodeMode::strict_if(bool)` (`:87`) is the constructor every call site uses, fed from `ProtocolFeature::CanonicalUniversalStateInit.enabled(...)`. Three decoders implement it in `core/primitives/src/universal_state_init.rs`: `from_raw_lenient` (`:152`) accepts any well-formed borsh, rejecting only malformed or trailing bytes; `from_raw_strict` (`:135`) additionally re-encodes the decoded value and requires `decoded.to_raw() == *raw`, i.e. byte-for-byte canonicality; `from_raw(raw, mode)` (`:124`) dispatches. The in-source comment notes borsh's `de_strict_order` was *not* used because it is a crate-wide feature that would change how every other `BTreeMap`/`BTreeSet` in the node decodes.
- **`StateInitError`** — `core/primitives-core/src/universal_state_init.rs:53` — **new**: `Malformed` ("bytes do not decode into a universal state init") | `NonCanonical` ("state init is not in canonical borsh form"). It is not a wire type; `exit_status()` (`:65`) maps it to the `u64` status the `universal_state_init_to_account_id` host function returns — `0` success, `1` malformed, `2` non-canonical (`runtime/near-vm-runner/src/logic/host.rs:3321`). Before `CanonicalUniversalStateInit` the host never inspects the bytes and `0` is the only status it can return.
- **`UniversalStateInitCounts`** — `core/primitives-core/src/universal_state_init.rs:98` — `{num_bytes, num_entries, num_keys}`, what the action is priced on. Two producers, split apart in this release:
  - `state_init_counts(raw)` (`core/primitives/src/universal_state_init.rs:168`) — what an *existing* action is priced on. Takes `num_bytes` from the payload's own length (not the decoded form, since borsh drops duplicate storage keys on decode) and the other two from a **lenient** decode. It takes no `DecodeMode` on purpose: receipts created under earlier protocol versions are re-priced from it (refunds, among other things), so it must give the same answer on every version. Bytes that fail to decode yield zero entries and keys, a reachable and deliberately priced arm.
  - `state_init_send_counts(raw, mode)` (`:184`) — **new**: what a contract is charged at *send* time, before validation. In `Lenient` mode it is exactly `state_init_counts`. In `Strict` mode a payload that passes `from_raw_strict` is charged `decoded_counts` (`:197`, identical to `state_init_counts` for canonical bytes) and one that fails it is charged `upper_bound_counts` (`:207`): the most entries and keys its length could hold (`MIN_ENTRY_BYTES = 8`, `MIN_KEY_BYTES = 33`, minus 6 and 10 bytes of framing, each rounded up), because the decoder had to walk every byte before rejecting it.
- **UAID address codec** — `core/primitives-core/src/universal_account_id.rs` — `UAID_PREFIX = "0u"` (`:20`), `UAID_DATA_SYMBOLS = 52` (`:22`), `UAID_LEN = 54` (`:24`). `encode_universal_account_id` (`:30`) emits `0u` + 52 lowercase Crockford-base32 symbols (`CROCKFORD = "0123456789abcdefghjkmnpqrstvwxyz"`, `:27` — `i l o u` excluded). `base32_encode` (`:44`) packs the 256 bits MSB-first; the 52nd symbol carries 1 hash bit plus 4 zero pad bits, so only two of the 32 symbols (`0` and `g`) can legally appear last. **There is no checksum** in the format. The base32 is hand-written rather than taken from a crate and was cross-checked against `data-encoding` over 40M random cases.
- **`AccountType::UniversalAccount`** — lives in the external `near-account-id` crate, bumped 2.0.0 → 3.0.0 in this release (`Cargo.toml:207`). It classifies an id as universal only when length, prefix, alphabet *and* the final-symbol padding rule all hold; anything else is a named account. Nearcore consumes it at e.g. `core/parameters/src/cost.rs:788` (transfer fee to a `0u` id).
- **`derive_universal_account_id`** — `core/primitives/src/utils.rs:503` — `encode_universal_account_id(sha3_256(state_init.0))`. It takes `RawStateInit`, not the typed value, precisely so re-serialization cannot change the id. The derivation itself is **blind**: it never checks the bytes. From `CanonicalUniversalStateInit` (PV 88) on, non-canonical bytes still derive *an* id, but no action carrying them can be accepted, so that id can never be created.

### Transaction

- **`Transaction`** — `core/primitives/src/transaction.rs:151` — enum `V0(TransactionV0) | V1(TransactionV1)` with a **hand-written** borsh impl (not a derived discriminant). `TransactionV0` (`:36`) = `{ signer_id, public_key, nonce: Nonce, receiver_id, block_hash, actions }`. `TransactionV1` (`:122`) replaces `nonce` with `TransactionNonce` (`:66`, either `Nonce` or a gas-key `{nonce, nonce_index}`) and adds `nonce_mode: NonceMode` (`:113`, `Monotonic`/`Strict`).
- **`Transaction::state_init_bootstrap`** — `:236` — recognizes a transaction shaped as a self-signed universal-account bootstrap: no gas-key nonce index, `signer_id == receiver_id`, and some top-level `Action::UniversalStateInit` whose `state_init` derives to that account id and whose `access_keys` contain the signing key's `PublicKeyHandle`. Matching on the *handle* is what makes it work for ML-DSA-65, where the trie stores only a hash. It decodes the payload with **`from_raw_lenient`** (`:255`, changed in this release): the transaction has already been validated by the time this runs, so from `CanonicalUniversalStateInit` on a non-canonical payload was already rejected, and below that version it is a valid bootstrap like any other. It deliberately does **not** look inside `Delegate` actions (a nested state init is validated against the delegate's receiver and runs in its own receipt) and it deliberately tolerates extra batched actions — safety comes from the runtime's uninitialized-account guard, not from restricting the action list. This is only the stateless half; existence/nonce are checked against state.
- **`SignedTransaction`** — `:456` — `{ transaction: Transaction, signature, #[borsh(skip)] hash, #[borsh(skip)] size }`; `hash`/`size` recomputed via `#[borsh(init=init)]` (`:455`, `:473`) from the borsh bytes of the inner `Transaction`. `get_size()` (`:487`) is the body-only length; `wire_size()` (`:497`) is the full borsh length including the signature — a ~3.3 KiB difference for ML-DSA-65. `size_for_limits` (`:507`) picks between them by protocol version. Serde ser/de is base64 of the borsh bytes.
- **`ValidatedTransaction`** — `:326` — newtype proving config checks *and* signature verification passed (`ValidatedTransaction::new`, `:330`; `check_valid_for_config`, `:351`).
- **`ExecutionOutcome`** — `:674` — `{ logs, receipt_ids, gas_burnt, #[borsh(skip)] compute_usage, tokens_burnt, executor_id, status: ExecutionStatus, metadata: ExecutionMetadata }`. `ExecutionStatus` (`:592`) is a discriminant enum `Unknown = 0 / Failure = 1 / SuccessValue = 2 / SuccessReceiptId = 3`; the comment on `status` notes it must stay last because light clients cannot parse `Failure`. `ExecutionMetadata` (`:714`) is `V1 = 0 / V2 = 1 / V3 = 2 / V4 = 3`; `ExecutionMetadataV4` (`:733`) is `{profile: ProfileDataV3, contracts: Vec<AccountContract>}`, one entry per action giving the contract attached to the receiver immediately before that action ran (`AccountContract::None` when the account did not yet exist). `ExecutionOutcomeWithId` (`:764`) pairs the outcome with its `id` (tx hash or receipt id).

### Error enums (shape only; semantics → [runtime-execution](runtime-execution.md))

Errors are wire types: `ExecutionStatus::Failure(TxExecutionError) = 1` (`transaction.rs:597`) is borsh-serialized into every stored `ExecutionOutcome` and returned over RPC, so the discriminants below are a compatibility contract. ## Behavior

### Serialization format selection

1. **Borsh** is used everywhere a byte layout must be *canonical* — hashing, consensus, storage, and the erasure-coded chunk payload. Borsh guarantees no two byte strings deserialize to the same value, which is why all hashed/committed types derive `BorshSerialize`/`BorshDeserialize` (see `docs/architecture/how/serialization.md`). Every such type also derives `ProtocolSchema` (`near_schema_checker_lib`) so a CI check catches accidental wire-format changes.
2. **Protobuf** is used only for the peer-to-peer transport envelope (`chain/network/src/network_protocol/network.proto`); the payloads it carries (blocks, chunks, txs) are borsh-encoded blobs inside proto fields. Network types are documented in [networking-p2p](networking-p2p.md).
3. **JSON** (serde) is the RPC/view representation. `CryptoHash` serializes as base58 (`hash.rs:137`); `SignedTransaction` serializes as base64 of its borsh bytes; `RawStateInit`, `DataReceipt.data` and global-contract `code` use base64 (`serde_as = Base64`). JSON is never hashed — with the single exception of `LightClientBlockLiteView::hash`, which re-serializes the view's inner-lite to borsh in order to recompute a header hash.

The distinction matters for hashing: only the borsh bytes are stable and canonical, so all commitments (block hash, chunk hash, tx hash, account id, receipt/outcome roots) are defined over borsh, never JSON. Where a view type must survive both worlds the two contracts are now split apart deliberately — see `StoredLightClientBlock` above.

### How IDs and hashes are derived

1. **Transaction hash** — `transaction.rs:144` `Transaction::get_hash_and_size` = `hash(borsh(transaction))`. `SignedTransaction.hash` caches this (`:473`). The signature is *not* part of the hash; the signature signs the hash bytes (`ValidatedTransaction::new`, `:340`).
2. **Block body hash** — `block_body.rs:220` `BlockBody::compute_hash` = `hash_borsh(self)` for V2/V3 (hashes the whole versioned enum including the discriminant); `BlockBodyV1` (`:24`) hashed the bare struct.
3. **Block header hash** — `block_header.rs:928` `compute_hash(prev_hash, inner_lite, inner_rest)` = `combine_hash(compute_inner_hash(inner_lite, inner_rest), prev_hash)`, where `compute_inner_hash` (`:922`) = `combine_hash(hash(inner_lite_bytes), hash(inner_rest_bytes))`. The two-part split lets light clients verify `inner_lite` without downloading `inner_rest`. `block_body_hash` lives inside `inner_rest` (from V4 on), so the body is committed transitively through the header hash. `compute_hash_and_sign` (`:1255`) is generic over the inner-lite type `L: BorshSerialize`, because `BlockHeaderV8` hashes `BlockHeaderInnerLiteV2` while V1–V7 hash `BlockHeaderInnerLite`. Note the hash input is the *bytes* of inner_lite/inner_rest with **no version tag of its own**: a V7 and a V8 header can never collide only because their inner-lite byte lengths differ, and a V6 and a V7 header over the same inner_lite differ only through `inner_rest` — which is why an un-gated V7 is a real hazard (see **Protocol-version-gated behavior**).
4. **Block hash** — the block's hash *is* its header hash (`block.rs:604`).
5. **Chunk hash** — `sharding.rs:296` `ShardChunkHeaderV3::compute_hash(inner)` = `ChunkHash(combine_hash(hash(borsh(inner)), inner.encoded_merkle_root()))`. `ShardChunkHeaderV2` does the same (`:191`); `ShardChunkHeaderV1` (`:743`) is just `hash(borsh(inner))` with no combine. `ShardChunkHeader::compute_hash` (`:683`) dispatches. Because the hash is over the *versioned* inner enum, the inner version is load-bearing for the chunk hash — hence the `proposed_split` absent/null distinction in `ChunkHeaderView`.
6. **Receipt / data / action ids** — `core/primitives/src/utils.rs:353` `create_hash_index(base, block_height, salt)` = `hash(base || block_height.to_le_bytes() || salt.to_le_bytes())`. Receipt id from a tx uses salt 0 (`:295`); from a parent receipt uses the receipt index (`:303`); action hashes count *down* from `u64::MAX` to avoid colliding with receipt-id salts (`:312`); a receipt id from an action hash uses the receipt index again (`:324`). Block *height* (not hash) is the fork-uniqueness salt because optimistic blocks lack a hash at id-generation time (`:346`).
7. **Account ids that are hashes** — `0s` deterministic accounts are `"0s" + hex(keccak256(borsh(DeterministicAccountStateInit))[12..32])` (`utils.rs:484`); `0u` universal accounts are `UAID(sha3_256(raw_state_init_bytes))` (`utils.rs:503`). Both make the id a commitment to the account's initial state, which is what lets a self-signed bootstrap transaction be authorized by the id alone.
8. **Merkle roots in the header** — computed from the chunk headers via the `Chunks` view (`block.rs:823`–`:844`): `compute_state_root`, `compute_chunk_prev_outgoing_receipts_root`, `compute_chunk_headers_root` (over `ChunkHashHeight` pairs), `compute_chunk_tx_root`, `compute_outcome_root`, each a `merklize` over the corresponding per-chunk field.
9. **Outcome hashing for proofs** — `transaction.rs:795` `ExecutionOutcomeWithId::to_hashes` produces `[id, hash_borsh(PartialExecutionOutcome), per-log hashes]`; `PartialExecutionOutcome` (`:622`) excludes logs/metadata and replaces the status with a payload-free `PartialExecutionStatus`, so light clients hash a stable subset and error-enum changes never move the outcome root.

### Versioned deserialization dispatch

Some types use bespoke borsh dispatch instead of a leading discriminant, relying on the fact that an `AccountId`'s borsh length prefix has a zero second byte:

1. **`Transaction`** (`transaction.rs:285`) — reads two bytes: `u2 == 0` ⇒ V0 (both bytes pushed back); `u1 == 1 && u2 != 0` ⇒ V1 (consume the `1` tag). Any other `u1` errors with "invalid transaction version tag" (`:317`).
2. **`Receipt`** (`receipt.rs:229`) — currently always V0; the same second-byte reservation is documented for a future V1.
3. **`ReceiptOrStateStoredReceipt`** (`receipt.rs:312`) — sniffs for the two `0xFF` sentinel bytes to distinguish a state-stored receipt from a plain receipt.
4. **`Account`** (`account.rs:738`) — reads the leading u128; sentinel ⇒ versioned `BorshVersionedAccount` (`V2 = 0`, `Uninitialized = 1`), otherwise legacy `AccountV1`.
5. **`PublicKey` / `PublicKeyHandle`** (`signature.rs:406`, `:680`) — read one byte, convert through `KeyTag` (`:359` `TryFrom<u8>`), and reject the *other* enum's reserved tag by name rather than falling through to a generic "unknown tag".
6. **`NonDelegateAction`** (`delegate.rs:434`) — reads the `Action` tag and rejects `8`/`14` before delegating to the derived variant deserializer.

For enum types that *do* use `#[borsh(use_discriminant = true)]` (Block, BlockBody, ShardChunkHeader, ShardChunkHeaderInner, PartialEncodedChunk, ReceiptEnum, Action, ExecutionStatus, ExecutionMetadata, UniversalStateInit, VersionedDelegateActionPayload, ContractCodeResponse, the error enums, StoredLightClientBlock, …), the leading byte is the explicit variant tag pinned in the source, so those tags are part of the wire contract.

**`BlockHeader` is the exception that matters.** It has *no* `use_discriminant` attribute (`block_header.rs:907`–`:910`), so its tags come from declaration order. Adding `BlockHeaderV8` at the end is therefore tag-safe — every older variant keeps its tag — but it also means a variant can never be reordered or removed, only appended. Equally, **the inner-lite/inner-rest structs are not self-describing**: which pair a given byte string is parsed as comes entirely from the outer `BlockHeader` tag. That is why changing `BlockHeaderV7::inner_lite` in place (as 2.14.0-rc.1 briefly did) is a hard wire break, and why #16621 restored V7 and appended V8 instead.

**Release schedule** (`core/primitives/src/version.rs:59`–`:84` — `get_protocol_upgrade_schedule`) — populated in this release, and it is a **two-step activation**:

| Chain | PV 87 | PV 88 |
|---|---|---|
| mainnet | 2026-11-04 00:00 UTC | 2026-11-06 00:00 UTC |
| testnet | 2026-09-23 00:00 UTC | 2026-10-21 00:00 UTC |

The two days between the mainnet steps are the window in which `RejectUniversalAccountTransfers` and `RejectBlockHeaderV7BeforeSpice` are armed but universal accounts are still off. That ordering is the point: transfers to `0u` ids are banned *before* `UniversalAccounts` turns on, so no receipt funded without the account-creation fee can execute once the fee applies.

## Invariants & failure modes

- **Borsh canonicality:** every hashed/committed type round-trips through borsh with a unique byte representation; schema drift is caught by the `protocol-schema-check` CI (`docs/architecture/how/serialization.md`). Adding/reordering enum variants without a new versioned type can silently corrupt stored/consensus data.
- **Canonicality of `RawStateInit` is version-dependent (changed in this release).**
  - **Below PV 88** (and, at any version, for a receipt that is *not* a `NewReceipt`): any well-formed borsh is accepted. A non-canonical encoding of the same logical value decodes fine and simply hashes to a different account id — it is a different account. `UniversalStateInit::from_raw_lenient` (`core/primitives/src/universal_state_init.rs:152`) rejects only malformed or trailing bytes.
  - **From PV 88** (`CanonicalUniversalStateInit`), a *new* receipt's `UniversalStateInit` is accepted only in its canonical encoding: `from_raw_strict` (`:135`) re-encodes the decoded value and requires `decoded.to_raw() == *raw`, so unsorted map keys, unsorted set elements and duplicates are all rejected with `StateInitError::NonCanonical` → `ActionsValidationError::MalformedUniversalStateInit` (`runtime/runtime/src/action_validation.rs:600`). Each logical state init then has exactly one valid encoding and therefore exactly one account id.
  - The **id derivation itself never changes**: it commits to the exact bytes hashed, never to a re-serialization, which is why `derive_universal_account_id` takes `RawStateInit` (`utils.rs:503`). Non-canonical bytes still derive *an* id from 88 on; that id just can never be created.
  - **Strict mode is `NewReceipt`-only, deliberately.** A receipt built before the feature took effect was valid then and must keep passing validation, because failing validation of an in-flight receipt would halt the chunk while failing the action only fails the action (`action_validation.rs:591`–`:596`).
  - Only the *outer* structure is checked — contracts serialize their own nested state inside the opaque storage values, out of the protocol's view (`universal_state_init.rs:17`–`:18`).
  - A corollary still stated in-source: **a new `UniversalStateInit` variant must arrive behind a protocol feature**, because gas depends on what decodes and two nodes on one protocol version disagreeing about what decodes would charge different gas (`universal_state_init.rs:166`).
- **Pricing must be version-stable.** `state_init_counts` (`universal_state_init.rs:168`) takes no `DecodeMode` and always decodes leniently, because receipts created under earlier protocol versions are re-priced from it. Only `state_init_send_counts` (`:184`) — what a contract prepays for bytes that have not been validated yet — follows the mode. Confusing the two would change the cost of an old receipt.
- **Key tags are disjoint:** borsh tag 2 (full ML-DSA-65 key) can never decode as a `PublicKeyHandle` and tag 3 (the 32-byte hash) can never decode as a `PublicKey` (`signature.rs:352`). Both deserializers match `KeyTag` exhaustively, so a future scheme cannot silently reuse a reserved tag.
- **Base58 parsing is bounded:** a 100k-character key string is rejected in microseconds because decoding targets a fixed-size buffer and `BufferTooSmall` is reported as `received = expected + 1` (`signature.rs:1286`).
- **`#[borsh(skip)]` cached fields must be recomputed:** `BlockHeaderVN.hash`, `SignedTransaction.{hash,size}`, and `ShardChunkHeaderV*.hash` are skipped on the wire and rebuilt by the `#[borsh(init=…)]` hook on deserialize (`block_header.rs:606`, `transaction.rs:455`, `sharding.rs:140`/`:154`/`:237`). `ExecutionOutcome.compute_usage` is skipped and is `None` after a DB read (`transaction.rs:686`).
- **Version-tag validity:** `Transaction::deserialize_reader` errors "invalid transaction version tag" on an unknown first byte (`transaction.rs:317`); `StateStoredReceipt::deserialize_reader` errors on a wrong sentinel or unknown version byte (`receipt.rs:264`); `PartialState::check_entry_limit` errors "unknown PartialState variant" / "state part entry limit exceeded" (`state.rs:56`, `:63`).
- **A released header variant's layout is frozen.** `BlockHeader` has no explicit discriminants, and `inner_lite`/`inner_rest` carry no version tag of their own, so changing the field list of an already-shipped `BlockHeaderVN` silently reinterprets bytes that older nodes already produce. 2.14.0-rc.1 changed `BlockHeaderV7::inner_lite` from `BlockHeaderInnerLite` to `BlockHeaderInnerLiteV2`; 2.14.0 (#16621) reverted that and appended `BlockHeaderV8` instead (`block_header.rs:777`, `:807`). The spec previously documented V7 as the spice shape — that is now V8.
- **`BlockHeaderV7` is never produced, but accepted below PV 87.** Because V7 is structurally a V6 header plus two spice fields in `inner_rest`, anyone can take an honest V6 block, re-wrap its header as V7 and re-sign it; before PV 87 `validate_header` treats it as a V6 header (`chain/chain/src/chain.rs:928`–`:938`, asserted by `test-loop-tests/src/tests/block_header_v7_before_spice.rs`). From PV 87 it is rejected with `Error::InvalidProtocolVersion` (`chain.rs:941`–`:950`).
- **Chunk-header version must match the protocol version:** `ShardChunkHeader::validate_version` (`sharding.rs:616`) accepts only inner V4 unconditionally, V5 under `DynamicResharding`, V6 under `Spice`, and rejects V1/V2 headers and inner V1–V3 outright with `BadHeaderForProtocolVersionError`.
- **`PartialEncodedChunkV3`'s new fields are untrusted:** `prev_prev_block_hash` and `epoch_id` are attacker-controlled and a forged value resolves a real producer; they are only safe after the cross-check in `resolve_and_verify_anchored_producer` (`sharding.rs:951`, `:954`). → [sharding-chunks](sharding-chunks.md).
- **Delegate nesting is structurally impossible:** `NonDelegateAction`'s private constructor plus its hand-written deserializer (`delegate.rs:434`) mean a `Transaction`/`Receipt` containing a nested delegate cannot be serialized-then-deserialized, which several call sites rely on.
- **Block self-consistency:** `Block::check_validity` (`block.rs:618`) recomputes `prev_state_root` (skipped for spice blocks), receipts/headers/tx/outcome roots, and the `chunk_mask` from the embedded chunk headers and returns `BlockValidityError::{InvalidStateRoot, InvalidReceiptRoot, InvalidChunkHeaderRoot, InvalidTransactionRoot, InvalidChunkMask}` (`:41`) on mismatch.
- **New blocks are BlockV4:** `Block::new_block` panics ("attempted to include BlockBodyV1 in new protocol version") if constructed with a `BlockBodyV1` (`block.rs:105`).
- **Header build requires the endorsement bitmap:** `new_impl` panics if `chunk_endorsements` is `None` for V5+ headers (`block_header.rs:1129`), and under Spice also if `prev_last_certified_block_epoch_id`, `spice_chunk_endorsement_stats` or `chunk_execution_root` are absent (`:1135`–`:1143`). Spice blocks carry an *empty* endorsement bitmap per shard, since endorsements are not included in spice blocks (`block.rs:248`).
- **`merklize` of an empty slice** yields `CryptoHash::default()` (`merkle.rs:48`), so a block with no chunks has zero-valued roots.
- **UAID encoding is total and checked:** `encode_universal_account_id` `expect`s that its output parses as an `AccountId` (`universal_account_id.rs:39`); the emitted charset and 54-byte length always satisfy that. There is **no checksum**, so a UAID with a typo that still satisfies length/alphabet/padding is a valid id for a different (almost certainly non-existent) account.

## Open questions

- `ShardChunkHeaderInnerV6SpiceTxOnly` is spice-only (PV 180, nightly) and its field set is not exercised at PV 88; the description here is from the struct definition, not from observed production behavior. The same applies to `BlockHeaderV8` and `BlockHeaderInnerRestV8`: they are defined and produced only under `ProtocolFeature::Spice`.
- `PartialEncodedChunkV3` is a *message* version with no protocol-feature gate of its own — it is selected purely by whether the producer supplies an anchor (`sharding.rs:1463`, `:1477`). The comment at `sharding.rs:1475`–`:1476` says it is "produced under EarlyKickout for non-spice chunks", but the version selection itself is not feature-checked in this file, so the exact conditions under which a V2 rather than V3 message appears on the wire at PV 88 must be read from the chunk-production call site → [sharding-chunks](sharding-chunks.md).
- `AccountType` (which decides whether an id is `0u` universal) lives in the external `near-account-id` 3.0.0 crate, not in this tree, so its classification rules could only be confirmed here from nearcore-side tests and call sites rather than from the implementation.
- **`BlockHeaderV7` and mixed-version decoding.** A 2.14.0 node and a 2.14.0-rc.1 node disagree about what `BlockHeaderV7` bytes mean (rc.1 parses `inner_lite` as `BlockHeaderInnerLiteV2`, 2.14.0 as `BlockHeaderInnerLite`). Because no honest node produces V7 in either build, this should never surface on a real network; it is nonetheless a genuine format divergence between two builds that both claim PV 87, and nothing in the code detects it. Whether any rc.1 build reached a public network could not be determined from the tree.
- The `MAX_UNCOMPRESSED_CONTRACT_CODE_PER_REQUEST_SIZE` cap and the response grouping (#16421) are enforced by node-local policy on both sides, with no feature gate and no version negotiation, so a node that has not upgraded will simply see a different number of responses per request. Whether the requester side tolerates the new multi-response pattern on an un-upgraded peer is a [stateless-validation](stateless-validation.md) / [networking-p2p](networking-p2p.md) question, not answerable from these type definitions.
