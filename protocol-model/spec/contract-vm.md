## Role

This component executes WASM smart-contract code for the `FunctionCall` action. It is invoked by the runtime ([runtime-execution](runtime-execution.md)) once per executed function call: the runtime builds a `GasCounter` and calls `prepare` (`runtime/runtime/src/pipelining.rs:441` — `prepare_function_call`), then `run` with a `VMContext`, the `RuntimeFeesConfig` and an `External` trait object that proxies trie reads/writes and receipt creation (`runtime/runtime/src/function_call.rs:233` — `execute_function_call`, calling `near_vm_runner::run` at `:281`). The VM validates and instruments the WASM (`prepare_contract`), compiles it with wasmtime, links it against the host-function (bindings) ABI, meters every WASM op and host call against a gas counter, and runs the requested entry point. Host calls let the contract read/write contract storage (delegated to [state-storage](state-storage.md)), read context/economics, compute hashes/signatures, and **create promises** that the runtime turns into receipts handled by [cross-shard-congestion](cross-shard-congestion.md). The result is a `VMOutcome` (burnt/used gas, compute usage, logs, return data, and an optional `aborted` guest error). Execution must be a deterministic pure function of its inputs: gas and outcome must be byte-identical on every validator (`runtime/near-vm-runner/src/runner.rs:25` — `VMResult` doc comment). Out of scope: how the runtime drives the `FunctionCall` action loop and distributes unused gas → [runtime-execution](runtime-execution.md); the trie itself → [state-storage](state-storage.md).

**Wasmtime is the only backend.** The NearVM engine crate tree (`runtime/near-vm*`) and the legacy `VMLogic` struct were deleted in 2.14.0-rc.1 (#15988, #15989, #16322). In 2.14.0 final, **#16428 decoupled the host-function layer from wasmtime**: the host functions moved out of `wasmtime_runner/logic.rs` into `runtime/near-vm-runner/src/logic/host.rs`, where they are free functions over a runtime-independent `HostCtx` plus the guest's linear memory (`&mut [u8]`). The wasmtime `Store` data type `Ctx` now keeps only the wasmtime-specific pieces and embeds a `HostCtx<'static>` (`runtime/near-vm-runner/src/wasmtime_runner/mod.rs:283`). This is a pure refactor — no host function's observable behavior, cost or gating changed with it. The commit (`fe7309470`) touches six files and none of them is `imports.rs`, `prepare.rs`, `prepare/`, `features.rs` or `cache.rs`, so the import list, the instrumentation and every engine setting are untouched; normalizing the `Ctx`→`HostCtx` rename away, the only differences between the old `wasmtime_runner/logic.rs` and the new `logic/host.rs` are the moved `HostCtx` struct and its `impl`, the `use` lines, rustfmt re-wrapping four signatures, and the dropped `#[cfg(feature = "test_features")]` on `burn_gas` — no function body changed, and the multiset of `pay_base`/`pay_per`/`pay_action_*` charges and `HostError`/`PrepareError` constructors is identical in both files. See §1 and §6.

## Behavior

### 1. VM backend selection — Wasmtime only

`VMKind` comes from `Config::vm_kind`, populated from the versioned parameter table (`core/parameters/src/parameter_table.rs:450` — `vm_kind: params.get(Parameter::VmKind)?`). The base value is `Wasmer2` (`core/parameters/res/runtime_configs/parameters.yaml:327`) and the last override is at protocol version 84: `vm_kind: { old: "NearVm", new: "Wasmtime" }` (`core/parameters/res/runtime_configs/84.yaml:2`). Since `MIN_SUPPORTED_PROTOCOL_VERSION` is 84 (`core/primitives-core/src/version.rs:670`), **every supported protocol version resolves to `Wasmtime`**.

`VMKindExt::runtime` (`runtime/near-vm-runner/src/runner.rs:214`) has exactly one arm, `Self::Wasmtime => WasmtimeVM::new(config)` under `#[cfg(feature = "wasmtime_vm")]`; every other kind falls through to `None`. `VMKindExt::is_available` (`:205`) returns `false` for `Wasmer0`, `Wasmer2` and `NearVm` unconditionally. The public wrappers `prepare` (`:54`), `run` (`:89`), `contract_cached` (`:27`), `precompile_contract`/`try_precompile_contract` (`runtime/near-vm-runner/src/cache.rs:1072`/`:1096`) resolve the runtime with `unwrap_or_else(|| panic!("the {vm_kind:?} runtime has not been enabled at compile time or has been removed"))` — i.e. a config naming any other kind is a hard node-level panic, not a protocol outcome.

`VMKind::replace_with_wasmtime_if_unsupported` (`core/parameters/src/vm.rs:43`) still forces `Wasmtime` on non-x86_64 when parsing the parameter (`core/parameters/src/parameter_table.rs:239`); at every supported version this is a no-op because the parsed value is already `Wasmtime`.

**Host functions are no longer wasmtime-specific** (#16428). `runtime/near-vm-runner/src/logic/host.rs` holds the implementations as plain functions `fn name(ctx: &mut HostCtx, memory: &mut [u8], ..) -> Result<..>`, so any embedder that can hand over a `HostCtx` and the guest's linear memory calls the real implementations (`host.rs:38`–`:43` doc). The crate's `logic` module declares `pub mod host;` (`runtime/near-vm-runner/src/logic/mod.rs:7`) and no longer carries the module-level `#![cfg_attr(not(feature = "wasmtime_vm"), allow(dead_code))]` it needed when the `wasmtime_vm` feature was off, because the host-function code is no longer there only to serve `wasmtime_runner`. The wasmtime backend keeps only the glue: `link` (`wasmtime_runner/mod.rs:1098`) forwards each import to `logic::$func(&mut ctx.host, memory, ..)` (`:1114`). `wasmtime_runner/mod.rs` is 59 lines shorter for 17 added (`git diff --numstat`), essentially all of it the `Ctx` fields that moved into `HostCtx`.

**Engine configuration and determinism.** One `WasmtimeVM`/`Engine` is cached per `(Config, target)` in a process-wide map (`runtime/near-vm-runner/src/wasmtime_runner/mod.rs:79` — `VMS`; `:404` — `new_for_target`). The engine is configured (`:438`–`:505`) with: pooling allocation bounded by `MAX_CONCURRENCY = 1_000` (`:45`) core instances/memories, `max_core_instance_size(MAX_CORE_INSTANCE_SIZE)` = 1 MiB of per-instance runtime metadata (`:71`, `:451`), `table_elements`/`max_tables_per_module` from `LimitConfig`, backtraces and address maps disabled, `memory_init_cow`, `max_wasm_stack(1 GiB)` (stack metering is done by instrumentation instead), NaN canonicalization on, signals-based traps, and a fixed memory reservation so bounds checks can be elided. The compilation **strategy is `Winch` on x86_64 and `Cranelift` elsewhere** (`:477`), because Winch on aarch64 lacks wide-arithmetic in wasmtime 45. Two different compilers can differ in observable trap/behavior corners, which is why `neard` refuses to start a mainnet/testnet validator on a non-x86_64 host (`neard/src/cli.rs:392` — `check_validator_arch`, panics with "running a … validator on the … architecture is not supported; validators must run on x86_64").

### 2. Contract preparation (`prepare_contract`)

`prepare::prepare_contract` (`runtime/near-vm-runner/src/prepare.rs:21`) builds a `WasmFeatures` from the config and delegates to `prepare_v3::prepare_contract` (`runtime/near-vm-runner/src/prepare/prepare_v3.rs:402`). `prepare_v2` was deleted in rc.1 (#16355); `prepare_v3` is the only path, and the old wasmparser version was dropped (#16052) — validation runs on `finite_wasm_6::wasmparser` only. Neither changed in 2.14.0 final.

Enabled wasm features are a fixed allow-list (`runtime/near-vm-runner/src/features.rs:41`): floats, mutable globals, sign extension and saturating float-to-int are always on; reference types and bulk memory follow `config.reftypes_bulk_memory` (on since PV 84); multi-value, SIMD, threads, tail calls, multi-memory, memory64, exceptions, GC, component model, function references, wide arithmetic and custom page sizes are all off (`runtime/near-vm-runner/src/features.rs:7`–`:24`). Note the engine itself is built with `wasm_wide_arithmetic(true)` (`wasmtime_runner/mod.rs:505`); that is harmless because validation already rejected such modules.

Preparation is a single streaming pass (`PrepareContext::run`, `prepare_v3.rs:62`) that validates, rewrites and limits the module, followed by instrumentation:

1. **Limits decremented per section** — each limit is a counter subtracted with `checked_sub`, so overflow is the error: types → `TooManyTypes` (`:86`), tables → `TooManyTables` (`:116`) and per-table `initial > max_elements_per_contract_table` → `TooManyTableElements` (`:122`), globals → `TooManyGlobals` (`:149`), functions → `TooManyFunctions` (`:235`), locals → `TooManyLocals` (`:259`).
2. **The globals cap does not bite on the stable path at 88.** `max_globals_per_contract` is an `Option<u64>` (`core/parameters/src/vm.rs:190`) with no base value in `parameters.yaml`, and the only diff that sets it is `core/parameters/res/runtime_configs/157.yaml:1` — `max_globals_per_contract: { new: 100_000 }`, i.e. **nightly only**. That value is unchanged from 2.14.0-rc.1; the 2.14.0 `87.json`/`88.json` config snapshots carry no `max_globals_per_contract` at all, while the 157 snapshot carries `100000` (`core/parameters/src/snapshots/near_parameters__config_store__tests__157.json.snap:273`). So at the stable path (87 and 88) the enforcement code of step 1 ships and runs but the limit resolves to unbounded, and no contract is rejected for defining too many globals; at nightly 157 the real cap is 100 000.
3. **Locals limit is code-size dependent** (#16348). `max_locals` (`:464`) takes the **minimum** of the absolute `max_locals_per_contract` and `code.len() / min_contract_size_per_local`. `min_contract_size_per_local` is set to `2` at PV 87 (`core/parameters/res/runtime_configs/87.yaml:11`), so a contract gets at most one local per two bytes of source, *in addition to* the absolute cap of 1,000,000 locals set at PV 53 (`core/parameters/res/runtime_configs/53.yaml:14`). Asserted by `locals_limit_depends_on_contract_size` (`runtime/near-vm-runner/src/prepare.rs:55`).
4. **Memory is normalized.** Any internal memory section is dropped and replaced with a single memory of exactly `initial_memory_pages`..`max_memory_pages` (`:352` — `ensure_memory_section`, `:376` — `memory_type`, emitted at `:136` and `:357`). An *imported* memory is rejected outright (`:327` — `TypeRef::Memory(_) => PrepareError::Memory`), as are imported tables, globals and tags (`:325`–`:328`). Imports from any module other than `env` are `PrepareError::Instantiate` (`:316`), and each function import consumes one unit of the function budget (`:322`).
5. **Exports are prefixed.** Every export name is rewritten with `EXPORT_PREFIX` = `"\0"` (`runtime/near-vm-runner/src/lib.rs:48`, applied at `prepare_v3.rs:163`), so guest exports can never collide with the host-injected `memory`/`remaining_gas`/`start` names.
6. **Per-function body size** above `max_function_body_size` → `FunctionBodyTooLarge` (`:250`), then full `wasmparser` function validation (`:274`).
7. **Custom sections** are dropped when `discard_custom_sections` is set (`:278`). Any unknown/unsupported section (component model, tags, module linking, …) → `Deserialization` (`:300`).
8. **finite-wasm analysis + instrumentation** (`:410`–`:449`): `finite_wasm_6::Analysis` computes gas and max-stack annotations using `regular_op_cost`/`linear_op_base_cost`/`linear_op_unit_cost`, then `InstrumentContext::run` injects the metering calls into the `internal` module (so contracts cannot call them through `env`) and enforces `max_blocks_per_function` → `TooManyBlocksPerFunction`, `max_blocks_per_contract` → `TooManyBlocksPerContract`, `max_params_per_function`/`_per_contract` → `TooManyParams*`, `max_operand_stack_bytes_per_function` → `OperandStackTooLarge`.
9. **Instrumented size cap** (`:455`): if the instrumented output exceeds `max_instrumented_code_size` (16 MiB since PV 84) → `InstrumentedCodeTooLarge`, guarding Cranelift's 24-bit SSA counter.

All failures are `PrepareError` variants (`runtime/near-vm-runner/src/logic/errors.rs:163`), wrapped by the caller into `CompilationError::PrepareError`. Preparation is **not** separately gas-costed: it runs inside `compile_uncached` (`runtime/near-vm-runner/src/wasmtime_runner/mod.rs:527`), i.e. once per cache miss rather than once per call, and the only load-related fee is the contract-loading fee of §3.

### 3. Compile, load, and the contract-loading fee

`WasmtimeVM::compile_uncached` (`runtime/near-vm-runner/src/wasmtime_runner/mod.rs:527`) runs `prepare_contract` then `engine.precompile_module`; a wasmtime failure becomes `CompilationError::WasmtimeCompileError`. `compile_and_cache` (`:566`) uses double-checked locking against a per-code-hash `CompilationLockMap` (`:89`) so concurrent apply/witness-validation threads never compile the same contract twice; `try_compile_and_cache` (`:592`) returns `Ok(None)` instead of blocking, for opportunistic background warming. Both funnel into `compile_and_persist` (`:614`), which stores either `CompiledContract::Code` or `CompiledContract::CompileModuleError` in the cache.

`with_compiled_and_loaded` (`:643`) resolves the artifact and charges the loading fee. Ordering is load-bearing:

1. Compute the `ContractCacheKey`, `touch` it, and look it up in the in-memory `AnyCache`; on a miss consult the on-disk cache; on a miss there, `contract.get_code()` (absent ⇒ `VMRunnerError::ContractCodeNotPresent`, `:680`) and `compile_and_cache`.
2. `unsafe { Module::deserialize(&self.engine, &module) }` (`:704`). **On failure the behavior is protocol-gated** (`:710`): if `config.fix_contract_loading_error` is set, the failure is cached and returned as `FunctionCallError::LoadingError { msg }`, so it flows through the fee-charge points below and finalizes as a *gas-bearing* `abort`; otherwise it returns `Err(VMRunnerError::LoadingError(..))`, which the runtime converts into a zero-gas `VMOutcome::nop_outcome` (`runtime/runtime/src/function_call.rs:331`). See §Protocol-version-gated behavior.
3. Resolve the `memory` export (missing ⇒ `FunctionCallError::LinkError { msg: "memory export missing" }`, `:721`), record the optional `remaining_gas` and `start` export indices, build a `Linker`, `link` the host functions (`:1098`), and `instantiate_pre` (`:731`). Every one of these failures is cached as a `FunctionCallError`, not as a hard error.
4. `gas_counter.before_loading_executable(config, method, wasm_bytes)` (`runtime/near-vm-runner/src/logic/gas_counter.rs:235`): reject an empty `method_name` with `MethodResolveError::MethodEmptyName`; then, **only if `fix_contract_loading_cost`**, pre-charge `add_contract_loading_fee` (= `contract_loading_bytes * code_len` then `contract_loading_base`, `:224`), mapping out-of-gas to `HostError::GasExceeded`. Failure here becomes `PreparationResult::OutcomeAbort`.
5. If the artifact resolved, `gas_counter.after_loading_executable(config, wasm_bytes)` (`:259`) charges the same fee **only if `fix_contract_loading_cost` is not set** — the legacy post-load ordering, which is what runs on stable at PV 88 (`fix_contract_loading_cost` is nightly-only, PV 129).
6. Then `prepare` (`:848`) resolves the method export by its prefixed name `"\0{method}"`: a missing export → `MethodResolveError::MethodNotFound` (`:864`) and a non-`() -> ()` signature → `MethodResolveError::MethodInvalidSignature` (`:871`), both recorded as `PreparationResult::OutcomeAbortButNopInOldProtocol`.

### 4. Run (`PreparedContract::run`)

`run` (`runtime/near-vm-runner/src/wasmtime_runner/mod.rs:953`) turns the `PreparedContract` into a `VMOutcome`:

1. Build `ExecutionResultState::new` (`runtime/near-vm-runner/src/logic/logic.rs:45`) — panics if `account_balance + attached_deposit` overflows `u128` (`:49`).
2. If preparation produced `OutcomeAbortButNopInOldProtocol`/`OutcomeAbort`, return immediately via `abort_but_nop_outcome_in_old_protocol`/`abort` (`:965`/`:968`).
3. Transmute `ext`/`context` to `'static` (safe only because they outlive the call), build the `Ctx` — which builds the `HostCtx` inside it (`:978`) — and create the `Store`; install the store limiter.
4. Acquire a concurrency permit from the `ConcurrencySemaphore` (`:982`); failure ⇒ `LinkError { msg: "failed to acquire execution slot" }` as a graceful abort.
5. `pre.instantiate(&mut store)`; failure ⇒ `abort` with the mapped error (`:991`). Then eagerly resolve the real post-instantiation `memory` export (`:1005`), avoiding a wasmtime panic path for host-trampoline callers.
6. If the module exports `remaining_gas`, install a `store.call_hook` (`:1017`): on `CallingHost`/`ReturningFromWasm` it burns `host.result_state.gas_counter.remaining_gas() - global` into the counter; on `ReturningFromHost`/`CallingWasm` it re-publishes `remaining_gas()` into the global. This is how inline-metered wasm gas reaches the `GasCounter`.
7. Run the optional `start` export, then the resolved method via `call` (`:933`). A method missing at call time yields `RunOutcome::AbortNop`.
8. Map the result (`:1057`): `Ok ⇒ VMOutcome::ok`, `AbortNop ⇒ abort_but_nop_outcome_in_old_protocol`, `Abort ⇒ abort`. Every exit path first does `store.into_data().host.into_result_state()`, because building the outcome consumes the `ExecutionResultState` that lives inside the `HostCtx`.

Wasmtime errors are classified by `IntoVMError for wasmtime::Error` (`:330`): a host error carried in an `ErrorContainer` is unwrapped back into `HostError`/`ExternalError`/`InconsistentStateError`; a `wasmtime::Trap` is mapped through `TrapClassification` to a `WasmTrap` variant, except that `Interrupt`/`HeapMisaligned` become `VMRunnerError::Nondeterministic` (`:371`), any other trap becomes `VMRunnerError::WasmUnknownError` (`:365`), and a trap that should be impossible under NEAR's engine configuration `panic!`s outright (`:359`).

### 5. Gas metering

Two categories, both through `GasCounter`:

- **WASM instruction cost.** finite-wasm instrumentation calls into the `internal` module: `finite_wasm_gas` (`runtime/near-vm-runner/src/logic/host.rs:271`) burns a precomputed gas amount; `linear_gas` (`:275`) backs the bulk memory/table variants (`finite_wasm_memory_copy`/`_fill`/`_init`, `finite_wasm_table_copy`/`_fill`/`_init`, `:282`–`:338`) as `constant + count * linear`. `finite_wasm_stack` (`:342`) decrements `ctx.remaining_stack` by `operand_size + frame_size` (underflow ⇒ `MemoryAccessViolation`) and charges `ceil(frame_size/8) * regular_op_cost`; `finite_wasm_unstack` (`:358`) restores it. `finite_wasm_gas_exhausted` (`:371`) burns all remaining gas and returns `IntegerOverflow`; `finite_wasm_stack_exhausted` (`:379`) returns `MemoryAccessViolation`. The legacy `gas` import is still exposed and maps to `gas_seen_from_wasm` → `gas_opcodes` (`:2316`, `:2294`), charging `opcodes * regular_op_cost`.
- **Host-function `ExtCosts`.** Every host fn starts with `pay_base(base)` and then pays its own `pay_base`/`pay_per` costs (`runtime/near-vm-runner/src/logic/gas_counter.rs:305`, `:290`); both update the profile with the gas actually burnt, even when the charge fails. Reading an argument charges `read_memory_base/_byte` or `read_register_base/_byte` depending on whether `len == u64::MAX` (`logic/host.rs:223` — `get_memory_or_register`); writing a result charges `write_memory_*`/`write_register_*`. Action-shaped costs go through `pay_action_accumulated` (`gas_counter.rs:322`), which also accumulates `send_action_compute_usage` (falling back to the burnt gas when the charge hit a limit, for backwards compatibility).

**Burnt vs. used.** `burn_gas` (`gas_counter.rs:155`) adds to `fast_counter.burnt_gas` and fails if it would exceed `fast_counter.gas_limit`. `deduct_gas(burnt, used)` (`:126`) moves `used - burnt` into `promises_gas` (gas reserved for prepaid promise execution) and shrinks `gas_limit` to `min(max_gas_burnt, prepaid_gas - promises_gas)` (`:139`). `used_gas = promises_gas + burnt_gas` (`:384`); `remaining_gas = prepaid_gas - used_gas` (`:389`). On a limit crossing, `process_gas_limit` (`:176`) clamps burnt to `min(prepaid_gas, max_gas_burnt)`, saturates `promises_gas`, and returns `GasLimitExceeded` if `max_gas_burnt` was crossed, else `GasExceeded` — preferring `GasLimitExceeded` for compatibility.

**View calls are bounded by `max_gas_burnt_view`** (#16130, rc.1). `GasCounter::new` (`:85`) sets `prepaid_gas = max_gas_burnt` when `is_view` (`:101`), instead of widening it to `Gas::MAX`. The comment at `:93` explains why: `remaining_gas()` seeds the in-wasm gas global on the wasmtime backend, so a `Gas::MAX` seed let a pure-wasm loop with no host imports run until it drained ~`u64::MAX` of guest gas before the cap was ever checked. Promises are prohibited in view mode, so `used_gas` never exceeds `burnt_gas` and no view-call result changes. The runtime supplies `max_gas_burnt` from `ViewConfig` when present, else `limit_config.max_gas_burnt` (`runtime/runtime/src/pipelining.rs:426` — `PipelineManager::gas_counter`).

`compute_outcome` (`runtime/near-vm-runner/src/logic/logic.rs:116`) folds the wasm-instruction cost into the profile and computes `compute_usage` via `total_compute_usage` (NEP-455 compute costs), decoupled from gas.

### 7. Compiled-contract caching

The cache key `ContractCacheKey::Version5` (`runtime/near-vm-runner/src/cache.rs:44`) hashes `code_hash`, `Config::non_crypto_hash()`, `vm_kind`, and the backend `vm_hash` (`get_contract_cache_key`, `:53`), so any config or engine change invalidates every entry. `WasmtimeVM::vm_hash` (`runtime/near-vm-runner/src/wasmtime_runner/mod.rs:515`) mixes `engine.precompile_compatibility_hash()` with a manually bumped `version` (currently **73**, unchanged from rc.1). `config_cache_key_signature` (`cache.rs:76`) exposes the same hash minus the code hash, so two configs can be compared for cache compatibility without enumerating the inputs.

**Does 2.14.0 invalidate cached artifacts?** The `vm_hash` side does not: `version` is still 73 and the wasmtime dependency is unchanged between rc.1 and 2.14.0, so `engine.precompile_compatibility_hash()` is the same. In particular the #16428 host-function refactor touches **no** cache-key input — it moves Rust code between modules and does not change the import list, the instrumentation, or the engine. The `Config` side does change: `Config` derives `Hash` (`core/parameters/src/vm.rs:210`) and `non_crypto_hash` hashes the whole struct (`:320`), and a new field `canonical_universal_state_init` was added (`:259`), so the struct's hash differs from the rc.1 binary's **at every protocol version, including those where the flag is `false`**: `#[derive(Hash)]` hashes each field in declaration order and `bool::hash` writes one byte, so an extra `false` field changes the `DefaultHasher` stream and therefore the digest (verified by hashing a two-field and a three-field `#[derive(Hash)]` struct, all fields `false` — the two digests differ). A node upgrading to 2.14.0 therefore misses on every cached artifact and compiles each contract afresh — one full recompile pass per node on upgrade. That is node-local work only — the artifact cache is not consensus state — and it is the routine consequence of adding a config parameter, not of the refactor.

Two levels: a per-cache in-memory `AnyCache` of loaded `PreparedModule`s (`cache.rs:947` — `AnyCache`, an LRU bounded both by item count and by an estimated weight; sized in `FilesystemContractRuntimeCache::with_memory_cache` at `:414` assuming ~16 MiB per contract), and an on-disk `FilesystemContractRuntimeCache` (`:300`) storing serialized executables or a `CompileModuleError`, with a byte-bounded LRU over the directory built by `build_disk_index` (`:542`) and refreshed via throttled atime updates (`:486`). The stored `CompiledContractInfo.wasm_bytes` carries the source size so the loading fee can be charged without re-reading the source.

`precompile_contract` (`:1072`) warms the cache; `try_precompile_contract` (`:1096`) is its non-blocking variant for background warming. **The `on_protocol_version_update` sweep was removed in rc.1** (#15988) — `FilesystemContractRuntimeCache` no longer overrides it, so the trait's no-op default applies (`:146`). Stale artifacts are now simply never hit (the on-disk LRU eventually evicts them), because the config change moves the cache key.

## Invariants & failure modes

- **Determinism.** Gas values and the outcome (including a guest error) must be identical across validators; a `VMRunnerError` signals node-local corruption and must crash rather than diverge (`runtime/near-vm-runner/src/runner.rs:10`–`:25` doc, `runtime/near-vm-runner/src/logic/errors.rs:12`).
- **Graceful guest errors vs. runner errors.** `FunctionCallError` (`errors.rs:45`) — `CompilationError`, `LinkError`, `MethodResolveError`, `WasmTrap`, `HostError`, `LoadingError` — becomes `VMOutcome.aborted` and is committed on-chain. It has **no `WasmUnknownError` variant** (removed by #16186). `VMRunnerError` (`errors.rs:12`) — `InconsistentStateError`, `CacheError`, `LoadingError`, `ExternalError`, `Nondeterministic`, `WasmUnknownError`, `ContractCodeNotPresent` — propagates as `Err` from `run`, and the runtime maps it to a storage error, a nop outcome, or a panic.
- **Host-function behavior does not depend on the embedder.** Every host function is a function of `(HostCtx, memory, args)` only (`logic/host.rs:38`–`:43`); the wasmtime backend contributes no state that a host function reads. This is what makes the #16428 split safe, and it is the invariant a second embedder must preserve.
- **Gas limits.** Never burn more than `min(prepaid_gas, max_gas_burnt)`; enforced in `burn_gas`/`process_gas_limit` (`gas_counter.rs:159`/`:179`). Out-of-gas ⇒ `GasLimitExceeded` / `GasExceeded`. In view mode `prepaid_gas` is `max_gas_burnt`, so a view call cannot exceed `max_gas_burnt_view` even in pure wasm (`gas_counter.rs:101`).
- **View-mode restrictions.** State-mutating and private host fns return `HostError::ProhibitedInView` (e.g. `storage_write` `logic/host.rs:5004`, every promise fn).
- **Pay before you decode.** For `universal_state_init_to_account_id` the per-byte fee is charged before the canonical check runs (`logic/host.rs:3316`–`:3322`, and its comment at `:3320`), and for `promise_batch_action_universal_state_init` the size terms precede the decode and the content terms precede the action's existence (`:3404`–`:3413`). A payload that fails the check has already paid for the work it caused.
- **Limit enforcement.** `NumberPromisesExceeded` (`logic/host.rs:614`), `KeyLengthExceeded`/`ValueLengthExceeded` (`:5015`/`:5029`), `NumberOfLogsExceeded` (`logic/logic.rs:83`), `TotalLogLengthExceeded` (`logic/logic.rs:104`), `RecordedStorageExceeded` (`recorded_storage_counter.rs:27`), plus the whole `PrepareError` family at preparation time (`errors.rs:163`).
- **Balance.** `deduct_balance` errors with `BalanceExceeded` (`logic/logic.rs:74`); `ExecutionResultState::new` panics if the starting balance overflows `u128` (`:49`) — a should-never-happen invariant guaranteed by the runtime, which pre-checks it (`runtime/runtime/src/function_call.rs:49`).
- **Preparation defense-in-depth.** `CompilationError::WasmtimeCompileError` (`errors.rs:138`) is emitted when the backend rejects a module our own preparation pass should have caught; it is a graceful abort, not a crash.
- **Host errors survive the wasmtime boundary.** Every host error is boxed in an `ErrorContainer` (`wasmtime_runner/mod.rs:1071`) and taken back out by value in `IntoVMError` (`:333`); taking it twice `panic!`s (`:339`), which asserts the one-error-per-trap invariant.
- **Cache poisoning is bounded.** A compile failure, a missing `memory` export, a link failure, and (at PV ≥ 87) a deserialize failure are all cached as `FunctionCallError`s keyed by the same `ContractCacheKey`, so a bad contract is diagnosed once and replayed identically, rather than recompiled every call.

## Open questions

- Testnet executed protocol version 87 from 2026-09-23 under 2.14.0-rc.1 binaries, where `87.yaml` still carried `universal_accounts: { new: true }`. In 2.14.0 that line moved to `88.yaml`, so a 2.14.0 node replaying testnet blocks from that window derives `universal_accounts: false` at 87. Whether any testnet traffic in that window actually linked or called the two universal-account host functions (which would make the replay diverge, rather than merely compute a different config hash) could not be determined from the tree. Mainnet is unaffected: it has not voted 87 yet (`core/primitives/src/version.rs:63`).
- The exact per-check ordering inside `prepare_v3` when several limits are violated at once follows wasm section order (types → tables → globals → functions → code), but the interaction with `finite_wasm` analysis errors (which all collapse to `Deserialization`/`Serialization`) was not exhaustively traced; `instrument_v3.rs` was read only for its error mapping.
- `max_globals_per_contract` (#16047) has now been enforced-but-unset on the stable path across two releases. Whether the cap is intended to reach a stable version before nightly reaches 157, and what would break if it were set at a stable version, could not be determined from the tree.
- `VMKind::replace_with_wasmtime_if_unsupported` and the `Wasmer0`/`Wasmer2`/`NearVm` enum variants are retained "because `VMKind` is part of a serialization protocol" (`core/parameters/src/vm.rs:15`), and nothing at a supported protocol version can produce those values. They are still load-bearing in one place: `VMKind` derives `BorshSerialize` (`core/parameters/src/vm.rs:21`) and is a field of `ContractCacheKey::Version5`, which is borsh-hashed into the on-disk cache key — so removing a variant would renumber `Wasmtime` from 1 and invalidate every cached artifact. Whether any other persisted artifact depends on the ordinals was not established.
- The `vm_hash` `version` constant (73) is bumped by hand when artifact compatibility changes; there is no automated check that it was bumped, so a missed bump would silently reuse incompatible cached artifacts. Whether CI covers this was not determined. It was *not* bumped for #16428, which is correct — that refactor changes no compiled output — but the absence of a check means the same judgement call is made unverified every release.
