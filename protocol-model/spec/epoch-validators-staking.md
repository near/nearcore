# Epoch management, validators & staking

> Protocol version: 87 (stable) · Release: 2.14.0-rc.1 · Derived from commit: 233252e · Generated: 2026-09-14
> Primary crates/files: `chain/epoch-manager/src/lib.rs`, `chain/epoch-manager/src/adapter.rs`, `chain/epoch-manager/src/validator_selection.rs`, `chain/epoch-manager/src/reward_calculator.rs`, `chain/epoch-manager/src/validator_stats.rs`, `chain/epoch-manager/src/epoch_info_aggregator.rs`, `chain/epoch-manager/src/genesis.rs`, `chain/epoch-manager/src/shard_assignment/mod.rs`, `chain/epoch-manager/src/shard_assignment/sticky_resharding.rs`, `core/primitives/src/epoch_info.rs`, `core/primitives/src/epoch_manager.rs`, `core/primitives/src/types.rs`, `core/store/src/columns.rs`, `core/store/src/adapter/epoch_store.rs`, `core/primitives-core/src/version.rs`

## Role

The epoch manager owns the validator economy. It divides the chain into variable-length **epochs** (nominally `epoch_length` blocks, but the boundary is finality-driven), and on the last block of each epoch T it deterministically computes the validator set for the epoch *after next* (T+2) from the staking proposals accumulated during T: who produces blocks, who produces chunks, who validates chunks, how seats are priced, how rewards and the protocol-treasury cut are distributed, who is kicked out (low uptime / missed chunks / stale protocol vote), which shard layout is in force and how chunk producers map to shards. It also tallies the per-block-producer protocol-version votes that drive network upgrades. New at v87: it additionally **pre-computes and persists the chunk producer of every shard for each block's grandchildren** (`DBCol::ChunkProducers`), excluding producers that are already failing inside the current epoch — the `EarlyKickout` feature, which moves chunk-producer punishment from "end of epoch" to "within the epoch". Stake proposals arrive as the output of `Stake` actions executed by [runtime-execution](runtime-execution.md); the producer schedule it computes is consumed by [consensus-finality](consensus-finality.md) (approver set + per-account stake) and [sharding-chunks](sharding-chunks.md) (chunk producer/validator assignment). Reward amounts feed the inflation accounting in [economics](economics.md); the version tally is the input side of [protocol-versioning](protocol-versioning.md). Shard-layout *migration* (resharding mechanics) lives in [sharding-chunks](sharding-chunks.md); only the per-epoch *choice* of layout and producer assignment lives here.

## Behavior

### 1. Epoch boundary detection (finality-driven)

The next block after `block_info` starts a new epoch iff `last_final_height + 3 >= estimated_next_epoch_start`, where `estimated_next_epoch_start = epoch_first_block.height + epoch_length` — `is_next_block_in_next_epoch_impl` (`lib.rs:1978`, decision at `lib.rs:1996`). For `epoch_length <= 3` a test-only shortcut uses `block_height + 1 >= estimated_next_epoch_start` (`lib.rs:1993`). So an epoch ends once a block is *finalized* within 3 of the estimated end; the boundary is not a fixed height. SPICE additionally blocks the transition while execution lags a full epoch behind (`lib.rs:2010`). Two lookahead variants exist for block production: `is_produced_block_last_in_epoch` (`lib.rs:1570`) and `is_next_block_possibly_last_in_epoch` (`lib.rs:1602`, may false-positive, never false-negative).

### 2. Recording a block, stamping its epoch, and seeding chunk producers

`record_block_info` (`lib.rs:1252`) wraps `record_block_info_impl` (`lib.rs:1271`) and, **on error, evicts the `blocks_info`/`epochs_info` cache entries it may have written** (`lib.rs:1264`) — callers drop the store update on error, so a cached-but-uncommitted value would otherwise be visible to other readers. `has_block_info` deliberately asks the *store*, not the cache, for the same reason (`lib.rs:2110`).

`record_block_info_impl` order of operations:
1. Genesis is special-cased as a new epoch under `EpochId(genesis_hash)` (`lib.rs:1280`), asserting zero proposals (`lib.rs:1282`), and then seeds chunk-producer rows for its grandchildren against the pre-genesis epoch info (`lib.rs:1297`) with an all-zero `final_hash` (empty blacklist).
2. The first real block (parent is genesis) gets `EpochId::default()` and becomes `epoch_first_block` (`lib.rs:1315`).
3. If the parent ends its epoch (`is_next_block_in_next_epoch(parent)`), the block gets `get_next_epoch_id_from_info(parent)` and becomes the new `epoch_first_block` (`lib.rs:1320`).
4. Otherwise it copies the parent's `epoch_id`/`epoch_first_block` (`lib.rs:1326`).
5. `save_block_info` (`lib.rs:1334`), then **`seed_chunk_producers`** for chunks anchored at this block (`lib.rs:1342`; see §11c). Since #15944 this is the single block-processing writer of `DBCol::ChunkProducers`, so the rows commit atomically with the block's `BlockInfo`.
6. The epoch-info aggregator is advanced only when the last-final block moves forward (`lib.rs:1357`), so no aggregator rollback is ever needed.
7. If the recorded block is itself the last block of its epoch, `finalize_epoch` runs (`lib.rs:1371`).
8. `DBCol::EpochStart` is written **last**, after every fallible step, when the block starts an epoch (`lib.rs:1377` → `save_epoch_start`, `lib.rs:2132`), so a failed record leaves no stale row.

### 3. EpochId and the T-2 rule

Epoch T's `EpochId` is `EpochId(hash of last block of T-2)` (`get_next_epoch_id_from_info` takes the first block of T and returns `EpochId(prev_hash)`, i.e. the last block of the previous epoch — `lib.rs:2044`). Correspondingly the `EpochInfo` computed at the end of epoch T is for T+2 and is stored under `EpochId(*last_block_hash_of_T)` (`lib.rs:1237`, `lib.rs:1248`). This two-epoch lead is why a `Stake` action takes ~2 epochs to affect the validator set.

### 4. Finalizing an epoch → computing T+2's validators

`finalize_epoch` (`lib.rs:1124`) runs on the last block of epoch T, in this order:
1. `collect_blocks_info` (`lib.rs:1131` → `lib.rs:843`) reads the epoch's `EpochInfoAggregator` (`get_epoch_info_aggregator_upto_last`, `lib.rs:858`) and builds an `EpochSummary`: proposals, kickouts, per-validator block/chunk/endorsement stats, and `next_next_epoch_version`. The version tally (see §8) and the uptime/miss kickouts (`compute_validators_to_reward_and_kickout`; see §6) both run *inside* this call (`lib.rs:873`, `lib.rs:967`). The summary is persisted for RPC (`lib.rs:1139`).
2. Rewards: kicked-out validators whose reason is `NotEnoughBlocks`/`NotEnoughChunks`/`NotEnoughChunkEndorsements` are first removed from the reward stats (`lib.rs:1156`), then `RewardCalculator::calculate_reward` runs over `epoch_duration = block.timestamp - prev_epoch_last_block.timestamp` (`lib.rs:1154`, `lib.rs:1176`). `endorsement_cutoff_threshold` is set to `chunk_validator_only_kickout_threshold` (`lib.rs:1172`).
3. Choose the T+2 shard layout (`next_next_shard_layout`, `lib.rs:1189` → `lib.rs:1006`) and set `last_resharding` if the layout changed (`lib.rs:1198`).
4. Choose the `AssignmentStrategy` from the T+1 vs T+2 layouts (`AssignmentStrategy::select`, `lib.rs:1202`).
5. `proposals_to_epoch_info` (`lib.rs:1209`; see §5) selects roles and builds the new `EpochInfo`, stored under `EpochId(*last_block_hash)` (`lib.rs:1237`/`lib.rs:1248`).
If selection fails because everyone unstaked (`EpochError::ThresholdError` or `NotEnoughValidators`), it clones the previous `EpochInfo` and just bumps `epoch_height` (`lib.rs:1223`, `lib.rs:1229`).

### 5. Validator selection from proposals

`proposals_to_epoch_info` (`validator_selection.rs:166`):
1. `apply_epoch_update_to_proposals` (`validator_selection.rs:290`) merges last-epoch proposals with the previous validator set into a per-account proposal map. Priority: an account in `validator_kickout` is dropped and its `stake_change` set to 0; an account kicked out for `ProtocolVersionTooOld` in T-1 is *barred from re-entry* in T (`validator_selection.rs:303`); otherwise a fresh proposal wins, else the prior stake is carried; rewards from last epoch are added to the carried stake (`validator_selection.rs:322`).
2. `select_validators_from_proposals` (`validator_selection.rs:45`) runs `select_validators` three independent times over the *same* proposal set — once each for chunk-producer, block-producer and chunk-validator seats — using `num_chunk_producer_seats`, `num_block_producer_seats`, `num_chunk_validator_seats`. The overall stake `threshold` is the minimum of the three role thresholds (`validator_selection.rs:88`). An account may hold several roles.
3. `select_validators` (`validator_selection.rs:357`) takes the top-N by stake from a max-heap, but stops early if adding proposal `p` would make `p.stake / running_total <= minimum_stake_ratio` (`validator_selection.rs:369`) — this is why low-relative-stake proposals are excluded even when seats remain. The threshold is `last_selected_stake + 1` when all N seats fill, otherwise `min_stake_ratio * total / (1 - min_stake_ratio)` rounded up (`validator_selection.rs:381`).
4. Proposals selected for no role, but which were validators in T, are kicked out with `NotEnoughStake{stake, threshold}` and their `stake_change` set to 0 (`validator_selection.rs:204`).
5. Ordering: proposals are compared by `(stake, Reverse(account_id))` (`OrderedValidatorStake::key`, `validator_selection.rs:405`) — larger stake wins, ties broken by lexicographically *smaller* account id.
6. `get_chunk_producers_assignment` (`validator_selection.rs:98`) builds `all_validators` and `validator_to_index` by walking chunk producers, then block producers, then chunk validators, assigning each account a stable local `ValidatorId` in that order (`validator_selection.rs:118`), then assigns chunk producers to shards (see §9, `validator_selection.rs:143`).
7. Chunk validators are wired via `ValidatorMandates::new` over `all_validators` with `target_validator_mandates_per_shard` mandates per shard (`validator_selection.rs:258`); a validator's mandate count derives from its stake vs the seat-price threshold.
8. Finally builds the `EpochInfo` with `epoch_height = prev + 1` (`validator_selection.rs:261`).

Genesis uses the same path: `make_genesis_epoch_info` (`genesis.rs:39`, called from `initialize_genesis_epoch_info`, `genesis.rs:21`) calls `proposals_to_epoch_info` with `AssignmentStrategy::Fresh` and `self.config.genesis_shard_layout()` (`genesis.rs:85`). Since #16148 a *dynamic* layout in genesis is allowed; a static layout in the genesis epoch config is only *required* when `DynamicResharding` is not enabled at the genesis protocol version, otherwise `EpochError::ShardingError` — "static shard layout expected for genesis when dynamic resharding is disabled" (`genesis.rs:68`). Mainnet/testnet keep a hardcoded genesis `EpochInfo` digest assertion (`genesis.rs:57`/`genesis.rs:60`).

### 6. Kickouts (end of epoch)

`compute_validators_to_reward_and_kickout` (`lib.rs:699`) computes per-validator `BlockChunkValidatorStats` by summing the block tracker and, over all shards, the chunk-production and endorsement trackers (`lib.rs:716`–`739`; the SPICE branch at `lib.rs:736` folds in header-carried endorsement stats). Then:
- **Block producers**: `NotEnoughBlocks` if produced/expected ratio `< block_producer_kickout_threshold` (`lib.rs:795`).
- **Chunk producers**: `NotEnoughChunks` if chunk-production ratio `< chunk_producer_kickout_threshold` (`lib.rs:804`).
- **Chunk-validator-only** (expected 0 blocks and 0 chunks): `NotEnoughChunkEndorsements` if endorsement ratio `< chunk_validator_only_kickout_threshold` (`lib.rs:814`).
- **Stale vote** (in `collect_blocks_info`): any validator whose voted version `< next_next_epoch_version` is kicked with `ProtocolVersionTooOld` (`lib.rs:915`).
- **Unstaked** (in `collect_blocks_info`): a zero-stake proposal from an account that still had nonzero stake in T+1 is kicked with `Unstaked` (`lib.rs:930`).

Two safety valves cap kickouts:
- **Stake cap**: at most `validator_max_kickout_stake_perc` of total validator stake may be kicked. `compute_exempted_kickout` (`lib.rs:642`) exempts validators (ordered by online ratio, then stake, then account id — `validator_comparator`, `lib.rs:754`) until the exempt set reaches `100 - validator_max_kickout_stake_perc` of stake (`lib.rs:657`).
- **Never kick everyone**: if every validator would be kicked or was already kicked, the one with the most produced blocks is saved (`all_kicked_out` → `validator_kickout.remove(max_validator)`, `lib.rs:834`).

Since #15843 the *chunk-production* half of these stats is attributed to the producer that consensus actually resolved (see §11f), not to a fresh canonical sample — see `anchored_chunk_producers_for_aggregator` (`lib.rs:2322`) and `EpochInfoAggregator::update_tail` (`epoch_info_aggregator.rs:66`, producer choice at `epoch_info_aggregator.rs:108`). Without this, a producer excluded by the early-kickout blacklist would keep accruing `expected` counts it was never asked to fill.

### 7. Reward computation and protocol treasury

`RewardCalculator::calculate_reward` (`reward_calculator.rs:51`):
1. `epoch_total_reward = max_inflation_rate * total_supply * epoch_duration / (num_seconds_per_year * NUM_NS_IN_SECOND)` (`reward_calculator.rs:69`).
2. `epoch_protocol_treasury = epoch_total_reward * protocol_reward_rate` credited to `protocol_treasury_account` (`reward_calculator.rs:78`, `reward_calculator.rs:84`). If `genesis_protocol_version == PROD_GENESIS_PROTOCOL_VERSION` (29) the rate is hardcoded to `1/10` (`reward_calculator.rs:63`).
3. The remaining `epoch_validator_reward` (`reward_calculator.rs:88`) is split pro-rata by stake, scaled by an online multiplier `min(1, (uptime - online_min)/(online_max - online_min))` (`reward_calculator.rs:109`–`141`); a validator below `online_min_threshold`, or with zero expected blocks/chunks/endorsements, gets 0 (`reward_calculator.rs:109`). The `production_ratio` blends block, chunk and endorsement ratios via `get_validator_online_ratio` (`validator_stats.rs:16`), applying the endorsement cutoff.
4. Returns `(rewards_map, actual_minted)`, where `actual_minted` sums treasury + all validator rewards (`reward_calculator.rs:145`) — this is `minted_amount` stored on the next `EpochInfo`.
Inflation-curve economics (why `max_inflation_rate` is what it is) live in [economics](economics.md).

### 8. Protocol-version vote tally

Inside `collect_blocks_info` (`lib.rs:873`): each block producer's most-recent voted version is weighted by that producer's stake (`lib.rs:876`). `total_block_producer_stake` is the deduped sum of block-producer stakes (`lib.rs:861`). The highest-staked version becomes `next_next_epoch_version` iff its stake `> total_block_producer_stake * protocol_upgrade_stake_threshold`, otherwise the current `next_epoch_info.protocol_version()` is kept (`lib.rs:894`–`907`). Validators voting below the resulting version are kicked out (step 6, `lib.rs:915`). Per-version stake percentages are exported as `PROTOCOL_VERSION_VOTES` and the outcome as `PROTOCOL_VERSION_NEXT` (`lib.rs:880`, `lib.rs:909`). See [protocol-versioning](protocol-versioning.md) for how votes are emitted and how the on/off schedule gates them; at this commit the MAINNET voting schedule is empty and TESTNET is scheduled to vote PV 87 on 2026-09-21 (`core/primitives/src/version.rs:58`–`67`).

### 9. Shard layout choice and chunk-producer assignment

- **Layout for T+2**: `next_next_shard_layout` (`lib.rs:1006`) returns the static layout if `next_next_epoch_config` defines one (`lib.rs:1021`); else, if dynamic resharding isn't yet active in T, reuses the T+1 layout (`lib.rs:1027`); else, if `block_info.shard_split()` names a shard+boundary, derives a new V3 layout via `derive_v3` (`lib.rs:1065`), otherwise reuses T+1's (`lib.rs:1033`). A split naming a shard that no longer exists in T+1 is skipped with a warning (`lib.rs:1040`). Which shard is proposed for splitting is decided at block production by `get_upcoming_shard_split` (`lib.rs:2621`) + `pick_shard_to_split` (`lib.rs:2665`), subject to the `min_epochs_between_resharding` cooldown (`can_reshard`, `lib.rs:1104`).
- **Strategy**: `AssignmentStrategy::select` (`mod.rs:170`) → `CarryOver` if layouts equal; `Fresh` if `StickyReshardingValidatorAssignment` is off; else `StickyResharding` (falling back to `Fresh` if sticky construction fails).
- **Assignment**: `assign_chunk_producers_to_shards` (`mod.rs:409`) errors `NotEnoughValidators` if `chunk_producers.len() < min_validators_per_shard` (`mod.rs:424`). When there are too few producers to fill every shard without repeats (`< min_validators_per_shard * num_shards`), it uses `assign_to_satisfy_shards` (repeats allowed, strategy ignored — `mod.rs:438`); otherwise `assign_to_balance_shards` (`mod.rs:446` → `mod.rs:287`) seeds from the strategy (`get_initial_chunk_producer_assignment`, `mod.rs:248`), places new validators onto the least-populated shards, then rebalances via random moves from the largest to smallest shard until balanced or the change limit is used. Sticky resharding raises the change limit to `max(limit, producers/shards)` (`needs_changes_limit_override`, `mod.rs:196`; applied at `mod.rs:431`) to top up freshly split children in one epoch.
- **Shuffle**: if `shuffle_shard_assignment_for_chunk_producers` is set, the whole `chunk_producers_settlement` is shuffled with the shard-assignment RNG (`validator_selection.rs:236`) — controlled by `ShuffleShardAssignments` (nightly only, see below).

### 10. Per-height producer/validator sampling

Given a finished `EpochInfo` (V3+), producers are sampled stake-weighted and deterministically from `rng_seed` + height (+ shard):
- **Block producer**: `sample_block_producer(height)` seeds `StakeWeightedIndex` with `hash(rng_seed || height)` (`epoch_info.rs:535`, seed at `epoch_info.rs:714`).
- **Chunk producer (canonical)**: `sample_chunk_producer(shard_layout, shard_id, height)` samples the per-shard `chunk_producers_sampler` from `hash(rng_seed || height || shard_id)` (`epoch_info.rs:560`, seed at `epoch_info.rs:721`).
- **Chunk producer excluding a blacklist** (new at v87): `sample_chunk_producer_excluding` (`epoch_info.rs:600`) filters the shard's settlement by the excluded `ValidatorId` set and then samples. With an empty exclusion set it delegates verbatim to `sample_chunk_producer` (`epoch_info.rs:607`). V1/V2 use `height % filtered.len()` (`sample_excluding_modulo`, `epoch_info.rs:644`); V3/V4/V5 build a **fresh `StakeWeightedIndex` renormalized over the survivors** and sample it with the same `chunk_produce_seed` (`sample_excluding_weighted`, `epoch_info.rs:659`). Returns `None` only when every eligible producer was excluded.
- **Chunk validators**: `sample_chunk_validators(height)` shuffles the `validator_mandates` with a ChaCha20 RNG seeded by `hash(rng_seed || height)` (`epoch_info.rs:679`, `epoch_info.rs:736`); empty for V1–V3. Results are cached per `(epoch_id, shard_id, height)` (`lib.rs:1446`).
Pre-V3 `EpochInfo` sampled block/chunk producers by round-robin (`height % settlement.len()`, `epoch_info.rs:537`/`epoch_info.rs:568`) rather than stake-weighted.

### 11. Early kickout: blacklist, seeding, and anchored producer lookup (v87)

`EarlyKickout` (stable at 87) replaces "sample the chunk producer for height H on demand" with "read the producer that was pre-committed at H's **grandparent anchor**". The anchor is the chunk's grandparent block; the nominal offset is `CHUNK_GRANDPARENT_ANCHOR_HEIGHT_OFFSET = 2` (`adapter.rs:35`).

**11a. Blacklist math.** `compute_chunk_producer_blacklist` (`lib.rs:292`) walks the aggregator's `shard_tracker`. For each shard it takes the *distinct* producers in that shard's settlement (`lib.rs:307`) — endorsement-only entries are skipped so chunk validators neither become candidates nor skew the denominator (`lib.rs:310`). A producer is a candidate iff **both**:
- `missed >= EARLY_KICKOUT_MIN_MISSES` where `missed = expected - produced` (constant `100`, `lib.rs:70`), and
- `produced * 100 < expected * 80` — production ratio below 80% (`lib.rs:71`–`72`, compared in `u128` at `lib.rs:316`).

**Keep-one-least-bad safety valve** (`lib.rs:332`): if *every* distinct producer of a shard is a candidate, exactly one is kept eligible — the one with the highest `produced/expected`, compared by integer cross-multiplication, tie-broken by *fewer* `expected` and then by *lower* `ValidatorId` (`lib.rs:339`–`342`). The ordering is a deterministic total order precisely because `HashSet` iteration order is not consensus-safe. A 1-producer shard therefore ends up with an empty blacklist (`lib.rs:352`).

**11b. Basis and grace.** `blacklist_for_epoch` (`lib.rs:374`) returns an empty blacklist when the aggregator belongs to a different epoch than the sample epoch (`lib.rs:383`) or when `blocks_into_epoch < EARLY_KICKOUT_EPOCH_GRACE_BLOCKS` (constant `1000`, `lib.rs:75`; check at `lib.rs:386`). `chunk_producer_blacklist_at_anchor` (`lib.rs:2406`) supplies both: the stats basis is the **anchor's last-final block** (`lib.rs:2415`), which is header-derived and therefore identical on every node for a canonical anchor and does not walk the growing non-final suffix during a finality stall; and `blocks_into_epoch` is computed from `get_epoch_start_height` — the `BlockInfo.epoch_first_block` walk (`lib.rs:2427`, `lib.rs:1636`) — **not** `DBCol::EpochStart`, because same-parent boundary siblings overwrite that shared row and its value would depend on fork processing order (#16139; the hazard is documented on `get_epoch_start_from_epoch_id`, `lib.rs:2146`). A genesis/default `final_hash` yields an empty blacklist (`lib.rs:2412`).

**11c. Seeding.** `seed_chunk_producers` (`lib.rs:2460`) is a no-op unless `EarlyKickout` is enabled **for the anchor's own epoch** (`lib.rs:2466`) — gating on the anchor's own epoch avoids writing dead rows for last-of-epoch anchors across an activation edge. It computes the blacklist via the shared helper (not the adapter accessor, which would re-take the read lock and deadlock, `lib.rs:2471`), emits the `EARLY_KICKOUT_BLACKLIST_SIZE` / `EARLY_KICKOUT_SAFETY_VALVE_FIRED` metrics (`lib.rs:2481`–`2500`; only here, never in the accessor, to avoid double counting), then `seed_chunk_producer_rows` (`lib.rs:2516`) samples each shard at `anchor.height + 2` via `sample_chunk_producer_excluding` (`lib.rs:2529`) and writes `(anchor_hash, shard_id) → ValidatorStake` with `set_chunk_producer` (`lib.rs:2574` → `core/store/src/adapter/epoch_store.rs:156`). A reassignment is counted only when the *plain* pick would itself have been blacklisted (`lib.rs:2554`–`2563`) — comparing `plain != sampled` would over-count, since the renormalized draw can legitimately move the pick.

**11d. Epoch sync.** The first block installed by epoch sync bypasses `record_block_info`, so `seed_chunk_producers_after_epoch_sync` (`adapter.rs:1224` → `seed_chunk_producers_for_first_block`, `lib.rs:2588`) seeds its rows in the same store update with an **empty** blacklist (first block of an epoch has no in-epoch stats, and the aggregator walk would fail because the block lives only in the pending update). The same path also writes the `EpochStart` row that `record_block_info` would have written (`chain/client/src/sync/epoch.rs:312`), which the grace check no longer reads but `get_validator_info`, `compare_epoch_id` and the epoch-sync-proof machinery still do (#16125).

**11e. Consensus read.** `get_chunk_producer_info_anchored` (`adapter.rs:594`, impl `adapter.rs:1093`) gates on the **chunk's** epoch protocol version (`adapter.rs:1106`). If the anchor exists and is in the *same* epoch as the chunk, it reads `DBCol::ChunkProducers` and hard-errors `EpochError::ChunkProducerNotInDB` on a miss (`adapter.rs:1121`; `core/primitives/src/errors.rs:1353`). If the feature is off, there is no anchor (genesis / genesis+1), or the anchor is in the *previous* epoch (the first ≤2 blocks of an epoch, where the blacklist is provably empty), it falls back to canonical sampling at `height_created` (`adapter.rs:1131`). `get_chunk_producer_info_from_prev_block` (`adapter.rs:608`) derives epoch, height and anchor from a **processed** parent block and delegates — this is what chunk production, chunk validation, chunk forwarding and signature verification call (`chain/chunks/src/shards_manager_actor.rs:506`, `shards_manager_actor.rs:2195`, `chain/chain/src/signature_verification.rs:56`, `chain/client/src/chunk_producer.rs:174`). A missing anchor block surfaces as `MissingBlock` (node ≥2 blocks behind).

**11f. Stats attribution.** `anchored_chunk_producers_for_aggregator` (`lib.rs:2322`) mirrors 11e for the kickout aggregator but is *lenient*: on a missing row or an account outside the epoch it falls back to canonical sampling at the anchor offset rather than erroring (`lib.rs:2369`, `lib.rs:2387`), because canonical sampling is exact wherever the blacklist is empty. It returns `None` (legacy sampler) when the feature is off, at genesis, when the anchor `BlockInfo` is missing, or when the anchor is cross-epoch (`lib.rs:2329`–`2342`).

**11g. Live blacklist accessor.** `get_chunk_producer_blacklist` (`adapter.rs:1135`) recomputes the blacklist for an anchor through the same `chunk_producer_blacklist_at_anchor` helper, so a live read always agrees with the stored row.

**11h. Test-only thresholds.** `EARLY_KICKOUT_MIN_MISSES` and `EARLY_KICKOUT_EPOCH_GRACE_BLOCKS` are read through functions that, under `test_features`, consult a **thread-local** override installed by `set_early_kickout_thresholds_for_testing` (`lib.rs:169`) and restored by a `!Send` drop guard (`lib.rs:149`). Production builds inline the constants (`lib.rs:80`, `lib.rs:87`). The override is deliberately not reachable from any runtime/adversarial RPC.

**11i. Storage lifecycle.** Rows are insert-only and garbage-collected together with their anchor: `gc_chunk_producers_for_block` (`chain/chain/src/garbage_collection.rs:535`) prefix-scans by anchor hash and is called from block-data cleanup (`garbage_collection.rs:753`, `garbage_collection.rs:1027`) and from the header-only sweep (`garbage_collection.rs:607`), so header hashes that never received a body do not orphan rows (#16023).

## Invariants & failure modes

- **Slashing is inactive.** `ValidatorKickoutReason::_UnusedSlashed` is variant 0 and deprecated (`types.rs:1256`); no code path produces a slash, and `CurrentEpochValidatorInfo::is_slashed` is hardcoded `false` (`lib.rs:1749`). Stake is only ever returned or lost via kickout/unstake, never confiscated.
- **Never kick out everyone (epoch boundary).** Enforced by the `all_kicked_out` guard that restores the top block producer (`lib.rs:834`).
- **Never blacklist every producer of a shard (early kickout).** The keep-one-least-bad valve (`lib.rs:332`) guarantees at least one eligible producer per non-empty shard; `seed_chunk_producer_rows` `debug_assert!`s that the excluding sampler returns `Some` for every shard with a non-empty settlement (`lib.rs:2540`).
- **Blacklist determinism is consensus-critical.** The stats basis is the anchor's *last-final* block (header-derived, `lib.rs:2472`); the epoch-start height comes from the `BlockInfo` walk, never from the fork-order-dependent `DBCol::EpochStart` row (`lib.rs:2427`); the least-bad tiebreak is a total order over `(ratio, -expected, validator_id)` (`lib.rs:339`). Violating any of these makes two honest nodes seed different rows and the reader hard-error.
- **Kickout stake is capped** at `validator_max_kickout_stake_perc` via `compute_exempted_kickout` (`lib.rs:642`).
- **Two-epoch staking lag** is structural: T+2's `EpochInfo` is computed at the end of T and stored under `EpochId(last_block_of_T)` (`lib.rs:1237`).
- **Proposals must be unique per account** — `debug_assert!` in `proposals_to_epoch_info` (`validator_selection.rs:179`); genesis must carry zero proposals — `assert_eq!` (`lib.rs:1282`).
- **Determinism of sampling**: all sampling is a pure function of `(rng_seed, height, shard_id)` (`epoch_info.rs:714`/`epoch_info.rs:721`/`epoch_info.rs:736`); shard-assignment randomness uses `EpochInfo::shard_assignment_rng` seeded from `rng_seed` (`epoch_info.rs:753`) so all honest nodes derive the identical settlement.
- **Cache/store consistency**: a failed `record_block_info` evicts the `blocks_info`/`epochs_info` entries it wrote (`lib.rs:1264`), and `has_block_info` reads the store rather than the cache (`lib.rs:2110`), so a dropped store update can never leave a phantom block visible.
- **Atomic seeding**: `ChunkProducers` rows are written into the *same* `EpochStoreUpdateAdapter` as the block's `BlockInfo` (`lib.rs:1334`/`lib.rs:1342`), so a block is never visible without its rows.
- **Everyone unstaked** → selection returns `ThresholdError`/`NotEnoughValidators`; handled by cloning prev `EpochInfo` and bumping height (`lib.rs:1223`), so the chain does not stall.
- **Too few chunk producers for a shard** → `assign_chunk_producers_to_shards` returns `NotEnoughValidators` (`mod.rs:424`), surfaced as `EpochError::NotEnoughValidators` (`validator_selection.rs:152`).
- **Missing chunk-producer row on the consensus path** → `EpochError::ChunkProducerNotInDB(anchor, shard_id)` (`adapter.rs:1121`). The stats path deliberately does not error, falling back to canonical sampling (`lib.rs:2363`).
- **`ProtocolVersionTooOld` bars re-entry** the following epoch (`validator_selection.rs:303`), preventing a validator that voted stale from immediately rejoining.
- **Balancing assertion**: `assign_to_balance_shards` asserts it never exceeds the hard change limit and never balances a shard with itself (`mod.rs:345`, `mod.rs:351`) — a panic here indicates a duplicate chunk producer in the prev assignment.
- **Transaction validity period ≤ 2 epochs** is asserted at construction for every epoch config, required by continuous epoch sync (`lib.rs:549`).

- The early-kickout constants (`EARLY_KICKOUT_MIN_MISSES = 100`, 80% production ratio, 1000-block grace) are hardcoded in `chain/epoch-manager/src/lib.rs:70`–`75` rather than living in `EpochConfig`. They are therefore **not** per-protocol-version tunable and cannot be changed by an epoch-config update — only by a binary release. Whether that is intentional (consensus simplicity) or a follow-up is not determinable from the code.
- `get_chunk_producer_info_anchored` reads `DBCol::ChunkProducers` on every lookup with no cache; the in-code TODO (`adapter.rs:1103`) flags this as a known performance gap. The production impact at mainnet chunk rates is not established here.
- `seed_chunk_producers` writes a row for a last-of-epoch anchor whose grandchild falls in the next epoch. The code argues this row is not read on any honest path but is reachable by the best-effort V2 partial-witness resolver with a sender-claimed epoch (`lib.rs:2446`). Whether that non-consensus path can be driven to a useful mis-resolution is a question for [stateless-validation](stateless-validation.md), not answerable from this component alone.
- Two DB-version bumps land in this release and only one belongs to this component: `DBCol::ChunkProducers` is the 49→50 bump and needs no data migration (`nearcore/src/migrations.rs:79` is `49 => Ok(())`), while 50→51 is the unrelated versioned-`StoredLightClientBlock` migration (`nearcore/src/migrations.rs:80`). The tree's `DB_VERSION` is therefore **51** (`core/store/src/db/metadata.rs:5`) even though the column arrived at 50.
