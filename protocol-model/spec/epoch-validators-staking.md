> Protocol version: 88 (stable) · Release: 2.14.0 · Derived from commit: bc4e9e8 · Generated: 2026-11-03
> Primary crates/files: `chain/epoch-manager/src/lib.rs`, `chain/epoch-manager/src/adapter.rs`, `chain/epoch-manager/src/validator_selection.rs`, `chain/epoch-manager/src/reward_calculator.rs`, `chain/epoch-manager/src/validator_stats.rs`, `chain/epoch-manager/src/epoch_info_aggregator.rs`, `chain/epoch-manager/src/genesis.rs`, `chain/epoch-manager/src/shard_assignment/mod.rs`, `chain/epoch-manager/src/shard_assignment/sticky_resharding.rs`, `core/primitives/src/epoch_info.rs`, `core/primitives/src/epoch_manager.rs`, `core/primitives/src/types.rs`, `core/store/src/columns.rs`, `core/store/src/adapter/epoch_store.rs`, `core/primitives-core/src/version.rs`

## Role

The epoch manager owns the validator economy. It divides the chain into variable-length **epochs** (nominally `epoch_length` blocks, but the boundary is finality-driven), and on the last block of each epoch T it deterministically computes the validator set for the epoch *after next* (T+2) from the staking proposals accumulated during T: who produces blocks, who produces chunks, who validates chunks, how seats are priced, how rewards and the protocol-treasury cut are distributed, who is kicked out (low uptime / missed chunks / stale protocol vote), which shard layout is in force and how chunk producers map to shards. It also tallies the per-block-producer protocol-version votes that drive network upgrades. Stable since v87 (unchanged at v88): it additionally **pre-computes and persists the chunk producer of every shard for each block's grandchildren** (`DBCol::ChunkProducers`), excluding producers that are already failing inside the current epoch — the `EarlyKickout` feature, which moves chunk-producer punishment from "end of epoch" to "within the epoch". Stake proposals arrive as the output of `Stake` actions executed by [runtime-execution](runtime-execution.md); the producer schedule it computes is consumed by [consensus-finality](consensus-finality.md) (approver set + per-account stake) and [sharding-chunks](sharding-chunks.md) (chunk producer/validator assignment). Reward amounts feed the inflation accounting in [economics](economics.md); the version tally is the input side of [protocol-versioning](protocol-versioning.md). Shard-layout *migration* (resharding mechanics) lives in [sharding-chunks](sharding-chunks.md); only the per-epoch *choice* of layout and producer assignment lives here.

## Behavior

### 1. Epoch boundary detection (finality-driven)

The next block after `block_info` starts a new epoch iff `last_final_height + 3 >= estimated_next_epoch_start`, where `estimated_next_epoch_start = epoch_first_block.height + epoch_length` — `is_next_block_in_next_epoch_impl` (`lib.rs:1991`, decision at `lib.rs:2009`). For `epoch_length <= 3` a test-only shortcut uses `block_height + 1 >= estimated_next_epoch_start` (`lib.rs:2006`). So an epoch ends once a block is *finalized* within 3 of the estimated end; the boundary is not a fixed height. SPICE additionally blocks the transition while execution lags a full epoch behind (`lib.rs:2023`). Two lookahead variants exist for block production: `is_produced_block_last_in_epoch` (`lib.rs:1583`) and `is_next_block_possibly_last_in_epoch` (`lib.rs:1615`, may false-positive, never false-negative).

### 2. Recording a block, stamping its epoch, and seeding chunk producers

`record_block_info` (`lib.rs:1261`) wraps `record_block_info_impl` (`lib.rs:1280`) and, **on error, evicts the `blocks_info`/`epochs_info` cache entries it may have written** (`lib.rs:1273`) — callers drop the store update on error, so a cached-but-uncommitted value would otherwise be visible to other readers. `has_block_info` deliberately asks the *store*, not the cache, for the same reason (`lib.rs:2123`).

`record_block_info_impl` order of operations:
1. Genesis is special-cased as a new epoch under `EpochId(genesis_hash)` (`lib.rs:1289`), asserting zero proposals (`lib.rs:1291`), and then seeds chunk-producer rows for its grandchildren against the pre-genesis epoch info (`lib.rs:1306`) with an all-zero `final_hash` (empty blacklist).
2. The first real block (parent is genesis) gets `EpochId::default()` and becomes `epoch_first_block` (`lib.rs:1324`).
3. If the parent ends its epoch (`is_next_block_in_next_epoch(parent)`), the block gets `get_next_epoch_id_from_info(parent)` and becomes the new `epoch_first_block` (`lib.rs:1329`).
4. Otherwise it copies the parent's `epoch_id`/`epoch_first_block` (`lib.rs:1335`).
5. `save_block_info` (`lib.rs:1343`), then **`seed_chunk_producers`** for chunks anchored at this block (`lib.rs:1351`; see §11c). Since #15944 this is the single block-processing writer of `DBCol::ChunkProducers`, so the rows commit atomically with the block's `BlockInfo`.
6. The epoch-info aggregator is advanced only when the last-final block moves forward (`lib.rs:1366`), so no aggregator rollback is ever needed.
7. If the recorded block is itself the last block of its epoch, `finalize_epoch` runs (`lib.rs:1380`).
8. `DBCol::EpochStart` is written **last**, after every fallible step, when the block starts an epoch (`lib.rs:1386` → `save_epoch_start`, `lib.rs:2153`), so a failed record leaves no stale row.
9. **New in 2.14.0 (#16474)**: the block's own `BlockInfo` is re-`put` into the `blocks_info` LRU as most-recently-used (`lib.rs:1396`), after everything above. Until the caller commits, that cache entry is the only readable copy, and the chain reads it pre-commit via `check_protocol_version`; see §11j.

### 3. EpochId and the T-2 rule

Epoch T's `EpochId` is `EpochId(hash of last block of T-2)` (`get_next_epoch_id_from_info` takes the first block of T and returns `EpochId(prev_hash)`, i.e. the last block of the previous epoch — `lib.rs:2057`). Correspondingly the `EpochInfo` computed at the end of epoch T is for T+2 and is stored under `EpochId(*last_block_hash_of_T)` (`lib.rs:1246`, `lib.rs:1257`). This two-epoch lead is why a `Stake` action takes ~2 epochs to affect the validator set.

### 4. Finalizing an epoch → computing T+2's validators

`finalize_epoch` (`lib.rs:1133`) runs on the last block of epoch T, in this order:
1. `collect_blocks_info` (`lib.rs:1140` → `lib.rs:852`) reads the epoch's `EpochInfoAggregator` (`get_epoch_info_aggregator_upto_last`, `lib.rs:867`) and builds an `EpochSummary`: proposals, kickouts, per-validator block/chunk/endorsement stats, and `next_next_epoch_version`. The version tally (see §8) and the uptime/miss kickouts (`compute_validators_to_reward_and_kickout`; see §6) both run *inside* this call (`lib.rs:882`, `lib.rs:976`). The summary is persisted for RPC (`lib.rs:1148`).
2. Rewards: kicked-out validators whose reason is `NotEnoughBlocks`/`NotEnoughChunks`/`NotEnoughChunkEndorsements` are first removed from the reward stats (`lib.rs:1165`), then `RewardCalculator::calculate_reward` runs over `epoch_duration = block.timestamp - prev_epoch_last_block.timestamp` (`lib.rs:1163`, `lib.rs:1185`). `endorsement_cutoff_threshold` is set to `chunk_validator_only_kickout_threshold` (`lib.rs:1181`).
3. Choose the T+2 shard layout (`next_next_shard_layout`, `lib.rs:1198` → `lib.rs:1015`) and set `last_resharding` if the layout changed (`lib.rs:1207`).
4. Choose the `AssignmentStrategy` from the T+1 vs T+2 layouts (`AssignmentStrategy::select`, `lib.rs:1211`).
5. `proposals_to_epoch_info` (`lib.rs:1218`; see §5) selects roles and builds the new `EpochInfo`, stored under `EpochId(*last_block_hash)` (`lib.rs:1246`/`lib.rs:1257`).
If selection fails because everyone unstaked (`EpochError::ThresholdError` or `NotEnoughValidators`), it clones the previous `EpochInfo` and just bumps `epoch_height` (`lib.rs:1232`, `lib.rs:1238`).

### 5. Validator selection from proposals

`proposals_to_epoch_info` (`validator_selection.rs:166`):
1. `apply_epoch_update_to_proposals` (`validator_selection.rs:290`) merges last-epoch proposals with the previous validator set into a per-account proposal map. Priority: an account in `validator_kickout` is dropped and its `stake_change` set to 0; an account kicked out for `ProtocolVersionTooOld` in T-1 is *barred from re-entry* in T (`validator_selection.rs:303`); otherwise a fresh proposal wins, else the prior stake is carried; rewards from last epoch are added to the carried stake (`validator_selection.rs:322`).
2. `select_validators_from_proposals` (`validator_selection.rs:45`) runs `select_validators` three independent times over the *same* proposal set — once each for chunk-producer, block-producer and chunk-validator seats — using `num_chunk_producer_seats`, `num_block_producer_seats`, `num_chunk_validator_seats`. The overall stake `threshold` is the minimum of the three role thresholds (`validator_selection.rs:88`). An account may hold several roles.
3. `select_validators` (`validator_selection.rs:357`) takes the top-N by stake from a max-heap, but stops early if adding proposal `p` would make `p.stake / running_total <= minimum_stake_ratio` (`validator_selection.rs:369`) — this is why low-relative-stake proposals are excluded even when seats remain. The threshold is `last_selected_stake + 1` when all N seats fill, otherwise `min_stake_ratio * total / (1 - min_stake_ratio)` rounded up (`validator_selection.rs:381`).
4. Proposals selected for no role, but which were validators in T, are kicked out with `NotEnoughStake{stake, threshold}` and their `stake_change` set to 0 (`validator_selection.rs:204`).
5. Ordering: proposals are compared by `(stake, Reverse(account_id))` (`OrderedValidatorStake::key`, `validator_selection.rs:405`) — larger stake wins, ties broken by lexicographically *smaller* account id.
6. `get_chunk_producers_assignment` (`validator_selection.rs:98`) builds `all_validators` and `validator_to_index` by walking chunk producers, then block producers, then chunk validators, assigning each account a stable local `ValidatorId` in that order (`validator_selection.rs:118`), then assigns chunk producers to shards (see §9, `validator_selection.rs:143`).
7. Chunk validators are wired via `ValidatorMandates::new` over `all_validators` with `target_validator_mandates_per_shard` mandates per shard (`validator_selection.rs:258`); a validator's mandate count derives from its stake vs the seat-price threshold.
8. Finally builds the `EpochInfo` with `epoch_height = prev + 1` (`validator_selection.rs:261`).

Genesis uses the same path: `make_genesis_epoch_info` (`genesis.rs:39`, called from `initialize_genesis_epoch_info`, `genesis.rs:21`) calls `proposals_to_epoch_info` with `AssignmentStrategy::Fresh` and `self.config.genesis_shard_layout()` (`genesis.rs:85`). Since #16148 a *dynamic* layout in genesis is allowed; a static layout in the genesis epoch config is only *required* when `DynamicResharding` is not enabled at the genesis protocol version, otherwise `EpochError::ShardingError` — "static shard layout expected for genesis when dynamic resharding is disabled" (`genesis.rs:68`). Mainnet/testnet keep a hardcoded genesis `EpochInfo` digest assertion (`genesis.rs:57`/`genesis.rs:60`).

### 6. Kickouts (end of epoch)

`compute_validators_to_reward_and_kickout` (`lib.rs:708`) computes per-validator `BlockChunkValidatorStats` by summing the block tracker and, over all shards, the chunk-production and endorsement trackers (`lib.rs:725`–`739`; the SPICE branch at `lib.rs:745` folds in header-carried endorsement stats). Then:
- **Block producers**: `NotEnoughBlocks` if produced/expected ratio `< block_producer_kickout_threshold` (`lib.rs:804`).
- **Chunk producers**: `NotEnoughChunks` if chunk-production ratio `< chunk_producer_kickout_threshold` (`lib.rs:813`).
- **Chunk-validator-only** (expected 0 blocks and 0 chunks): `NotEnoughChunkEndorsements` if endorsement ratio `< chunk_validator_only_kickout_threshold` (`lib.rs:823`).
- **Stale vote** (in `collect_blocks_info`): any validator whose voted version `< next_next_epoch_version` is kicked with `ProtocolVersionTooOld` (`lib.rs:924`).
- **Unstaked** (in `collect_blocks_info`): a zero-stake proposal from an account that still had nonzero stake in T+1 is kicked with `Unstaked` (`lib.rs:939`).

Two safety valves cap kickouts:
- **Stake cap**: at most `validator_max_kickout_stake_perc` of total validator stake may be kicked. `compute_exempted_kickout` (`lib.rs:651`) exempts validators (ordered by online ratio, then stake, then account id — `validator_comparator`, `lib.rs:763`) until the exempt set reaches `100 - validator_max_kickout_stake_perc` of stake (`lib.rs:666`).
- **Never kick everyone**: if every validator would be kicked or was already kicked, the one with the most produced blocks is saved (`all_kicked_out` → `validator_kickout.remove(max_validator)`, `lib.rs:843`).

Since #15843 the *chunk-production* half of these stats is attributed to the producer that consensus actually resolved (see §11f), not to a fresh canonical sample — see `anchored_chunk_producers_for_aggregator` (`lib.rs:2339`) and `EpochInfoAggregator::update_tail` (`epoch_info_aggregator.rs:66`, producer choice at `epoch_info_aggregator.rs:108`). Without this, a producer excluded by the early-kickout blacklist would keep accruing `expected` counts it was never asked to fill.

### 7. Reward computation and protocol treasury

`RewardCalculator::calculate_reward` (`reward_calculator.rs:51`):
1. `epoch_total_reward = max_inflation_rate * total_supply * epoch_duration / (num_seconds_per_year * NUM_NS_IN_SECOND)` (`reward_calculator.rs:69`).
2. `epoch_protocol_treasury = epoch_total_reward * protocol_reward_rate` credited to `protocol_treasury_account` (`reward_calculator.rs:78`, `reward_calculator.rs:84`). If `genesis_protocol_version == PROD_GENESIS_PROTOCOL_VERSION` (29) the rate is hardcoded to `1/10` (`reward_calculator.rs:63`).
3. The remaining `epoch_validator_reward` (`reward_calculator.rs:88`) is split pro-rata by stake, scaled by an online multiplier `min(1, (uptime - online_min)/(online_max - online_min))` (`reward_calculator.rs:109`–`141`); a validator below `online_min_threshold`, or with zero expected blocks/chunks/endorsements, gets 0 (`reward_calculator.rs:109`). The `production_ratio` blends block, chunk and endorsement ratios via `get_validator_online_ratio` (`validator_stats.rs:16`), applying the endorsement cutoff.
4. Returns `(rewards_map, actual_minted)`, where `actual_minted` sums treasury + all validator rewards (`reward_calculator.rs:145`) — this is `minted_amount` stored on the next `EpochInfo`.
Inflation-curve economics (why `max_inflation_rate` is what it is) live in [economics](economics.md).

### 8. Protocol-version vote tally

Inside `collect_blocks_info` (`lib.rs:882`): each block producer's most-recent voted version is weighted by that producer's stake (`lib.rs:885`). `total_block_producer_stake` is the deduped sum of block-producer stakes (`lib.rs:870`). The highest-staked version becomes `next_next_epoch_version` iff its stake `> total_block_producer_stake * protocol_upgrade_stake_threshold`, otherwise the current `next_epoch_info.protocol_version()` is kept (`lib.rs:903`–`907`). Validators voting below the resulting version are kicked out (step 6, `lib.rs:924`). Per-version stake percentages are exported as `PROTOCOL_VERSION_VOTES` and the outcome as `PROTOCOL_VERSION_NEXT` (`lib.rs:889`, `lib.rs:918`). See [protocol-versioning](protocol-versioning.md) for how votes are emitted and how the on/off schedule gates them. **Changed in 2.14.0**: the MAINNET schedule is no longer empty — it is a *two-step* schedule, PV **87 on 2026-11-04 00:00 UTC** then PV **88 on 2026-11-06 00:00 UTC** (`get_protocol_upgrade_schedule`, `core/primitives/src/version.rs:59`); TESTNET votes PV 87 on 2026-09-23 (moved from 2026-09-21) then PV 88 on 2026-10-21 (`core/primitives/src/version.rs:72`). Because at most one upgrade vote can be tallied per epoch, the two steps occupy two different epochs: 87 arms `RejectUniversalAccountTransfers` / `RejectBlockHeaderV7BeforeSpice` before `UniversalAccounts` turns on at 88. Neither of the two 87/88 rows affects this component beyond the ordinary tally; `EarlyKickout` activates with the **first** step (87) — it is *not* a v88 feature, so the §11j fix is a prerequisite for the mainnet 87 step, not the 88 one.

### 9. Shard layout choice and chunk-producer assignment

- **Layout for T+2**: `next_next_shard_layout` (`lib.rs:1015`) returns the static layout if `next_next_epoch_config` defines one (`lib.rs:1030`); else, if dynamic resharding isn't yet active in T, reuses the T+1 layout (`lib.rs:1036`); else, if `block_info.shard_split()` names a shard+boundary, derives a new V3 layout via `derive_v3` (`lib.rs:1074`), otherwise reuses T+1's (`lib.rs:1042`). A split naming a shard that no longer exists in T+1 is skipped with a warning (`lib.rs:1049`). Which shard is proposed for splitting is decided at block production by `get_upcoming_shard_split` (`lib.rs:2643`) + `pick_shard_to_split` (`lib.rs:2687`), subject to the `min_epochs_between_resharding` cooldown (`can_reshard`, `lib.rs:1113`).
- **Strategy**: `AssignmentStrategy::select` (`mod.rs:170`) → `CarryOver` if layouts equal; `Fresh` if `StickyReshardingValidatorAssignment` is off; else `StickyResharding` (falling back to `Fresh` if sticky construction fails).
- **Assignment**: `assign_chunk_producers_to_shards` (`mod.rs:409`) errors `NotEnoughValidators` if `chunk_producers.len() < min_validators_per_shard` (`mod.rs:424`). When there are too few producers to fill every shard without repeats (`< min_validators_per_shard * num_shards`), it uses `assign_to_satisfy_shards` (repeats allowed, strategy ignored — `mod.rs:438`); otherwise `assign_to_balance_shards` (`mod.rs:446` → `mod.rs:287`) seeds from the strategy (`get_initial_chunk_producer_assignment`, `mod.rs:248`), places new validators onto the least-populated shards, then rebalances via random moves from the largest to smallest shard until balanced or the change limit is used. Sticky resharding raises the change limit to `max(limit, producers/shards)` (`needs_changes_limit_override`, `mod.rs:196`; applied at `mod.rs:431`) to top up freshly split children in one epoch.
- **Shuffle**: if `shuffle_shard_assignment_for_chunk_producers` is set, the whole `chunk_producers_settlement` is shuffled with the shard-assignment RNG (`validator_selection.rs:236`) — controlled by `ShuffleShardAssignments` (nightly only, see below).

### 10. Per-height producer/validator sampling

Given a finished `EpochInfo` (V3+), producers are sampled stake-weighted and deterministically from `rng_seed` + height (+ shard):
- **Block producer**: `sample_block_producer(height)` seeds `StakeWeightedIndex` with `hash(rng_seed || height)` (`epoch_info.rs:535`, seed at `epoch_info.rs:714`).
- **Chunk producer (canonical)**: `sample_chunk_producer(shard_layout, shard_id, height)` samples the per-shard `chunk_producers_sampler` from `hash(rng_seed || height || shard_id)` (`epoch_info.rs:560`, seed at `epoch_info.rs:721`).
- **Chunk producer excluding a blacklist** (used since v87): `sample_chunk_producer_excluding` (`epoch_info.rs:600`) filters the shard's settlement by the excluded `ValidatorId` set and then samples. With an empty exclusion set it delegates verbatim to `sample_chunk_producer` (`epoch_info.rs:607`). V1/V2 use `height % filtered.len()` (`sample_excluding_modulo`, `epoch_info.rs:644`); V3/V4/V5 build a **fresh `StakeWeightedIndex` renormalized over the survivors** and sample it with the same `chunk_produce_seed` (`sample_excluding_weighted`, `epoch_info.rs:659`). Returns `None` only when every eligible producer was excluded.
- **Chunk validators**: `sample_chunk_validators(height)` shuffles the `validator_mandates` with a ChaCha20 RNG seeded by `hash(rng_seed || height)` (`epoch_info.rs:679`, `epoch_info.rs:736`); empty for V1–V3. Results are cached per `(epoch_id, shard_id, height)` (`lib.rs:1459`).
Pre-V3 `EpochInfo` sampled block/chunk producers by round-robin (`height % settlement.len()`, `epoch_info.rs:537`/`epoch_info.rs:568`) rather than stake-weighted.

### 11. Early kickout: blacklist, seeding, and anchored producer lookup (stable since v87)

`EarlyKickout` (stable at 87) replaces "sample the chunk producer for height H on demand" with "read the producer that was pre-committed at H's **grandparent anchor**". The anchor is the chunk's grandparent block; the nominal offset is `CHUNK_GRANDPARENT_ANCHOR_HEIGHT_OFFSET = 2` (`adapter.rs:35`).

**11a. Blacklist math.** `compute_chunk_producer_blacklist` (`lib.rs:295`) walks the aggregator's `shard_tracker`. For each shard it takes the *distinct* producers in that shard's settlement (`lib.rs:310`) — endorsement-only entries are skipped so chunk validators neither become candidates nor skew the denominator (`lib.rs:313`). A producer is a candidate iff **both**:
- `missed >= EARLY_KICKOUT_MIN_MISSES` where `missed = expected - produced` (constant `100`, `lib.rs:71`), and
- `produced * 100 < expected * 80` — production ratio below 80% (`lib.rs:72`–`73`, compared in `u128` at `lib.rs:319`).

**Keep-one-least-bad safety valve** (`lib.rs:335`): if *every* distinct producer of a shard is a candidate, exactly one is kept eligible — the one with the highest `produced/expected`, compared by integer cross-multiplication, tie-broken by *fewer* `expected` and then by *lower* `ValidatorId` (`lib.rs:342`–`345`). The ordering is a deterministic total order precisely because `HashSet` iteration order is not consensus-safe. A 1-producer shard therefore ends up with an empty blacklist (`lib.rs:355`).

All four numbers are unchanged in 2.14.0: `EARLY_KICKOUT_MIN_MISSES = 100` (`lib.rs:71`), numerator `80` / denominator `100` (`lib.rs:72`–`73`), `EARLY_KICKOUT_EPOCH_GRACE_BLOCKS = 1000` (`lib.rs:76`), and the grandparent offset `2` (`adapter.rs:35`).

**11b. Basis, grace, and when the epoch walk runs.** The blacklist is a pure function of the anchor's **last-final block** (`SeedAnchor.final_hash` / `final_height`), which is header-derived and therefore identical on every node for a canonical anchor, and which keeps the walk off the growing non-final suffix during a finality stall. `chunk_producer_blacklist_at_anchor` (`lib.rs:2423`) resolves it in this exact order — **restructured in 2.14.0 (#16474)** so every "empty by rule" answer is returned *before* any epoch walk:

1. A genesis/default `final_hash` yields an empty blacklist (`lib.rs:2429`).
2. The basis epoch is read from `BlockInfo(final_hash).epoch_id()`, except when `final_hash` *is* the aggregator's sync point, where the aggregator's own `epoch_id` is used instead — after epoch sync that block may have no `BlockInfo` (`lib.rs:2434`). A basis in a different epoch than the anchor's own epoch returns empty (`lib.rs:2439`); this is the normal state for the first two anchors of an epoch at steady finality, and for longer while finality lags. (`ValidatorId` is an epoch-local index, so previous-epoch stats would blacklist whoever occupies those indices in the target epoch.)
3. `blocks_into_epoch = final_height − get_epoch_start_height(final_hash)` (`lib.rs:2445`). The epoch start comes from two `BlockInfo` reads — the basis block, then its `epoch_first_block` (`get_epoch_start_height`, `lib.rs:1649`) — **not** `DBCol::EpochStart`, because same-parent boundary siblings overwrite that shared row and its value would depend on fork processing order (#16139; the hazard is documented on `get_epoch_start_from_epoch_id`, `lib.rs:2167`). A missing `BlockInfo` here is an error, not grace.
4. `blocks_into_epoch < EARLY_KICKOUT_EPOCH_GRACE_BLOCKS` returns empty (`lib.rs:2447`).
5. Only now, and memoized per `final_hash` in a 128-entry LRU (`chunk_producer_blacklists`, `lib.rs:2450`), does it run `get_epoch_info_aggregator_upto_last(final_hash)` and `blacklist_for_epoch`.

`blacklist_for_epoch` (`lib.rs:377`) still repeats the epoch-match (`lib.rs:386`) and grace (`lib.rs:389`) checks, but they are now *defense in depth for direct callers* — in production `chunk_producer_blacklist_at_anchor` has already returned on both. The restructuring does not change any seeded row: in every case where the pre-2.14.0 order produced a blacklist, the new order produces the same one (§11j).

Steps 2 and 3 still read through `get_block_info` (`lib.rs:2434`, `lib.rs:1649`), i.e. they do insert into the `blocks_info` LRU — but they are at most three O(1) reads, and the block being recorded is the most-recently-used entry at that point, so they cannot evict it. The cache-neutrality requirement of §11j applies to the unbounded *walk*, not to these gates.

The memo key is complete: once step 2 has established that the basis is in the anchor's own epoch, `final_height`, `epoch_id`, `EpochInfo` and `ShardLayout` are all determined by `final_hash`, and the aggregate over `final_hash`'s ancestry is itself deterministic. In particular the boundary case is closed: anchors in epochs T and T+1 can share a last-final block, but the T+1 anchor's basis is then cross-epoch and step 2 returns empty *before* the memo is consulted, so a single `final_hash` key can only ever be reached from one epoch. The memo is cleared only by epoch sync (`init_after_epoch_sync`, `lib.rs:633`), which replaces the chain data the walks read. Asserted by `memoized_blacklist_matches_restarted_manager`, `memoized_blacklist_is_keyed_by_last_final_block` and `epoch_sync_clears_memoized_blacklists` (`chain/epoch-manager/src/tests/early_kickout.rs:1429`, `:1486`, `:1529`).

**11c. Seeding.** `seed_chunk_producers` (`lib.rs:2484`) is a no-op unless `EarlyKickout` is enabled **for the anchor's own epoch** (`lib.rs:2490`) — gating on the anchor's own epoch avoids writing dead rows for last-of-epoch anchors across an activation edge. It obtains the blacklist via the shared helper, not the adapter accessor, which would re-take the read lock and deadlock (`lib.rs:2495`); since 2.14.0 the helper hands back an `Arc<ChunkProducerBlacklist>` that the seeder borrows (`lib.rs:2500`) instead of an owned value. It emits the `EARLY_KICKOUT_BLACKLIST_SIZE` / `EARLY_KICKOUT_SAFETY_VALVE_FIRED` metrics (`lib.rs:2503`–`2522`; only here, never in the accessor, to avoid double counting), then `seed_chunk_producer_rows` (`lib.rs:2538`) samples each shard at `anchor.height + 2` via `sample_chunk_producer_excluding` (`lib.rs:2551`) and writes `(anchor_hash, shard_id) → ValidatorStake` with `set_chunk_producer` (`lib.rs:2596` → `core/store/src/adapter/epoch_store.rs:156`). A reassignment is counted only when the *plain* pick would itself have been blacklisted (`lib.rs:2576`–`2585`) — comparing `plain != sampled` would over-count, since the renormalized draw can legitimately move the pick.

**11d. Epoch sync.** The first block installed by epoch sync bypasses `record_block_info`, so `seed_chunk_producers_after_epoch_sync` (`adapter.rs:1225` → `seed_chunk_producers_for_first_block`, `lib.rs:2610`) seeds its rows in the same store update with an **empty** blacklist (first block of an epoch has no in-epoch stats, and the aggregator walk would fail because the block lives only in the pending update). The same path also writes the `EpochStart` row that `record_block_info` would have written (`chain/client/src/sync/epoch.rs:312`), which the grace check no longer reads but `get_validator_info`, `compare_epoch_id` and the epoch-sync-proof machinery still do (#16125).

**11e. Consensus read.** `get_chunk_producer_info_anchored` (`adapter.rs:594`, impl `adapter.rs:1093`) gates on the **chunk's** epoch protocol version (`adapter.rs:1106`). If the anchor exists and is in the *same* epoch as the chunk, it reads `DBCol::ChunkProducers` and hard-errors `EpochError::ChunkProducerNotInDB` on a miss (`adapter.rs:1121`; `core/primitives/src/errors.rs:1368`). If the feature is off, there is no anchor (genesis / genesis+1), or the anchor is in the *previous* epoch (the first ≤2 blocks of an epoch, where the blacklist is provably empty), it falls back to canonical sampling at `height_created` (`adapter.rs:1131`). `get_chunk_producer_info_from_prev_block` (`adapter.rs:608`) derives epoch, height and anchor from a **processed** parent block and delegates — this is what chunk production, chunk validation, chunk forwarding and signature verification call (`chain/chunks/src/shards_manager_actor.rs:506`, `shards_manager_actor.rs:2195`, `chain/chain/src/signature_verification.rs:56`, `chain/client/src/chunk_producer.rs:174`). A missing anchor block surfaces as `MissingBlock` (node ≥2 blocks behind).

**11f. Stats attribution.** `anchored_chunk_producers_for_aggregator` (`lib.rs:2339`) mirrors 11e for the kickout aggregator but is *lenient*: on a missing row or an account outside the epoch it falls back to canonical sampling at the anchor offset rather than erroring (`lib.rs:2386`, `lib.rs:2404`), because canonical sampling is exact wherever the blacklist is empty. It returns `None` (legacy sampler) when the feature is off, at genesis, when the anchor `BlockInfo` is missing, or when the anchor is cross-epoch (`lib.rs:2346`–`2359`). **Changed in 2.14.0 (#16474)**: it no longer re-reads the parent — the caller (`aggregate_epoch_info_upto`) passes the already-loaded `prev_block_info: Option<&BlockInfo>` (`lib.rs:2345`, call site `lib.rs:2308`), and the grandparent anchor is read with `peek_block_info` (`lib.rs:2356`). Neither change alters which producer is attributed.

**11g. Live blacklist accessor.** `get_chunk_producer_blacklist` (`adapter.rs:1135`) recomputes the blacklist for an anchor through the same `chunk_producer_blacklist_at_anchor` helper, so a live read always agrees with the stored row; since 2.14.0 it clones the map out of the memoized `Arc` (`adapter.rs:1164`).

**11h. Test-only thresholds.** `EARLY_KICKOUT_MIN_MISSES` and `EARLY_KICKOUT_EPOCH_GRACE_BLOCKS` are read through functions that, under `test_features`, consult a **thread-local** override installed by `set_early_kickout_thresholds_for_testing` (`lib.rs:172`) and restored by a `!Send` drop guard (`lib.rs:150`). Production builds inline the constants (`lib.rs:81`, `lib.rs:88`). The override is deliberately not reachable from any runtime/adversarial RPC. **Tightened in 2.14.0**: the guard must be installed *before any `EpochManager` is created*, and every thread sharing a manager must hold the same thresholds, because the new blacklist memo (11b) is keyed only by last-final-block hash and does not include them (`lib.rs:164`–`167`).

**11i. Storage lifecycle.** Rows are insert-only and garbage-collected together with their anchor: `gc_chunk_producers_for_block` (`chain/chain/src/garbage_collection.rs:535`) prefix-scans by anchor hash and is called from block-data cleanup (`garbage_collection.rs:753`, `garbage_collection.rs:1027`) and from the header-only sweep (`garbage_collection.rs:607`), so header hashes that never received a body do not orphan rows (#16023).

**11j. Cache discipline during the seed walk (#16474, new in 2.14.0, ungated).** Seeding runs *inside* `record_block_info_impl`, after `save_block_info` has put the new block's `BlockInfo` into the `blocks_info` LRU but **before** the store update is committed — so for the duration of the record, the cache holds the only readable copy of that `BlockInfo`. Up to 2.14.0 the blacklist's epoch walk read every ancestor through `get_block_info` (`lib.rs:2131`), which is `get_or_try_put`: each step *inserts and reorders*. `BLOCK_CACHE_SIZE` is 1000 (`lib.rs:67`), so a walk longer than ~1000 blocks evicted the uncommitted `BlockInfo` of the very block being recorded. `record_block_info` then returned `Ok`, but the chain's pre-commit `check_protocol_version` (`chain/chain/src/chain_update.rs:67`, called from `postprocess_block_only` at `chain/chain/src/chain.rs:1914` — guarded by `new_head.is_some()`, i.e. only when the block would become the new head, and two lines before `chain_update.commit()` at `chain.rs:1916`) starts with `is_next_block_epoch_start(block_hash)` → `get_block_info` (`chain/epoch-manager/src/adapter.rs:115`), which missed the cache, missed the store, and returned `EpochError::MissingBlock` (`core/store/src/adapter/epoch_store.rs:50`).

**Severity: local (and, if enough nodes hit it, network) liveness — not consensus divergence.** The epoch manager's `EpochStoreUpdateAdapter` is *merged into* the chain's `ChainStoreUpdate` rather than committed on its own (`chain/chain/src/chain_update.rs:270`), so the `?` on `check_protocol_version` drops the whole update: the block, its `BlockInfo`, its `ChunkProducers` rows and the epoch-info aggregator row are all unwritten. No node ever persisted or published a different value from any other node; the affected node simply could not accept the block, and re-processing it hit the same deterministic path. (The in-memory `self.epoch_info_aggregator` / `self.largest_final_height` advance is *not* rolled back, which is one reason the retry reproduces rather than recovers; it is derived state rebuilt from the store on restart.)

The walk could get that long even though the aggregator sync point is normally one block back: a *late fork sibling* recorded after the canonical block advances `self.epoch_info_aggregator` past the canonical block's own last-final block, so the canonical child's walk never meets the sync point and runs to the epoch start (`aggregate_epoch_info_upto` breaks only on the sync point or an epoch/genesis boundary, `lib.rs:2322`/`lib.rs:2273`).

The fix is four changes, all ungated:
1. **The walk peeks.** `aggregate_epoch_info_upto` and `anchored_chunk_producers_for_aggregator` read through `peek_block_info` (`lib.rs:2136`), which reads the LRU without inserting or reordering and otherwise falls back to the store, so no walk can evict or promote anything (asserted by `aggregator_walk_leaves_block_info_cache_alone`, `chain/epoch-manager/src/tests/early_kickout.rs:1354`). The walk also carries the parent's `BlockInfo` forward instead of re-fetching it (`lib.rs:2284`, `lib.rs:2330`).
2. **Empty-by-rule answers skip the walk entirely** (11b steps 2 and 4), so the common cases — the start-of-epoch grace window and a cross-epoch basis — do no walking at all (asserted by `seed_walk_skipped_during_in_grace_stall` and `seed_walk_skips_fork_basis_behind_sync_point`, `early_kickout.rs:1114`, `:1173`).
3. **Past-grace blacklists are memoized** per last-final-block hash in a 128-entry LRU (`CHUNK_PRODUCER_BLACKLIST_CACHE_SIZE`, `lib.rs:68`; field at `lib.rs:485`), so fork siblings that share a last final block walk the epoch once.
4. **The record re-marks its own block most-recently-used** after every fallible step (`lib.rs:1396`), belt-and-braces for any other pre-commit reader (asserted by `record_block_info_leaves_new_block_most_recently_used`, `early_kickout.rs:1388`).

**Seeded rows are unchanged.** The two gates moved ahead of the walk return exactly the values `blacklist_for_epoch` would have returned after it: the basis epoch id in step 2 is the same value `aggregate_epoch_info_upto` assigns to `aggregator.epoch_id` (from `BlockInfo(final_hash)`, or from the aggregator itself at the sync point), and `blocks_into_epoch` is computed identically. So wherever the old code produced a blacklist, the new code produces the same one, and the feature needed no protocol gate. The one *intentional* difference is error behavior, and it is strictly more permissive: a `BlockInfo` missing somewhere behind an in-grace or cross-epoch last-final block no longer fails the record, because those blacklists are empty by rule and the walk that would have tripped over the hole never runs (asserted by `seeder_recovers_from_hole_behind_in_grace_basis` / `..._cross_epoch_basis`, `early_kickout.rs:1731`, `:1752`; the same-epoch, past-grace case still propagates `MissingBlock` — `seeder_propagates_missing_block_info_on_same_epoch_basis`, `early_kickout.rs:1773`).

End-to-end regressions: `slow_test_withheld_block_mid_epoch` and `slow_test_withheld_block_at_epoch_boundary` (`test-loop-tests/src/tests/early_kickout_withheld_block.rs:152`, `:168`) withhold a block past both the grace window and the 1000-entry cache (`EPOCH_LENGTH = 1100`, fork offset 1040), deliver it after its canonical sibling, and assert every node stays on the canonical chain.

## Invariants & failure modes

- **Slashing is inactive.** `ValidatorKickoutReason::_UnusedSlashed` is variant 0 and deprecated (`types.rs:1256`); no code path produces a slash, and `CurrentEpochValidatorInfo::is_slashed` is hardcoded `false` (`lib.rs:1762`). Stake is only ever returned or lost via kickout/unstake, never confiscated.
- **Never kick out everyone (epoch boundary).** Enforced by the `all_kicked_out` guard that restores the top block producer (`lib.rs:843`).
- **Never blacklist every producer of a shard (early kickout).** The keep-one-least-bad valve (`lib.rs:335`) guarantees at least one eligible producer per non-empty shard; `seed_chunk_producer_rows` `debug_assert!`s that the excluding sampler returns `Some` for every shard with a non-empty settlement (`lib.rs:2562`).
- **Blacklist determinism is consensus-critical.** The stats basis is the anchor's *last-final* block (header-derived, `lib.rs:2495`); the epoch-start height comes from the `BlockInfo` walk, never from the fork-order-dependent `DBCol::EpochStart` row (`lib.rs:2445`); the least-bad tiebreak is a total order over `(ratio, -expected, validator_id)` (`lib.rs:342`). Violating any of these makes two honest nodes seed different rows and the reader hard-error. The 2.14.0 memo (`lib.rs:2450`) does not weaken this: it is keyed by that same last-final-block hash, and every other input is derived from it. Asserted by `memoized_blacklist_matches_restarted_manager` and `fork_seeded_rows_reflect_each_branch_blacklist` (`chain/epoch-manager/src/tests/early_kickout.rs:1429`, `:2657`).
- **An epoch walk must never evict an uncommitted `BlockInfo`** (new invariant in 2.14.0, #16474). Seeding runs inside `record_block_info_impl` while the new block's `BlockInfo` lives only in the `blocks_info` LRU, and the chain reads it back pre-commit through `check_protocol_version`. Every walk therefore reads through `peek_block_info` (`lib.rs:2136`), which neither inserts nor reorders, and the record re-marks its own block most-recently-used afterwards (`lib.rs:1396`). Asserted by `aggregator_walk_leaves_block_info_cache_alone` and `record_block_info_leaves_new_block_most_recently_used` (`early_kickout.rs:1354`, `:1388`), and end-to-end by `test-loop-tests/src/tests/early_kickout_withheld_block.rs:152`. Violating it is a **liveness** failure, not a safety one: the chain store update is dropped whole, so nothing divergent is written or published, but the node deterministically fails to accept the block and cannot advance its head past it (§11j).
- **Kickout stake is capped** at `validator_max_kickout_stake_perc` via `compute_exempted_kickout` (`lib.rs:651`).
- **Two-epoch staking lag** is structural: T+2's `EpochInfo` is computed at the end of T and stored under `EpochId(last_block_of_T)` (`lib.rs:1246`).
- **Proposals must be unique per account** — `debug_assert!` in `proposals_to_epoch_info` (`validator_selection.rs:179`); genesis must carry zero proposals — `assert_eq!` (`lib.rs:1291`).
- **Determinism of sampling**: all sampling is a pure function of `(rng_seed, height, shard_id)` (`epoch_info.rs:714`/`epoch_info.rs:721`/`epoch_info.rs:736`); shard-assignment randomness uses `EpochInfo::shard_assignment_rng` seeded from `rng_seed` (`epoch_info.rs:753`) so all honest nodes derive the identical settlement.
- **Cache/store consistency**: a failed `record_block_info` evicts the `blocks_info`/`epochs_info` entries it wrote (`lib.rs:1273`), and the re-record guard `has_block_info` asks the *store*, not the cache (`lib.rs:2123`), so a block whose update the caller dropped is always re-recorded rather than skipped. Note the guarantee is only that: a *successful* record whose caller then drops the update (the §11j failure) does leave a cached `BlockInfo` with nothing behind it in the store, which `get_block_info` will serve — the code comment on `has_block_info` states this trade-off explicitly. It costs duplicate work on the retry, not correctness, because recording is deterministic and the writes are insert-only.
- **Atomic seeding**: `ChunkProducers` rows are written into the *same* `EpochStoreUpdateAdapter` as the block's `BlockInfo` (`lib.rs:1343`/`lib.rs:1351`), so a block is never visible without its rows.
- **Everyone unstaked** → selection returns `ThresholdError`/`NotEnoughValidators`; handled by cloning prev `EpochInfo` and bumping height (`lib.rs:1232`), so the chain does not stall.
- **Too few chunk producers for a shard** → `assign_chunk_producers_to_shards` returns `NotEnoughValidators` (`mod.rs:424`), surfaced as `EpochError::NotEnoughValidators` (`validator_selection.rs:152`).
- **Missing chunk-producer row on the consensus path** → `EpochError::ChunkProducerNotInDB(anchor, shard_id)` (`adapter.rs:1121`). The stats path deliberately does not error, falling back to canonical sampling (`lib.rs:2380`).
- **`ProtocolVersionTooOld` bars re-entry** the following epoch (`validator_selection.rs:303`), preventing a validator that voted stale from immediately rejoining.
- **Balancing assertion**: `assign_to_balance_shards` asserts it never exceeds the hard change limit and never balances a shard with itself (`mod.rs:345`, `mod.rs:351`) — a panic here indicates a duplicate chunk producer in the prev assignment.
- **Transaction validity period ≤ 2 epochs** is asserted at construction for every epoch config, required by continuous epoch sync (`lib.rs:555`).

## Open questions

- The early-kickout constants (`EARLY_KICKOUT_MIN_MISSES = 100`, 80% production ratio, 1000-block grace) are hardcoded in `chain/epoch-manager/src/lib.rs:71`–`76` rather than living in `EpochConfig`. They are therefore **not** per-protocol-version tunable and cannot be changed by an epoch-config update — only by a binary release. Whether that is intentional (consensus simplicity) or a follow-up is not determinable from the code.
- `get_chunk_producer_info_anchored` reads `DBCol::ChunkProducers` on every lookup with no cache; the in-code TODO (`adapter.rs:1103`) flags this as a known performance gap. The production impact at mainnet chunk rates is not established here.
- `seed_chunk_producers` writes a row for a last-of-epoch anchor whose grandchild falls in the next epoch. The code argues this row is not read on any honest path but is reachable by the best-effort V2 partial-witness resolver with a sender-claimed epoch (`lib.rs:2470`). Whether that non-consensus path can be driven to a useful mis-resolution is a question for [stateless-validation](stateless-validation.md), not answerable from this component alone.
- #16474 removes the walk from the in-grace and cross-epoch paths, so a seed on those paths no longer
  needs the ancestry behind the last-final block. The commit describes this as the one behavioral
  difference from the old code. It is a strict relaxation of an error path, so no stored row changes,
  but whether any reachable state actually had such a hole outside epoch sync is not determinable from
  code alone — the tests construct it synthetically (`early_kickout.rs:1731`, `:1752`).
- Two DB-version bumps land in this release and only one belongs to this component: `DBCol::ChunkProducers` is the 49→50 bump and needs no data migration (`nearcore/src/migrations.rs:79` is `49 => Ok(())`), while 50→51 is the unrelated versioned-`StoredLightClientBlock` migration (`nearcore/src/migrations.rs:80`). The tree's `DB_VERSION` is therefore **51** (`core/store/src/db/metadata.rs:5`) even though the column arrived at 50.
