# Sharding & chunk lifecycle

> Protocol version: 87 (stable) · Release: 2.14.0-rc.1 · Derived from commit: 233252e · Generated: 2026-09-14
> Primary crates/files: `core/primitives/src/shard_layout/`, `core/primitives/src/sharding.rs`, `core/primitives/src/reed_solomon.rs`, `chain/client/src/chunk_producer.rs`, `chain/chunks/src/{shards_manager_actor,logic,chunk_cache}.rs`, `chain/chain/src/signature_verification.rs`, `chain/chain/src/resharding/`, `chain/epoch-manager/src/{lib,adapter,shard_assignment,shard_tracker}.rs`

## Role

NEAR partitions account state across **shards**; each block carries one **chunk** per shard. This component covers the chunk lifecycle: how `ShardLayout` maps accounts to shards, how a chunk producer builds a chunk for its assigned shard and Reed–Solomon-encodes it into parts, how those parts and receipt proofs are distributed and reconstructed via the `ShardsManager`, what a *missing* chunk means, and **dynamic resharding** (splitting a shard at an epoch boundary). It sits downstream of [epoch management](epoch-validators-staking.md) (which assigns chunk producers and part owners), feeds [stateless validation](stateless-validation.md) (chunk *validation* via witnesses is out of scope here) and [chain & block processing](chain-block-processing.md), and the state transition a chunk applies belongs to [runtime execution](runtime-execution.md). Resharding storage mechanics (trie/flat-storage migration, memtrie preload) live in [state & storage](state-storage.md).

## Key data structures

- **`ShardLayout`** — `core/primitives/src/shard_layout/mod.rs:64` — versioned enum `V0|V1|V2|V3` holding everything needed to assign accounts to shards plus parent/child split history. V0 hashes account ids; V1/V2/V3 use sorted account-id boundaries. V2 introduced non-contiguous, stable `ShardId`s distinct from `ShardIndex`; V3 (dynamic resharding, `:68`) additionally stores cumulative split history + ancestor maps (`ancestor_uids`, `:449`). `single_shard()` (`:94`) builds a V2 single-shard layout.
- **`ShardUId`** — `core/primitives/src/shard_layout/mod.rs:479` — `{version: u32, shard_id: u32}`. Globally unique across layouts (because it carries the layout `version`), used as the DB/storage key for shard-indexed state; `ShardId` alone is the protocol-facing ordinal exposed in chunk headers. `to_bytes()` (`:497`) gives the 8-byte storage prefix (little-endian `version` then `shard_id`).
- **`ShardChunkHeader`** — `core/primitives/src/sharding.rs:396` — enum `V1|V2|V3`; production builds `V3` (`ShardChunkHeaderV3`, `:238`). Carries `prev_state_root`, `encoded_merkle_root`, `encoded_length`, `height_created`, `height_included`, `shard_id`, gas/balance, `prev_outgoing_receipts_root`, `tx_root`, congestion info, bandwidth requests, and (via the V5 inner) `proposed_split`.
- **`ShardChunkHeaderInner`** — `core/primitives/src/sharding/shard_chunk_header_inner.rs:18` — versioned; the V5 inner (`:23`) adds `proposed_split: Option<TrieSplit>` for dynamic resharding, and the V6 inner (`:24`) is the spice tx-only variant. Accessors gate on the version.
- **`EncodedShardChunkBody`** — `core/primitives/src/sharding.rs:1281` — `parts: Vec<Option<Box<[u8]>>>`, one slot per total part. `get_merkle_hash_and_paths()` (`:1298`) merklizes the parts into `encoded_merkle_root` + per-part `MerklePath`.
- **`TransactionReceipt`** — `core/primitives/src/sharding.rs:1309` — `(Vec<SignedTransaction>, Vec<Receipt>)`; this is the payload that is Reed–Solomon-encoded into the parts.
- **`ShardChunkWithEncoding`** — `core/primitives/src/sharding.rs:1519` — pairs the decoded `ShardChunk` with its `EncodedShardChunk` so encode/decode is done once and the two are guaranteed consistent.
- **`PartialEncodedChunk`** — `core/primitives/src/sharding.rs:790` — the over-the-wire unit: a header plus a subset of parts (each with its merkle proof) plus the receipt proofs the recipient needs. Enum `V1|V2|V3`. **New at 2.14:** `PartialEncodedChunkV3` (`:947`, discriminant `2`) additionally carries a **grandparent anchor** — `prev_prev_block_hash: CryptoHash` (`CryptoHash::default()` when the parent is genesis) and `epoch_id: EpochId`. Both fields are attacker-controlled and must be cross-checked before use (doc comments at `:897`, `:906`). V3 is emitted only under `ProtocolFeature::EarlyKickout` (`chain/chunks/src/logic.rs:119`).
- **`ReceiptProof` / `ShardProof`** — `core/primitives/src/sharding.rs` — a set of receipts plus the merkle path proving them against a chunk's `prev_outgoing_receipts_root`; `ShardProof` labels the proof with `from_shard_id`/`to_shard_id`. Neither label is covered by a merkle root, so both must be checked explicitly by the consumer (see Invariants).
- **`ChunkExtra` (V5)** — `core/primitives/src/types.rs:816` (`ChunkExtraV5`, `:882`) — per-(block,shard) post-application summary (state root, gas, congestion info, …); V5 adds `proposed_split` (`:900`, accessor `:1067`), the authoritative locally-computed split proposal used to validate incoming chunk headers.
- **`TrieSplit`** — `core/primitives/src/trie_split.rs:20` — result of the split search: `boundary_account: AccountId`, `left_memory`, `right_memory`; `total_memory()` (`:54`) returns their saturating sum. Embedded in chunk headers and `ChunkExtra`.
- **`ReshardingSplitShardParams`** — `chain/chain/src/resharding/event_type.rs:19` — `{parent_shard, left_child_shard, right_child_shard, boundary_account, resharding_block}`; the deduced split event for the storage layer.
- **`AssignmentStrategy`** — `chain/epoch-manager/src/shard_assignment/mod.rs:140` — `CarryOver | Fresh | StickyResharding{shard_idx_mapping}`; chooses how chunk-producer→shard assignment carries across an epoch boundary.
- **`EncodedChunksCache`** — `chain/chunks/src/chunk_cache.rs:62` — per-`ChunkHash` accumulation of parts/receipts, bounded by `[largest_seen_height − height_horizon, largest_seen_height + MAX_HEIGHTS_AHEAD]` (`:289`–`:297`, `MAX_HEIGHTS_AHEAD = 5` at `:29`). `height_horizon` comes from config; the default dropped from 128 to **2** heights (`core/chain-configs/src/client_config.rs:638` — `default_chunks_cache_height_horizon`). The old `pub const DEFAULT_CHUNKS_CACHE_HEIGHT_HORIZON = 128` (2.13 `chain/chunks/src/chunk_cache.rs:30`, re-exported from `chain/chunks/src/lib.rs`) is gone at HEAD; the config function is the only source (#16163).

## Behavior

### Account → shard mapping

1. `ShardLayout::account_id_to_shard_id` (`core/primitives/src/shard_layout/mod.rs:203`) dispatches by version. For V2/V3 the boundary accounts are sorted; the shard index is `boundary_accounts.partition_point(|x| x <= account_id)` and the result is `shard_ids[idx]` (`core/primitives/src/shard_layout/v2.rs:265`). V0 hashes the account id instead.
2. `account_id_to_shard_uid` (`:214`) wraps the id with the layout `version` to get the storage-unique `ShardUId`. Note: receipts must use `Receipt::receiver_shard`, not this function (doc comment `:202`).
3. `get_shard_index` (`:374`) maps `ShardId`→array index (identity for V0/V1, lookup for V2/V3). Parent/child relations: `get_children_shards_ids` (`:241`), `try_get_parent_shard_id` (`:253`); a shard has at most one parent.
4. **Descendant test** (`chain/epoch-manager/src/shard_tracker.rs:571` — `check_if_descendant_of_tracked_shard_impl`): a shard is a descendant of **itself** — the self-match is tested first, before either branch (`:580`–`:584`). Under a V3 layout the ancestor set is read directly from the layout (`ancestor_uids`, `:588`); otherwise the code walks consecutive historical layouts (`:595`–`:611`). Before 2.14 the self-match lived only in the walking branch, so a node tracking a shard by its own `ShardUId` silently stopped tracking it once the layout became V3 (fixed by #16184).

### Chunk production

`ChunkProducer::produce_chunk` (`chain/client/src/chunk_producer.rs:161`):

1. Confirm the local signer is the assigned chunk producer for `(prev_block, shard_id)` via `get_chunk_producer_info_from_prev_block` (`:174`); return `None` otherwise. (This replaced the former `get_chunk_producer_info_db`; it derives the chunk's epoch, height and grandparent anchor from the parent block and resolves through the anchored lookup — `chain/epoch-manager/src/adapter.rs:608`.)
2. `produce_chunk_internal` (`:259`): if the next block starts a new epoch and the prev block is not caught up, skip with an error (`:275`–`:288`).
3. Load the prev block's `ChunkExtra` for this shard (`:300`) — supplies the *prev* state root, outcome root, gas used/limit, balance burnt, validator proposals, congestion info, bandwidth requests, and `proposed_split` (`:412`).
4. Build the ordered transaction list from the sharded pool via `prepare_transactions` (`:472`), running runtime tx validation against the prev state. A background early-preparation job (`start_prepare_transactions_job`, `:687`) may have cached the result (`get_cached_prepared_transactions`, `:770`, consulted at `:304`).
5. Compute `tx_root` by merklizing the signed txs (`:342`) and fetch the shard's outgoing receipts produced since the prev chunk (`get_outgoing_receipts_for_shard_from_store`, `:354`); `calculate_receipts_root` (`:238`) groups receipts by receiver shard and merklizes the group hashes.
6. `ShardChunkWithEncoding::new` (`core/primitives/src/sharding.rs:1526`) assembles `TransactionReceipt(signed_txs, prev_outgoing_receipts)`, Reed–Solomon-encodes it (next section), merklizes the parts into `encoded_merkle_root` + merkle paths, and signs a `ShardChunkHeaderV3`. The `proposed_split` from the prev `ChunkExtra` is copied verbatim into the new header (`chunk_producer.rs:412`) — the producer does **not** recompute it. (A separate spice-only path `new_for_spice` (`:1586`) builds a tx-only chunk; inactive at v87.)
7. The producer's own `PartialEncodedChunk` is built by `create_partial_chunk` (`chain/chunks/src/logic.rs:170`), which computes the receipt proofs and then calls `make_partial_encoded_chunk` (`:100`) to choose the wire envelope: under `EarlyKickout` a **V3** carrying `grandparent_anchor(prev_block_hash)` and the chunk's `epoch_id` (`:119`–`:128`), otherwise a V2 (`:130`). A V1 header short-circuits to V1 (`:106`).

### Reed–Solomon encoding into parts

`reed_solomon_encode` (`core/primitives/src/reed_solomon.rs:18`):

1. Borsh-serialize the `TransactionReceipt`; `encoded_length` = byte length.
2. `part_length = encoded_length.div_ceil(data_parts)` (`reed_solomon_part_length`, `:76`); pad bytes to `data_parts * part_length` with zeros.
3. Split into `data_parts` data shards, append `parity_parts` empty slots, then `rs.reconstruct` fills the parity shards. The encoder is built once per `ChunkProducer` with `data_parts = num_data_parts` and `parity_parts = num_total_parts − num_data_parts` (`chain/client/src/chunk_producer.rs:130`–`:131`, stored at `:153`).
4. The part counts are epoch-config derived, not protocol constants: `num_total_parts` (`chain/epoch-manager/src/adapter.rs:968`) is the `num_block_producer_seats` of the epoch config resolved at the **genesis protocol version**, floored at 2 (`if seats > 1 { seats as usize } else { 2 }`), and `num_data_parts = if total <= 3 { 1 } else { (total − 1) / 3 }` (`:80`). So the chunk is reconstructible from roughly one third of the parts. Both are *binary-local* (read from the local epoch-config store), not values committed on chain.

The separate `ReedSolomonEncoder` wrapper (`reed_solomon.rs:108`) — used by state-witness distribution, *not* by `ChunkProducer`, which holds a bare `ReedSolomon` — handles the degenerate single-part case (`total_parts <= 1`) by storing no RS instance and treating the whole payload as one part (`encode` `:132`, `decode` `:146`).

### Part assignment & distribution

`distribute_encoded_chunk` (`chain/chunks/src/shards_manager_actor.rs:2273`):

1. Recover the grandparent anchor from the producer's own partial chunk (`:2294`) so every outgoing message can carry it.
2. For each `part_ord` in `0..num_total_parts`, ask the epoch manager `get_part_owner(epoch_id, part_ord)` and group part ords by owner account (`:2297`–`:2303`). Part ownership is an epoch-level round-robin over the block-producer settlement (`adapter.rs:86`), not per-shard.
3. Add every **next-epoch** block producer to the recipient map (even with no parts) because they begin tracking shards a full epoch early and need the receipt proofs (`:2307`–`:2313`).
4. Build receipt proofs (`make_outgoing_receipts_proofs`, `logic.rs:78`): the outgoing receipts are grouped per target shard and merklized; each recipient gets only the proofs for shards it cares about this-or-next epoch (`:2324`–`:2336`).
5. Send a `PartialEncodedChunkMessage` (the recipient's part ords + relevant receipt proofs + header + merkle paths + anchor) to every recipient except self (`create_partial_encoded_chunk_with_arc_receipts`, `core/primitives/src/sharding.rs:1463`; send at `:2347`–`:2366`).
6. Merge the producer's own parts/receipts into `encoded_chunks` and mark the chunk for inclusion (`:2369`–`:2371`).

### Receiving, forwarding, reconstruction

A node obtains parts three ways (module doc, `shards_manager_actor.rs`): a `PartialEncodedChunkResponse` to its own request; a `PartialEncodedChunk` pushed by the producer to part owners; or a `PartialEncodedChunkForward` from a part owner to shard-trackers. The last two are validator→validator only.

- **Requesting** — `request_partial_encoded_chunk` (`:476`): picks a *shard-representative target* (the chunk producer, or a random shard-tracking block producer when requesting own parts / from archival / from self) (`:535`–`:541`). For each missing part: if the node tracks the shard (`request_full`, `:501`) or owns the part it requests it; own parts are fetched from the representative target, others from the part owner (`:544`–`:571`). A `MissingBlock`/`ChunkProducerSelectionError` from producer resolution is swallowed into `None` rather than propagated (`:509`–`:514`).
- **Arrival gate** — `process_partial_encoded_chunk` (`:1684`) runs, in order: 1.a known/poisoned-entry short-circuit (`:1705`); 1.b height horizon + un-requested duplicate-`(height, shard)` rejection (`:1719`); 1.c preliminary header validation (`:1747`); 1.d part-count and per-part validation (`:1777`); 1.e receipt-proof validation (`:1793`). Only then are parts merged into the cache (`:1812`).
- **Preliminary validation now verifies the signature** — `validate_chunk_header_preliminary` (`:1462`) resolves `epoch_id` through a three-layer fallback (processed prev block → the request's `ancestor_hash` → chain head, with `epoch_id_confirmed = false` in the last case, `:1471`–`:1490`), checks `shard_id` and header version (`:1503`–`:1504`), and then verifies the producer signature **at arrival**:
  - Under `EarlyKickout` (`:1510`): the message must carry an anchor, else `InvalidChunkHeader` (`:1511`–`:1513`) — i.e. a V2 envelope is rejected on an `EarlyKickout` epoch. The signed `epoch_id` must equal the parent-implied epoch when confirmed (`:1515`), else must be one of `possible_epochs_of_height_around_tip` (`:1519`–`:1526`). The producer is then resolved by `resolve_and_verify_anchored_producer` (`:1532`) and the signature checked (`:1540`–`:1542`).
  - Otherwise: epoch-based resolution via `verify_chunk_header_signature` (`:1546`, helper at `:1552`).
  When `epoch_id_confirmed` is false, the shard/version checks and the `EarlyKickout` epoch checks are remapped to `DBNotFoundErr` (`err_mapper`, `:1494`–`:1501`) so the message is retried instead of blamed on the sender. Two failures are *not* routed through `err_mapper` and propagate as-is: errors from `resolve_and_verify_anchored_producer` (`:1532`–`:1539`, which raises its own `DBNotFoundErr` when the parent/anchor is unknown) and `Error::InvalidChunkSignature` on a bad signature (`:1541`). The net effect (#16081) is that an unauthenticated header can no longer occupy the `(height, shard)` cache/dedup slot of the real chunk. Note the in-source comments at `:1747`–`:1748` and `:1926`–`:1928` still claim the signature is deferred to `validate_chunk_header_full`; they are stale.
- **Anchored key cross-check** — `verify_anchored_chunk_key` (`chain/chain/src/signature_verification.rs:87`): if the parent block is processed, the signed `(epoch_id, height_created, prev_prev_block_hash)` must match the parent exactly (`:96`–`:116`). If the parent is absent but the anchor is real, `height_created` must equal `anchor.height + CHUNK_GRANDPARENT_ANCHOR_HEIGHT_OFFSET` (= 2, `chain/epoch-manager/src/adapter.rs:35`); below is rejected as invalid, above is *deferred* with `DBNotFoundErr` (`:127`–`:139`). With a default (genesis) anchor only genesis and genesis+1 are accepted (`:140`–`:153`). `resolve_and_verify_anchored_producer` (`:190`) resolves the producer from the anchor's `DBCol::ChunkProducers` row first and then applies the cross-check.
- **Forwarding** — on receiving an *owned* part, `send_partial_encoded_chunk_to_chunk_trackers` (`:2142`) forwards it to block producers of this-or-next epoch that care about the shard (`:2197`–`:2213`), plus the **next height's** chunk producer, resolved through `get_chunk_producer_info_anchored` with the parent as anchor when the parent is processed and `None` (static sampler) otherwise (`:2192`–`:2195`, call sites `:1828`/`:1843`). `need_part` (`logic.rs:29`) and `need_receipt` (`logic.rs:20`) decide what a node must retain.
- **Forward messages** — `process_partial_encoded_chunk_forward` (`:1394`) drops forwards outside the cache horizon *before* doing any work (`:1399`–`:1404`), then validates hash, part count, per-part merkle proofs and the producer signature (`validate_partial_encoded_chunk_forward`, `:1305`). Forwards for an unknown chunk hash, or whose prev block is not yet processed, are parked in `chunk_forwards_cache` (`:1417`, `:1426`), an LRU of `CHUNK_FORWARD_CACHE_SIZE = 10` entries (`:154`) — reduced from 1000 in 2.14 to bound worst-case memory of unverified data. Parked parts are replayed by `insert_header_if_not_exists_and_process_cached_chunk_forwards` (`:1616`).
- **Full validation is still deferred** — `validate_chunk_header_full` (`:1571`) re-verifies the signature via the hash-based producer lookup once the prev block is processed, inside `try_process_chunk_parts_and_receipts` (`:1926`–`:1953`); failure removes the cache entry and the pending request.
- **Reconstruction** — `try_process_chunk_parts_and_receipts` (`:1903`): once `entry.parts.len() >= num_data_parts` the chunk `can_reconstruct` (`:1968`). If the node does **not** track the shard but has the parts/receipts it owns, it completes the chunk without decoding (`:2003`–`:2017`). Otherwise it fills an `EncodedShardChunk::from_header` with the gathered parts (`:2022`–`:2030`), asserts ≥`num_data_parts` present (`:2032`), and decodes; `decode_chunk` (`sharding.rs:1487`) reconstructs parts up to `encoded_length` and borsh-deserializes the `TransactionReceipt`. The full `ShardChunk` is persisted only if the node tracks the shard (`:2042`–`:2046`). A decode failure poisons the cache entry, drops the request, and reports `DecodedChunk::Invalid` (`:2049`–`:2083`) — the partial chunk handed to the client is rebuilt through `make_partial_encoded_chunk` so it keeps the correct envelope version (`:2068`).
- **Invalid chunks are no longer persisted pre-spice** — `Client::on_chunk_completed` (`chain/client/src/client.rs:1612`): on `DecodedChunk::Invalid`, the pre-spice path returns immediately (`:1642`–`:1645`) *before* `save_invalid_chunk`, because rows in `DBCol::InvalidChunks` written that way were not garbage-collected (#16164). Only the spice path persists the invalid chunk as evidence (`:1647`).

### Missing / skipped chunks

A chunk header's `height_included` is set to the block height that actually included it; `is_new_chunk(block_height)` is true iff `height_included == block_height` (`core/primitives/src/sharding.rs:470`). When a chunk producer fails to produce (or a chunk is not received in time), the block carries the **previous** chunk header for that shard with an unchanged `height_included`, i.e. no new chunk — the shard's state is not advanced that height. Block processing and runtime treat such a shard as applying an empty/implicit transition (`is_new_chunk: false`, `chain/chain/src/chain_update.rs:632`; see [chain & block processing](chain-block-processing.md), [runtime execution](runtime-execution.md)).

Chunks are indexed for GC by their **creation** height, not their inclusion height: `DBCol::ChunkHashesByHeight` is keyed by `chunk.height_created()` and the two differ whenever a chunk is created at one height and included later (`core/store/src/columns.rs:214` — `ChunkHashesByHeight` (doc comment `:210`–`:213`); doc corrected by #16202).

### Dynamic resharding (split at epoch boundary)

Gated by `ProtocolFeature::DynamicResharding` (active at v85+, see below). Active only when the epoch config's `shard_layout_config` is `Dynamic` (`chain/epoch-manager/src/lib.rs:2629`–`:2631`). Pipeline, two-epoch delayed:

1. **Propose (chunk application, epoch N near the end)** — `compute_proposed_split` (`chain/chain/src/runtime/mod.rs:593`): returns `None` unless the feature is on (`:603`), a dynamic config exists (`:607`), the next block *could* be the last in the epoch (`is_next_block_possibly_last_in_epoch`, `:611`), and the cooldown has elapsed (`can_reshard`, `:615`; implementation `chain/epoch-manager/src/lib.rs:1104`). Otherwise it runs `check_dynamic_resharding` (`:1802`) which applies, in priority order: max-shard-count veto (`:1818`), force-split list (`:1822`), block-split list (`:1825`), then `total_mem_usage ≥ memory_usage_threshold` with both children ≥ `min_child_memory_usage` (`:1829`–`:1838`); on success `find_trie_split` (`core/store/src/trie/split.rs`, see [state-storage](state-storage.md)) finds the boundary account. A `FindSplitError` other than a storage error is logged, counted in `DYNAMIC_RESHARDING_FIND_SPLIT_ERRORS` and treated as "no split" (`:623`–`:629`). The result is stored in `ChunkExtra.proposed_split` (`:289`, `:435`), published to metrics via `set_proposed_split_metrics` (`:301`, defined `chain/chain/src/runtime/metrics.rs:221`), and copied into the next chunk header's V5 inner `proposed_split`.
2. **Select (last block of epoch N)** — `get_upcoming_shard_split` (`chain/epoch-manager/src/lib.rs:2621`): returns `None` for a static layout (`:2629`) or a failed cooldown (`:2635`–`:2639`); collects `proposed_split` from all chunk headers (`:2642`–`:2647`) and `pick_shard_to_split` (`:2665`) chooses force-split shards first, else the highest `(total_memory, shard_id)` (the tuple makes ties deterministic, `:2682`). The chosen `(ShardId, AccountId)` is embedded in the block header.
3. **Derive (epoch finalization)** — `next_next_shard_layout` (`lib.rs:1006`): static fallback if the N+2 config is static (`:1021`); else if the current epoch has no dynamic config, carry the N+1 layout forward (`:1027`); else if `block_info.shard_split()` is set (`:1033`), `next_shard_layout.derive_v3(boundary_account, …)` (`:1066`, definition `core/primitives/src/shard_layout/mod.rs:288`) builds the new V3 layout (allocating two new shard ids), stored for epoch **N+2**. A selected shard that no longer exists in the next layout is skipped with a warning rather than an error (`:1038`–`:1048`). The schedule is exported as `DYNAMIC_RESHARDING_SCHEDULED_EPOCH_HEIGHT` (`chain/epoch-manager/src/metrics.rs:21`), set best-effort so a metrics failure cannot break derivation (`lib.rs:1057`–`:1064`).
4. **Execute (boundary block, storage layer)** — `ReshardingManager::start_resharding` (`chain/chain/src/resharding/manager.rs:47`) fires when `is_next_block_epoch_start` and the layout actually changes (`:66`–`:75`); `ReshardingEventType::from_shard_layout` (`event_type.rs:48`) deduces the single `SplitShard` event (erroring on two simultaneous splits, `:79`); `split_shard` / `process_memtrie_resharding_storage_update` (`manager.rs:107`, `:162`) retain the parent trie into left/right children, derive child congestion info (`:223`–`:236`, `get_child_congestion_info` `:297`), and atomically commit the `ShardUId` mapping + child `ChunkExtra` + trie nodes (`:190`–`:196`). Memtrie preload and flat-storage split are in [state-storage](state-storage.md). Old and new shards coexist: epoch N+1 nodes still run the old layout while preparing the children; the new layout takes effect at the N+1→N+2 boundary.
5. **Validator-side agreement on the boundary block** — the producer resolves both parent and child shard layouts from the **boundary block** (last block of epoch N, `manager.rs:224`/`:228`). Stateless validation now does the same, resolving from `boundary_block_hash` rather than the witness's main-transition block (`chain/chain/src/stateless_validation/chunk_validation.rs:727`, `:731`). Before this fix (#16068) a shard that produced no chunk anywhere in epoch N resolved to the *old* layout on the validator side, so the child's new shard id was absent and every validator deterministically rejected the child's first chunk, permanently halting the resharded shards. Validator-side only: no protocol gate, no committed state change.
6. **Genesis** — genesis may now declare a **dynamic** shard layout (#16148). `EpochManager::init_genesis_epoch_info` only demands a static layout from the epoch config when `DynamicResharding` is *not* enabled at the genesis protocol version (`chain/epoch-manager/src/genesis.rs:68`–`:76`); otherwise the layout comes from `AllEpochConfig::genesis_shard_layout()` (`core/primitives/src/epoch_manager.rs:364`), which prefers the epoch config's static layout and falls back to the genesis-declared one. This is what lets a forknet start from a mainnet state that is already on a V3 layout. See [genesis & configuration](genesis-configuration.md).

### Validator assignment across resharding

`AssignmentStrategy::select` (`chain/epoch-manager/src/shard_assignment/mod.rs:170`): `CarryOver` when layouts are equal (`:176`); `Fresh` when `StickyReshardingValidatorAssignment` is off (`:178`) or sticky construction fails (`:187`); else `StickyResharding` (`:155`), which preserves assignment by `ShardId` and distributes a split parent's producers across its children via greedy stake-balanced bin-packing. `needs_changes_limit_override` (`:196`) raises the per-epoch reassignment limit only for `StickyResharding` (`:199`) so freshly split children reach target population in one epoch. Without the feature a layout change reassigns every chunk producer by `ShardIndex`, forcing extra state sync.

## Interactions

- **Consumes** from [epoch management](epoch-validators-staking.md): chunk-producer assignment (`get_chunk_producer_info_from_prev_block`, `get_chunk_producer_info_anchored`, the `DBCol::ChunkProducers` column), part owners (`get_part_owner`), shard layout (`get_shard_layout`), and the resharding select/derive hooks.
- **Consumes** the prev `ChunkExtra` (post-application summary) from [runtime execution](runtime-execution.md) / [state & storage](state-storage.md); transaction pool from the client.
- **Produces** chunk headers consumed by [chain & block processing](chain-block-processing.md) (block assembly, `height_included`) and reconstructed `ShardChunk`s applied by [runtime execution](runtime-execution.md).
- **Parts and receipt proofs** move over [networking / P2P](networking-p2p.md) as `PartialEncodedChunk{,Forward,Request,Response}`; in 2.14 each of these network messages carries a receive permit from the incoming-memory semaphore, threaded through the `ShardsManager` request enum (`shards_manager_actor.rs:2464`, `:2486`, `:2500`, `:2517`).
- **Receipt proofs** are also re-served during state sync; the `from_shard_id` binding there is enforced in `chain/chain/src/state_sync/adapter.rs:503`–`:520` — see [sync](sync.md).
- **Resharding** triggers trie/flat-storage migration in [state & storage](state-storage.md); the produced layout feeds back into epoch management.
- Chunk *validation* (witnesses, `proposed_split` forgery checks, the boundary-block layout resolution) is in [stateless validation](stateless-validation.md); enforcement sites cited below.
- **RPC views**: `ChunkHeaderView.proposed_split` is a `Option<Option<TrieSplit>>` where absent means a V4-or-earlier inner and explicit `null` means V5 (`core/primitives/src/views.rs:1157`). Deserialization uses `serde_with::rust::double_option` so an explicit `null` round-trips as `Some(None)`; without it a V5 header decoded as V4 and the reconstructed chunk hash changed (#16405).

## Invariants & failure modes

- **A shard has at most one parent** across a layout change; `from_shard_layout` errors `"can't perform two reshardings at the same time!"` if two shards each have two children (`chain/chain/src/resharding/event_type.rs:79`).
- **A shard is a descendant of itself.** `check_if_descendant_of_tracked_shard_impl` matches the shard's own `ShardUId` before consulting ancestors, in both the V3 and the layout-walk branch (`chain/epoch-manager/src/shard_tracker.rs:580`).
- **`proposed_split` cannot be forged**: `validate_chunk_with_chunk_extra_and_receipts_root` (`chain/chain/src/validate.rs:134`) compares `chunk_header.proposed_split()` against the locally recomputed `prev_chunk_extra.proposed_split()`, returning `Error::InvalidChunkHeaderShardSplit` on mismatch (`:179`).
- **`shard_split` cannot be forged**: `validate_block_shard_split` (`validate.rs:194`) recomputes the block header's split via `get_upcoming_shard_split` and returns `Error::InvalidBlockHeaderShardSplit` on mismatch (`:219`).
- **A part must fit the chunk-size bound**: `validate_part` rejects `part.part.len() > reed_solomon_part_length(MAX_CHUNK_SIZE_BYTES, num_data_parts)` with `Error::InvalidChunkPartSize` (`shards_manager_actor.rs:1287`–`:1290`), where `MAX_CHUNK_SIZE_BYTES = 20 MiB` (`:161`). This is a node-local resource bound sized to fit ~4 MiB of transactions plus ~4.5 MiB of outgoing receipts, not a consensus rule.
- **Part ord must be in range and its merkle path must match the index**: out-of-range → `Error::InvalidChunkPartId` (`:1284`); `verify_path_with_index` ties the path shape to `part_ord` (`:1292`), failing with `Error::InvalidMerkleProof`.
- **A message may not carry more parts than exist**: `Error::TooManyChunkParts` both on the direct path (`:1780`) and on forwards (`:1319`).
- **`ReceiptProof.from_shard_id` must equal the header's shard**: the label is not covered by any merkle root, so `process_partial_encoded_chunk` checks it explicitly before the root check (`:1802`–`:1806`), returning `Error::ChainError(InvalidReceiptsProof)` (#16136). The same class of gap was closed on the state-sync ingest path by requiring `verify_path_with_index` at the labelled index *and* that the index name a chunk the block actually included (`chain/chain/src/state_sync/adapter.rs:507`–`:518`, #16379) — see [sync](sync.md).
- **A chunk header is authenticated before it is cached**: preliminary validation verifies the producer signature (`shards_manager_actor.rs:1510`–`:1545`), so a forged header cannot claim the `(height_created, shard_id)` dedup slot of the real chunk. Unconfirmed-epoch failures are downgraded to `DBNotFoundErr` and retried rather than treated as misbehavior (`:1494`).
- **The grandparent anchor pins exactly one chunk key per shard**: `height_created` must equal `anchor.height + 2` when the parent is missing; a lower height is `InvalidPartialChunkStateWitness`, a higher one is deferred (`chain/chain/src/signature_verification.rs:127`–`:139`). A default anchor is only accepted at genesis or genesis+1 (`:144`–`:152`).
- **Recomputed receipt roots must match, and a mismatch is an error, not a panic**: `make_outgoing_receipts_proofs` returns `ChainError::InvalidChunkReceiptsRoot` instead of asserting (`chain/chunks/src/logic.rs:91`–`:96`). Genesis chunks store `CryptoHash::default()` as their receipts root, so before #16141 any peer requesting a genesis chunk by hash panicked the node on this unauthenticated path.
- **Reconstruction needs ≥`num_data_parts`**: enforced by an assertion in `try_process_chunk_parts_and_receipts` (`shards_manager_actor.rs:2032`); a chunk whose decoded body fails proof validation is rejected, the cache entry poisoned and the request dropped (`:2049`–`:2083`).
- **Invalid chunks are not written to the DB pre-spice**: `Client::on_chunk_completed` returns before `save_invalid_chunk` on non-spice epochs, because such rows were never garbage-collected (`chain/client/src/client.rs:1642`–`:1647`).
- **`encoded_length` bound**: `reed_solomon_decode` rejects an attacker-supplied length > `MAX_ENCODED_LENGTH` (512 MiB, `core/primitives/src/reed_solomon.rs:15`) with `"encoded length is too large"` (`:56`, guard `:55`).
- **Cache horizon**: chunks whose `height_created` falls outside `[largest_seen_height − height_horizon, largest_seen_height + 5]` are dropped unless explicitly requested (`shards_manager_actor.rs:1398`, `:1721`; `chunk_cache.rs:289`–`:297`). The default horizon is 2 heights (`core/chain-configs/src/client_config.rs:638`).
- **Cooldown** (`min_epochs_between_resharding`, a `NonZeroEpochHeight`): back-to-back reshardings are unsafe — a fresh child would inherit the parent's `proposed_split` while its own chunk computes `None`, tripping `InvalidChunkHeaderShardSplit`; enforced via `can_reshard` (`chain/epoch-manager/src/lib.rs:1104`).
- **Memtrie required for split**: `process_memtrie_resharding_storage_update` errors `"Memtrie not loaded"` if the parent memtrie is absent and `allow_resharding_without_memtries` is false (`chain/chain/src/resharding/manager.rs:213`).
- **Right-child congestion invariant**: after subtracting buffered receipts, `buffered_receipts_gas() == 0` is asserted (`manager.rs:362`).
- **Chunk-header JSON must round-trip to the same version**: absent / `null` / value on `proposed_split` select V4 / V5-unset / V5-set respectively and therefore a different chunk hash; `double_option` deserialization preserves the distinction (`core/primitives/src/views.rs:1152`–`:1157`).

## Open questions

- **Stale architecture doc (not edited by this pass).** `docs/architecture/how/dynamic_resharding.md:124` states `ProtocolFeature::StickyReshardingValidatorAssignment` is "protocol version 153"; the real activation is **85** (`core/primitives-core/src/version.rs:607`, arm `→ 85` at `:617`), so it is active at stable v87. `153` is the only version literal in that doc, and it is attached only to `StickyReshardingValidatorAssignment` — the doc never states a version for `DynamicResharding` (line 7 only names the flag), so the earlier claim that the doc cites v153 for `DynamicResharding` too is **refuted**. The doc line should be corrected to 85.
- The dynamic-resharding pipeline is fully present at this commit, but whether any mainnet/testnet **epoch config** at v87 actually sets `shard_layout_config = Dynamic` (vs. `Static`) is a deployment/genesis question not answerable from this code alone — see [genesis & configuration](genesis-configuration.md). Genesis is now *permitted* to carry a dynamic (V3) layout (`chain/epoch-manager/src/genesis.rs:68`), which is a strong hint that the forknet/mainnet path expects it, but the code does not say it is enabled.
- `MAX_CHUNK_SIZE_BYTES` (20 MiB) is a node-local drop threshold applied to individual parts, not a consensus-enforced maximum chunk size. Nothing in this scope proves that a chunk accepted by consensus is always below it; the justification is the comment's arithmetic (~4 MiB txs + ~4.5 MiB receipts, `shards_manager_actor.rs:158`–`:161`). If the runtime limits ever rise, this becomes a silent fork risk.
- `CHUNK_FORWARD_CACHE_SIZE = 10` (down from 1000 in 2.13) is documented as "roughly the mainnet shard count" (`shards_manager_actor.rs:151`–`:154`), but it is a fixed constant, not derived from `num_shards`. Under a dynamic layout that grows past 10 shards, one height's worth of legitimate forwards no longer fits; the consequence is extra re-requests, not incorrectness.
- **Stale in-source comments (code, not spec).** `chain/chunks/src/shards_manager_actor.rs:1747`–`:1748` ("preliminary: shard_id + protocol_version only, signature is checked later") and `:1926`–`:1928` ("the signature is deferred to here") both still describe the pre-#16081 behavior; `validate_chunk_header_preliminary` now verifies the signature at arrival. The spec follows the code, not the comments. Flagged for a comment cleanup.
