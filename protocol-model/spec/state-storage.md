## Role

This component defines how per-shard state is represented, hashed, persisted, and proved. The canonical state is a Merkle-Patricia trie (MPT) per shard, keyed by encoded `TrieKey`s; its root hash is the `StateRoot` committed in each chunk's `ChunkExtra`. On top of the trie sit three derived/auxiliary structures: **flat storage** (a flat key→value-ref map per shard giving near-O(1) reads), **in-memory tries (memtries)** (the whole trie kept in an arena for fast reads/writes and witness generation), and **partial storage / proofs** (the set of trie nodes touched during a chunk, replayed during stateless validation). State mutations are batched in `TrieUpdate` (see [runtime-execution](runtime-execution.md)) and committed as `TrieChanges` (refcount deltas) into the reference-counted `DBCol::State` column. It is read and written by [runtime-execution](runtime-execution.md) and VM host functions; it produces state parts for [sync](sync.md), produces `PartialStorage` proofs for [stateless-validation](stateless-validation.md), and its trie/flat split mechanics feed resharding ([sharding-chunks](sharding-chunks.md)). The same crate also owns the physical database: the RocksDB column layout, the hot/cold split, and (new this release) the cloud-archival blob format.

## Key data structures

- **`RawTrieNode` / `RawTrieNodeWithSize`** — `core/store/src/trie/raw_node.rs:27` / `:11` — the on-disk node. Four variants (borsh discriminant explicit): `Leaf(Vec<u8> key, ValueRef) = 0`, `BranchNoValue(Children) = 1`, `BranchWithValue(ValueRef, Children) = 2`, `Extension(Vec<u8> key, CryptoHash child) = 3`. `RawTrieNodeWithSize` wraps a node with a `memory_usage: u64` that *is* serialized and contributes to the hash (comment `raw_node.rs:9`). The node hash is `CryptoHash::hash_bytes(borsh(self))` (`raw_node.rs:17` — `RawTrieNodeWithSize::hash`).

- **`ValueRef`** — `core/primitives/src/state.rs:82` — `{ length: u32, hash: CryptoHash }`; the trie stores value *references*, not values, so gas can be charged on `length` before the value is dereferenced. The value itself lives in `DBCol::State` keyed by its own hash.

## Behavior

### Trie structure, paths, and hashing

1. **Path.** A key's bytes are split into 4-bit nibbles (`NibbleSlice`, `mod.rs:9`); the trie is walked nibble by nibble. A branch has 16 child slots (one per nibble) plus an optional value. An extension compresses a shared nibble run. A leaf holds the remaining key tail (`extension`) plus a `ValueRef`.
2. **Hashing.** Each node's hash is `hash(borsh(RawTrieNodeWithSize { node, memory_usage }))` (`raw_node.rs:17`). Because `memory_usage` is inside the hashed bytes, two structurally identical subtrees with different aggregate sizes hash differently. The `StateRoot` is the hash of the root node; the empty trie root is `Trie::EMPTY_ROOT = StateRoot::new()` (`mod.rs:606`).
3. **Costs.** `TRIE_COSTS = { byte_of_key: 2, byte_of_value: 1, node_cost: 50 }` (`mod.rs:158`) feeds `memory_usage`. `node_cost` is mirrored as `MIN_MEMORY_USAGE_PER_PART_ENTRY` in near-primitives (`core/primitives/src/state_part.rs:24`) because that crate cannot see `TRIE_COSTS`; a test asserts the two stay equal (`mod.rs:1903`).
4. **On-disk lookup** walks from the root via `lookup_from_state_column` (`mod.rs:1270`): retrieve node by hash, match Leaf/Extension/Branch, descend or return the `ValueRef`. `retrieve_raw_node` short-circuits `EMPTY_ROOT` to `None` (`mod.rs:1174`).

### Read path selection (`get_optimized_ref`)

`Trie::get_optimized_ref` (`mod.rs:1527`) picks the source in priority order, controlled by `KeyLookupMode` (`mod.rs:96`):

1. **Memtrie**, if `self.memtries.is_some()` — `lookup_from_memory` (`mod.rs:1342`); under a read lock it walks the arena and, if `use_trie_accounting_cache` or witness recording is on, serializes each visited node and feeds it to the access tracker and/or recorder (`mod.rs:1354`–`:1372`).
2. **Flat storage**, if mode is `MemOrFlatOrTrie` and a `flat_storage_chunk_view` is present — `lookup_from_flat_storage` (`mod.rs:1242`, dispatched at `mod.rs:1538`). If recording, it *also* walks the on-disk trie to capture the nodes proving the value (or its absence) and `debug_assert`s the two agree (`mod.rs:1249`–`:1259`).
3. **On-disk trie** otherwise — `lookup_from_state_column` (`mod.rs:1541`).

`get_optimized_ref` returns an `OptimizedValueRef` (`mod.rs:559`): either a `Ref(ValueRef)` or an `AvailableValue(ValueAccessToken)` (the value already in hand, e.g. inlined in flat storage; `mod.rs:561`, with `from_flat_value` mapping an inlined flat value into it at `mod.rs:574`). `deref_optimized` (`mod.rs:1551`) turns it into bytes, charging gas / recording exactly as if the value had been read from the trie — this keeps gas accounting identical regardless of which read path served the request (`mod.rs:1547` doc; the `AvailableValue` arm still calls `track_mem_lookup`/`track_disk_lookup` and `recorder.record`, `mod.rs:1560`–`:1573`).

### Update path (`update` → `TrieChanges`)

`Trie::update` (`mod.rs:1586`) takes an iterator of `(key_bytes, Option<value>)` (`Some` = set, `None` = delete). It first force-reads any contract codes the recorder asked to record (`recorder.codes_to_record`, `mod.rs:1590`–`:1602`), then branches:

- **Memtrie present** → `update_with_memtrie` (`mod.rs:1612`): obtains a tracking mode (`RefcountsAndAccesses(recorder)` when recording, else `Refcounts`), applies inserts/deletes to the main memtrie (and, rarely, to child memtries for resharding forks, `mod.rs:1632`), and calls `to_trie_changes` to emit `TrieChanges` including `memtrie_changes`.
- **No memtrie** → `update_with_trie_storage` (`mod.rs:1678`): copies the root into a mutable `TrieStorageUpdate`, applies `generic_insert`/`generic_delete` per change, then flattens new `RawTrieNodeWithSize` nodes, computes their hashes, and produces `TrieChanges`.

Either way the result's `insertions`/`deletions` are refcount deltas: every newly created node/value is a +1 (or +N if shared) and every node that became unreferenced along the path is a −1, netted per hash and split by sign in `TrieRefcountDeltaMap::into_changes` (`mod.rs:417`).

### Commit path (`TrieChanges` → DB) and refcounting GC

`ShardTries::apply_all` (`shard_tries.rs:384`) writes a chunk's `TrieChanges` into a `TrieStoreUpdateAdapter`:

1. `apply_insertions_inner` (`shard_tries.rs:283`) calls `increment_refcount_by(shard_uid, hash, payload, rc)` for each insertion, and updates the in-memory `TrieCache`.
2. `apply_deletions_inner` (`shard_tries.rs:268`) calls `decrement_refcount_by(shard_uid, hash, rc)` for each deletion.
3. `WrappedTrieChanges` drives the full commit: `insertions_into` / `deletions_into` (`shard_tries.rs:846`/`:851`), `state_changes_into` (writes `DBCol::StateChanges`, `shard_tries.rs:865`), `trie_changes_into` (writes `DBCol::TrieChanges` for GC/undo, `shard_tries.rs:898`), and `apply_mem_changes` (applies memtrie changes, `shard_tries.rs:841`).

The `DBCol::StateChanges` row key is chosen by `KeyForStateChanges::for_state_change` (`shard_tries.rs:945`, extracted from an inline match this release): a `TrieKey` that names an account identifies its shard, so its row key is just `block_hash ++ trie_key`; a shard-global key (delayed receipts, buffered receipts, bandwidth scheduler state) does not, so the shard uid is folded into the row key by `delayed_receipt_key_from_trie_key` (`shard_tries.rs:958`).

The `DBCol::State` column is reference-counted (`columns.rs:553` — `is_rc` returns true for `State`). Refcounts are stored as a little-endian `i64` suffix on the value; RocksDB's merge operator sums them at compaction and **removes the key when the count hits 0** (`db/refcount.rs:110` — `refcount_merge`, with `Ordering::Equal => Vec::new()` at `:126`). The DB row key for a node/value is `shard_uid.to_bytes() (8) ++ node_or_value_hash (32)` = 40 bytes (`adapter/trie_store.rs:234` — `get_key_from_shard_uid_and_hash`), so identical content under different shards is stored separately. A missing node read yields `StorageError::MissingTrieValue` (`adapter/trie_store.rs:58`). Because deletions corrupt GC refcounts if replayed, resharding writes use `TrieChanges::insertions_only` (`mod.rs:518`).

`revert_insertions` (`shard_tries.rs:362`) applies each insertion's `.revert()` (`mod.rs:380`) as a subtraction — this is how a discarded fork's nodes are released.

**Earliest servable block.** `get_earliest_block_hash` (`chain/chain/src/store/mod.rs:127`) resolves the oldest block whose state the node can serve as the first height at or above `max(gc_stop_height, tail)` that has a canonical block. Before #16100 it used the GC tail alone; since tail lags `gc_stop_height - 1` while GC is catching up, and resharding drops the whole parent shard at once, a `sync_checkpoint: earliest_available` query could name a block whose state was already gone and fail with `MissingTrieValue` (`chain/chain/src/store/mod.rs:128`–`:136`).

**GC rate.** GC reclaims at most `gc_blocks_limit` blocks per `gc_step_period` tick and never catches up, so config validation now rejects a configuration where `gc_blocks_limit * min_block_production_delay < gc_step_period` and warns when it is below `RECOMMENDED_GC_RATE_MULTIPLIER` (2×) of that (`nearcore/src/config_validate.rs:91` — `validate_gc_config`; error at `:148`, warning at `:159`). A non-positive `min_block_production_delay` is rejected outright because no GC config can keep up (`config_validate.rs:123`–`:130`).

### Flat storage

Flat storage maps every trie *leaf* key to a `FlatStateValue` for the state at a particular block, avoiding root-to-leaf traversal (module doc `flat/mod.rs:1`). It is split into:

- A **flat head**: the on-disk `DBCol::FlatState` snapshot at one block (normally the last final block), plus its `FlatStorageStatus::Ready` marker (`flat/storage.rs:241`, `:404`).
- **In-memory deltas** per block from the head forward, cached in `FlatStorageInner.deltas` and persisted in `DBCol::FlatStateChanges` / `DBCol::FlatStateDeltaMetadata` (`columns.rs:269`/`:273`).

A read for `(block_hash, key)` (`flat/storage.rs:297` — `FlatStorage::get_value`) collects the delta chain from `block_hash` back to the head via `get_blocks_to_head` (`flat/storage.rs:88`, following `prev_block_with_changes` to skip empty blocks, `:108`), returns the first delta that mentions the key, and otherwise reads the on-disk flat head (`flat/storage.rs:315`). This read path yields only `ValueRef`s from deltas, never inlined values (`flat/storage.rs:309`); the actual value is then fetched from `DBCol::State`. `add_delta` (`flat/storage.rs:441`) appends a block's delta, rejecting a block whose parent is neither the head nor a known delta (`flat/storage.rs:451`). `update_flat_head` (`flat/storage.rs:432` → `update_flat_head_impl` `:364`) advances the head by applying intervening deltas to `DBCol::FlatState`, rewriting the `Ready` status (`:404`), and pruning deltas at or below the new head — all in per-block store commits so a crash mid-advance is recoverable. Head advancement is suppressed while any `FlatHeadHold` is active (`update_flat_head_impl` early-returns when `move_head_hold_count > 0`, `flat/storage.rs:370`), which subsystems like state snapshots and background memtrie loading use to pin the head (`hold_flat_head`, `:494`).

Flat storage and memtries are *node-local optimizations*, not consensus state — but which of them is loaded changes trie-node-touched (TTN) counting and therefore gas, so it is protocol-relevant (`KeyLookupMode` doc `mod.rs:98`–`:103`; `Trie` field doc `mod.rs:262`–`:277`).

Background memtrie loading loads a base state from the flat head (while holding a `FlatHeadHold`) and then catches up on deltas; `handle_memtrie_loading_result` (`shard_tries.rs:691`) now receives and reports the delta count applied *during* the background load (`near_memtrie_background_load_deltas`) rather than the two-or-so deltas of the finalization tail, and a shard that is already loaded reports `MemtrieBackgroundLoadStatus::AlreadyLoaded` instead of leaving the gauge unset (`shard_tries.rs:560`).

### Partial storage (proofs) for stateless validation

When a `Trie` is built with `recording_reads_new_recorder`/`recording_reads_with_proof_size_limit` (`mod.rs:653`/`:661`), every node/value retrieved through `internal_retrieve_trie_node` (`mod.rs:779`) and every dereferenced value is fed to a `TrieRecorder.record` (`trie_recording.rs:109`). Crucially, reads that hit flat storage or memtrie *also* record the equivalent on-disk trie nodes (`mod.rs:1249`, `mod.rs:1354`) so the proof can stand alone. `recorded_storage` (`trie_recording.rs:165`) drains the recorder into a sorted `PartialStorage`.

Size is tracked live: `recorded_storage_size` (actual, `trie_recording.rs:199`) and `recorded_storage_size_upper_bound` (`:203`), the latter incremented by 2000 bytes per key removal (`record_key_removal`, `:140`) and by contract-code length (`record_code_len`, `:148`); `check_proof_size_limit_exceed` (`:161`) compares the upper bound against `proof_size_limit`. Two consumers read this accumulator:

- Inside the VM, `RecordedStorageCounter` (`runtime/near-vm-runner/src/logic/recorded_storage_counter.rs:6`) observes the size after every trie operation and aborts the `FunctionCall` with `HostError::RecordedStorageExceeded` once the receipt's delta passes the limit (`recorded_storage_counter.rs:19`). It only exists inside a WASM execution, so it bounds `FunctionCall` actions alone.
- Outside the VM, the runtime snapshots `recorded_storage_size_upper_bound()` before a receipt and re-checks it after each action — see *Protocol-version-gated behavior* for the `EnforcePerReceiptStorageProofLimit` (v86) / `EnforceStorageProofLimitForAllActions` (v87) gates.

A verifier reconstructs a `Trie` from the proof via `from_recorded_storage` (`mod.rs:715`), backed by `TrieMemoryPartialStorage` which returns `MissingTrieValue` for any hash not in the proof (`trie_storage.rs:311`, `:333`). Detail of how the witness is transmitted/verified: [stateless-validation](stateless-validation.md).

Contract code is recorded separately from trie nodes. `ContractStorage` collects the chunk's deploys and calls; `record_deploy` tags a deploy `ContractType::Local` and `record_global_contract_deploy` tags it `ContractType::Global` (`contract.rs:195`, `:202`). `finalize` (`contract.rs:110`) emits `contract_deploys` for every code with at least one local deploy and drops codes deployed only globally, since global contracts reach validators through global-contract distribution.

### State parts (for sync)

State is partitioned into `num_parts` contiguous ranges by DFS order, with each part boundary at the node whose prefix-sum of `memory_usage` crosses `total_size / num_parts * boundary_idx` (`state_parts.rs:52` — `find_state_part_boundary`). Boundaries are found by descending the trie following accumulated `memory_usage` (`find_node_in_dfs_order` `:382`, `find_child_in_dfs_order` `:326`). `get_trie_nodes_for_part_with_flat_storage` (`state_parts.rs:162`) builds a part: capture boundary nodes via a recording trie (`get_state_part_boundaries`, `:116`), iterate flat storage over the part's key range, look up referenced values in `DBCol::State`, rebuild a local trie, unite boundary + local nodes and `visit_nodes_for_state_part` (`:309`) to emit the exact `PartialState`. Each part includes the root-to-boundary paths and all left siblings, so a receiver can verify positions from just the state root (module doc `state_parts.rs:14`). `validate_state_part` (`state_parts.rs:401`) reconstructs a trie from the part, visits its nodes, and requires that visited-node count equals provided-node count (else `UnexpectedTrieValue`, `:419`). `apply_state_part` (`state_parts.rs:473` → `apply_state_part_impl` `:424`) traverses the part building a `TrieChanges` of +1 insertions plus a `FlatStateChanges` delta, and is `expect`ed infallible for a valid part.

**Decode limits (new this release).** A received part is bounded twice before it is materialized:

1. `PART_SIZE_LIMIT = 512 MiB` caps the decompressed byte length; `StatePartV1::to_partial_state` decompresses through a `Read::take(PART_SIZE_LIMIT + 1)` and errors with `"decompression limit exceeded"` (`core/primitives/src/state_part.rs:105`).
2. `PART_ENTRY_LIMIT = 2 * STATE_PART_MEMORY_LIMIT / MIN_MEMORY_USAGE_PER_PART_ENTRY` (`state_part.rs:36`) caps the *entry count*, which the byte cap alone does not: an entry can be four bytes on the wire, so 512 MiB permits >100M `Arc<[u8]>` allocations. The count is read from the borsh length prefix before any entry is decoded — `PartialState::check_entry_limit` (`core/primitives/src/state.rs:50`) errors with `"state part entry limit exceeded"`; `V0` checks it via `try_from_slice_with_entry_limit` (`state_part.rs:78`) and `V1` reads only the first `PARTIAL_STATE_HEADER_LEN` decompressed bytes (`state_part.rs:98`–`:100`).

Part *format/transport*: [sync](sync.md).

### State snapshots

A `StateSnapshot` (`state_snapshot.rs:71`) is a read-only checkpoint of the hot store taken at `prev_block_hash` (`:73`), with flat storage created (via `FlatStorageManager::mark_ready_and_create_flat_storage`, `state_snapshot.rs:94`) and its flat head moved to the last-chunk replay point for each included shard on construction (`StateSnapshot::new`, `state_snapshot.rs:84`–`:124`). It is the source for generating state parts without blocking live state (`get_trie_nodes_for_part_from_snapshot`, `state_snapshot.rs:199`). The flat head is pinned by `FlatHeadHold` guards held on the manager side while a snapshot is pending (`flat/manager.rs:94`, `:312`; the `holds` field `:30`), not by the `StateSnapshot` struct itself. `STATE_SNAPSHOT_COLUMNS` (`state_snapshot.rs:185`) lists what the checkpoint carries: `DbVersion`, `BlockMisc`, and the four flat-storage columns.

**Snapshots can no longer be turned off on a node (#16120).** The `store.state_snapshot_config.state_snapshot_type` config option and its `EveryEpoch`/`ForReshardingOnly` aliases are gone; old `config.json` files still load and the field is ignored. A running node always builds an `Enabled` config: `NightshadeRuntimeExt::from_config` (`nearcore/src/config.rs:921`) calls `StateSnapshotConfig::enabled(hot_store_path)` (`config.rs:938`), or `enabled_with_cadence(.., writer_config.snapshot_every_n_epochs)` when a cloud-archival writer is configured (`config.rs:934`). Checkpoints land in `<hot_store_path>/state_snapshot` (`state_snapshot.rs:150`, `:156`–`:168`) and the default cadence is 1 epoch (`state_snapshot.rs:152`–`:154`). (`opener.rs:299` also constructs an `enabled` config, but only to locate the snapshot directory when migrating snapshot DBs — `migrate_state_snapshots`, `opener.rs:292`.) The `StateSnapshotConfig::Disabled` variant (`state_snapshot.rs:141`) survives for offline tools (`tools/fork-network/src/cli.rs:534`, `tools/cold-store/src/cli.rs:720`, `tools/database/src/analyze_delayed_receipt.rs:60`; entry point `NightshadeRuntimeExt::from_config_with_state_snapshot`, `nearcore/src/config.rs:953`) **and** for throwaway in-process `ShardTries` that never snapshot: genesis initialization (`core/store/src/genesis/initialization.rs:181`), `from_flat` (`core/store/src/trie/from_flat.rs:35`), DB migrations (`nearcore/src/migrations.rs:119`, `chain/chain/src/resharding/migrations.rs:61`), and the cloud-archive reader/writer (`chain/client/src/archive/cloud_reader_trie_utils.rs:26`, `core/store/src/archive/cloud_storage/shards.rs:469`). Two runtime sites short-circuit on it (`chain/chain/src/state_snapshot_actor.rs:131`, `chain/chain/src/chain.rs:3869`). Snapshot-read failures now keep their underlying `StorageError` instead of being flattened into a string: `SnapshotError::Storage(StorageError)` (`state_snapshot.rs:34`) is passed through by the `From<SnapshotError> for StorageError` impl (`state_snapshot.rs:61`).

### Trie split (resharding mechanics)

`Trie::retain_split_shard` (`mod.rs:1747`) produces a `TrieChanges` retaining only the left or right side of a boundary account (memtrie variant `retain_split_shard_with_memtrie` `:1759`, trie-storage variant `:1787`). The split logic (`core/store/src/trie/split.rs`) descends the account-keyed subtrees `SUBTREES = [ACCOUNT, CONTRACT_CODE, ACCESS_KEY, CONTRACT_DATA]` (`split.rs:26`), since shards are split by `AccountId`, not arbitrary bytes; attached-data subtrees (access keys, contract data) are separated from the account id by a separator byte. The per-key retain intervals for a boundary account are computed in `core/store/src/trie/ops/resharding.rs` (`boundary_account_to_intervals`, `:35`). Orchestration: [sharding-chunks](sharding-chunks.md).

### Database versioning and migrations

`DB_VERSION` is **51** at this release (`core/store/src/db/metadata.rs:5`), up from 49 at 2.13.0; `MIN_SUPPORTED_DB_VERSION = 45` (`metadata.rs:8`). The constant used to be computed from `ProtocolFeature::ContinuousEpochSync.enabled(PROTOCOL_VERSION)`; that branch was dead once every build sat at protocol ≥ 85, so it is now a plain literal. `StoreOpener::ensure_version` (`core/store/src/node_storage/opener.rs:503`) walks `version..DB_VERSION` one step at a time, migrating hot and cold in lockstep and stamping `version + 1` after each step (`opener.rs:572`, `:599`–`:602`); a freshly created database is stamped `DB_VERSION` directly (`opener.rs:449`). A database newer than the binary is rejected with `DbVersionTooNew` (`opener.rs:540`), and a **read-only** open of an out-of-date database is rejected outright with `DbVersionMismatchOnRead` before any migration is attempted (`opener.rs:545`). Two bumps landed this release (`nearcore/src/migrations.rs:63`–`:81` — `Migrator::migrate`):

1. **49 → 50 (#16301)** — a no-op migration arm, `49 => Ok(())` (`migrations.rs:79`). The `DBCol::ChunkProducers` column family, previously `#[cfg(feature = "nightly")]`, now exists on every build (`core/store/src/columns.rs:423`). Nothing is rewritten: the migrating open just creates the column family. This matters operationally because a **read-only process cannot create a column family**: a read-only open of a version-49 database fails inside RocksDB's own `open_cf_descriptors` — before the version check at `opener.rs:545` is even reached, since reading the version requires opening the DB — with an error naming `ChunkProducers` (asserted by `slow_test_migration_49_to_50_creates_chunk_producers_column`, `migrations.rs:971`). Every hot and cold database must therefore complete one read-write 49→50 open before `EarlyKickout` activates.
2. **50 → 51 (#16394, #16396)** — `migrate_50_to_51` (`migrations.rs:367`) rewrites every `DBCol::EpochLightClientBlocks` row as a versioned `StoredLightClientBlock`. The column holds one permanent row per epoch, is never rewritten and never garbage collected (`columns.rs:666` — not cold; `:747` — `GcPolicy::Permanent`), so a long-lived database holds rows in several borsh layouts written by binaries going back to 2020. `read_light_client_row` (`migrations.rs:321`) tries the known layouts oldest-first — `WithUnversionedValidatorStake` (pre-#4179 bare `ValidatorStakeView`), `Released`, `WithChunkExecutionRoot`, `Versioned` (`migrations.rs:273`–`:282`) — and, because borsh rejects both trailing and missing bytes, at most one layout reads a row whole. A row that no layout reads, or that two layouts read *differently*, aborts the migration naming its epoch id (`migrations.rs:342`, `:346`) rather than being guessed at. Hot store only. After the migration, reads go through `get_epoch_light_client_block` (`core/store/src/adapter/chain_store.rs:326`), which deserializes `StoredLightClientBlock` and converts to `LightClientBlockView`; writes go through `ChainStoreUpdate::finalize` (`chain/chain/src/store/mod.rs:1929`).

### RocksDB column families, hot/cold split, and open diagnostics

`SplitDB` (`db/splitdb.rs:18`) presents a hot+cold pair: reads hit hot first, falling back to cold only for cold-eligible columns (`get_raw_bytes` `:62`, gated on `col.is_cold()` `:66`); iterators merge-sort the two (`:95`). `ColdDB` (`db/colddb.rs:16`) stores the same byte format but forces every refcounted value's rc to 1 (cold data is never GC'd) and ignores/asserts-against decrements and deletes (module doc `colddb.rs:9`–`:16`; `assert_is_in_colddb` `:34`). Only columns for which `is_cold` returns true are copied to cold (`columns.rs:567`); `State`/`StateChanges` are cold (`columns.rs:588`/`:589`), while `StateParts`/`StatePartsApplied` (`columns.rs:630`), `TrieChanges` (`:632`), and the flat-storage columns (`:680`–`:683`) are explicitly *not*. `is_in_colddb` (`columns.rs:789`) additionally admits `DbVersion`/`BlockMisc`, which cold storage maintains itself rather than copying.

New columns and column changes this release:

| Column | Change | Citation |
|---|---|---|
| `ChunkProducers` | stable on every build (was nightly-only); insert-only; **cold** (`is_cold` → true); `GcPolicy::Delete`; key `BlockHash \|\| ShardId` (40 bytes), the *anchor* block (a chunk's grandparent), sampled at `anchor.height+2` in the anchor's own epoch | `columns.rs:416`–`:423`, `:512`, `:688`, `:784`, `:889` |
| `ChunkHashesByHeight` | doc fix only: maps height → chunk hashes **created** at that height (a chunk may be included at `height >= height_created`), value is a `HashSet` | `columns.rs:209`–`:214` |
| `StateParts` / `StatePartsApplied` | doc: row key's part component is a `StatePartIndex` | `columns.rs:118`–`:125` |
| `ProcessedReceiptIds` | still not cold; a TODO records that split-storage archival nodes therefore lose it past the GC horizon (#15465) | `columns.rs:652`–`:654` |
| `ChunkCertifyingBlock`, `SpiceInvalidChunks` | new, `#[cfg(feature = "protocol_feature_spice")]` only — nightly, not stable at v87 | `columns.rs:403`–`:415` |

**`ChunkProducers` GC (#16023).** Rows are deleted by prefix scan on the anchor block hash, since the key prefixes all shards' rows: `gc_chunk_producers_for_block` (`chain/chain/src/garbage_collection.rs:535`). It is called from three places: alongside the anchor block's `BlockInfo` in `clear_block_data` (`garbage_collection.rs:753`) — prefix scanning rather than iterating `get_shard_uids_to_gc`, because the column is keyed by `ShardId` and that union can hold two `ShardUId`s sharing one `ShardId` at a reshard boundary — and per header hash in `clear_chunk_data_and_headers` (`garbage_collection.rs:607`), which catches header-only anchors (fork siblings, headers synced ahead of their bodies) that never get a `clear_block_data` pass — and again in `clear_head_block_data` (`garbage_collection.rs:1027`), which rolls back head-block data so the insert-only row goes before re-processing re-seeds it. A row for anchor `A` therefore dies when `A` crosses the GC boundary, far below the near-head read horizon (a chunk's anchor is `head-2`), so no live consensus read is lost. Archival nodes copy the row to cold before hot GC deletes it. Who writes and reads the column: [epoch-validators-staking](epoch-validators-staking.md).

**Open-failure diagnostics (#15851).** `RocksDB::open_db` wraps a failed `DB::open_cf_descriptors` with `log_rocksdb_open_failure` (`core/store/src/db/rocksdb.rs:581`), which logs the `CURRENT` pointer and stats the `MANIFEST` it names before returning — RocksDB's own error is a terse IO error, and a failed start is usually rolled back to an older binary whose successful open rewrites those files and destroys the evidence. `InstanceTracker::mark_opened` (defined `core/store/src/db/rocksdb/instance_tracker.rs:143`) is called only after a successful open (`rocksdb.rs:134`, after the `?` on `open_db`), so a failed open no longer logs a spurious open/close pair. The `rocksdb` crate moved `0.21.0` → `0.24.0` (`Cargo.toml:316`); the property-name API changed from `CString` to `PropertyName` (`rocksdb.rs:26`).

**Reading cold storage for a dynamically chosen column.** `ColumnCheckedColdDB` (`core/store/src/db/cold_column_checked.rs:12`) wraps a cold `Store` for callers whose column comes from a request rather than from code — the entity-debug endpoint. `ColdDB` expects its callers to pick an `is_in_colddb` column statically; the wrapper instead records the first inadmissible column in `rejected_column` (`cold_column_checked.rs:23`) and reports the read absent, letting the caller turn it into an error instead of a confusing empty result (#16162). Separately, `EntityQuery::TrieNode` now reads through a bare `TrieDBStorage` (`nearcore/src/entity_debug.rs:422`) instead of `get_tries().get_trie_for_shard`, which would register a trie cache and prefetcher for every attacker-chosen `ShardUId`; the endpoint consequently never consults memtries, matching what `is_view` reads already do, since the request carries an arbitrary state root (#16161).

### Cloud archival (new subsystem)

`core/store/src/archive/cloud_storage/` is a second archival path alongside the hot/cold `SplitDB`: instead of a cold RocksDB, a node uploads versioned borsh blobs to external object storage (`CloudStorage`, `archive/cloud_storage/mod.rs:33`), and a reader node reconstructs a store from them. Objects are named by `CloudStorageFileID` (`file_id.rs:31`): `Config`, `BlockHead`, `ShardHead(ShardId)`, `Epoch(EpochId)`, `BlockBatch(BatchId)`, `ShardBatch(ShardId, BatchId)`, `StateHeader(..)`, `StatePart(.., StatePartId)`. Only bounded directories may be listed (`ListableCloudDir`, `file_id.rs:9`).

The blob formats were frozen this release (#16381): both are versioned enums whose `V1` payload must not change — add a `V2` variant instead (`blocks.rs:24`).

- **`BlockData`** — `archive/cloud_storage/blocks.rs:20` — per height: `Block`, `BlockInfo`, `next_block_hash`, `block_merkle_tree` (`PartialMerkleTree`, added #16271), and the block's `ChunkProducers` rows keyed by shard id (empty until `EarlyKickout` activates). Batched into a `BlockBatch` over a height range, with `None` at skipped slots.
- **`ShardData`** — `archive/cloud_storage/shards.rs:34` — `V1(ShardDataV1) = 0`, whose payload (`shards.rs:44`) is per `(shard, height)` either `NewChunk(NewChunkData) = 0` (chunk, incoming/outgoing receipts, `ChunkExtra`, `ChunkApplyStats`, `StateChanges`, outcomes, receipt→tx and processed-receipt rows and bodies) or `Carried(CarriedData) = 1` for a missing chunk. `build_shard_batch` (`shards.rs:452`) is resharding-aware: it attaches inverse state-change deltas below an `inverse_ceiling` so a reader bootstrapping across a resharding boundary can walk state backwards, and it builds a fresh `ShardTries` for that read rather than using the writer's memtries, which may not hold the child layout's roots (`shards.rs:459`–`:468`).

This subsystem is node-local infrastructure, not consensus state: nothing it stores is hashed into a block, and no protocol version gates it. See *Open questions* on its modelling depth.

## Protocol-version-gated behavior

`STABLE_PROTOCOL_VERSION = 87` (`core/primitives-core/src/version.rs:680`), `MIN_SUPPORTED_PROTOCOL_VERSION = 84` (`version.rs:652`).

**Active at v87 (state-storage-relevant):**

- **`EnforceStorageProofLimitForAllActions`** — `version.rs:473`, activates at **87** (`version.rs:624`). The in-VM `RecordedStorageCounter` only runs inside a WASM execution, so before v87 only `FunctionCall` actions were bounded and other actions in the same receipt could push the recorded proof past the limit. At v87 the runtime re-reads `recorded_storage_size_upper_bound()` after *every* action, subtracts the pre-receipt snapshot, and fails the receipt with `ActionErrorKind::ReceiptStorageProofSizeExceeded { limit }` once the delta exceeds `wasm_config.limit_config.per_receipt_storage_proof_size_limit` (`runtime/runtime/src/lib.rs:933`–`:942` gate, `:987`–`:996` check). The accumulator it reads is this component's (`trie_recording.rs:203`); the enforcement decision is [runtime-execution](runtime-execution.md)'s.
- **`EnforcePerReceiptStorageProofLimit`** — `version.rs:466`, activates at **86** (`version.rs:618`), i.e. baseline at the pinned version but still a live gate for replay. It is what makes the runtime snapshot `recorded_storage_size_upper_bound()` before executing a receipt (`runtime/runtime/src/lib.rs:925`–`:931`); pre-86 the snapshot is `None`, and the v87 per-action check above is therefore inert without it.
- **`GlobalContractSameChunkCallFix`** — `version.rs:413`, activates at **87** (`version.rs:628`). Records a just-distributed global contract's code into `ContractStorage` via `TrieUpdate::record_global_contract_deploy` (`core/store/src/trie/update.rs:303`, gated at `runtime/runtime/src/global_contracts.rs:219`) so a same-chunk call to it resolves. The recording is deliberately *excluded* from the broadcast `contract_deploys` set (`contract.rs:110`), because global contracts are distributed by their own mechanism; a code hash deployed both locally and globally in the same chunk is still broadcast (`contract.rs:81`).
- **`EarlyKickout`** — `version.rs:395`, activates at **87** (`version.rs:626`), moved from nightly. It is the consumer of the `ChunkProducers` column documented above; the column family itself is unconditional (DB 50), and rows only appear once the feature is on (`columns.rs:418`–`:421`).
- **`UniversalAccounts`** — `version.rs:491`, activates at **87** (`version.rs:629`). Creates accounts whose id derives from a canonical state init. It writes ordinary `TrieKey::Account` / `ContractCode` / `AccessKey` / `ContractData` rows; no new trie column byte was added. Semantics: [accounts-keys](accounts-keys.md).
- **`ContinuousEpochSync`** — `version.rs:355`, activates at **85** (`version.rs:605`). It is the one feature that changes the hot/cold split, making `DBCol::BlockHeader` a cold column (`columns.rs:655`–`:656`) and enabling header GC (`chain/chain/src/garbage_collection.rs:758`). Note both sites evaluate it against the *binary's* `PROTOCOL_VERSION`, not the chain's current version, so this is a build-time switch rather than a per-block gate; at v87 (and on nightly) it is always true, which is why `DB_VERSION` no longer branches on it.

**Baseline (activated below `MIN_SUPPORTED_PROTOCOL_VERSION = 84`, behavior now unconditional):**

- **Flat storage reads** (NEP-399) — `_DeprecatedFlatStorageReads` (`version.rs:177`), version 61 (`version.rs:549`).
- **Stateless validation** (NEP-509) — `_DeprecatedStatelessValidation` (`version.rs:225`), version 69 (`version.rs:562`). Proof recording (`PartialStorage`) and proof-size limits are baseline.
- **Exclude contract code from witness** — `_DeprecatedExcludeContractCodeFromStateWitness` (`version.rs:271`), version 73 (`version.rs:570`); contract codes are recorded separately via the recorder's `codes_to_record` set (`mod.rs:1590`–`:1602`).
- **State-stored receipts** — `_DeprecatedStateStoredReceipt` (`version.rs:259`), version 72 (`version.rs:569`) — and **bandwidth scheduler** `_DeprecatedBandwidthScheduler` (`version.rs:274`), version 74 (`version.rs:576`) — populate the `BandwidthSchedulerState` / buffered-receipt-group `TrieKey` columns (`trie_key.rs:65`, `:68`–`:70`).
- **Global contracts** — `_DeprecatedGlobalContracts` (`version.rs:307`), version **77** (`version.rs:580`), and `_DeprecatedEthImplicitGlobalContract` (`version.rs:381`), version **83** (`version.rs:598`); the `GLOBAL_CONTRACT_CODE` (18) and `GLOBAL_CONTRACT_NONCE` (19) trie columns are unconditional.
- **Compressed state parts** — `_DeprecatedStatePartsCompression` (`version.rs:337`), version 82 (`version.rs:589`). This is why part generation unconditionally emits `StatePart::V1` (zstd) today (`core/primitives/src/state_part.rs:117`) while `V0` survives only as a decode path.

Note on the previous edition of this spec: the v86 entry claimed "an older baseline showed PV 86 as `FixContractLoadingError`; on the 2.13.0 stable tree there is no such feature". That is now stale — `FixContractLoadingError` exists and activates at **87** (`version.rs:448`, `:619`), while the nightly `FixContractLoadingCost` sits at 129 (`version.rs:632`). ## Invariants & failure modes

- **Canonical refcount representation.** `TrieRefcountDeltaMap::into_changes` sorts insertions/deletions so equal `TrieChanges` serialize identically (`mod.rs:417`). Refcount reaching 0 deletes the DB key (`db/refcount.rs:126`).
- **Same key ⇒ same value.** Refcounted columns must never store differing values under one key; `refcount_merge` `debug_assert`s equal payloads (`db/refcount.rs:119`).
- **`memory_usage` integrity.** A `memory_usage` mismatch found while computing a state-part boundary returns `StorageInconsistentState` (`state_parts.rs:364`, in `find_child_in_dfs_order`).
- **Missing node.** Reading an absent hash returns `StorageError::MissingTrieValue` (disk: `adapter/trie_store.rs:58`; partial storage: `trie_storage.rs:333`).
- **State part validity.** `validate_state_part` requires visited-node count == provided-node count, else `UnexpectedTrieValue` (`state_parts.rs:419`); `apply_state_part` is documented infallible for a valid part and `expect`s success (`state_parts.rs:479`).
- **State part decode bounds.** Entry count ≤ `PART_ENTRY_LIMIT`, checked from the length prefix before allocation (`core/primitives/src/state.rs:60`); decompressed size ≤ `PART_SIZE_LIMIT` (`core/primitives/src/state_part.rs:105`). Both fail with `borsh::io::ErrorKind::InvalidData`.
- **`node_cost` mirror.** `TRIE_COSTS.node_cost` must equal `MIN_MEMORY_USAGE_PER_PART_ENTRY`, or `PART_ENTRY_LIMIT` is wrong; asserted by `state_part_entry_limit_uses_the_real_node_cost` (`core/store/src/trie/mod.rs:1903`).
- **NotWritableToDisk never finalized.** `state_changes_into` asserts no `StateChangeCause::NotWritableToDisk` change is committed — `"NotWritableToDisk changes must never be finalized."` (`shard_tries.rs:871`–`:877`).
- **Gas key access keys carry nonce 0.** `set_access_key_by_handle` `debug_assert`s that an access key with gas-key permission is stored with `nonce == 0`, since gas keys track nonces per index in separate `GasKeyNonce` rows (`core/store/src/utils/mod.rs:372`, assert at `:378`).
- **Flat delta continuity.** `add_delta` rejects a block whose parent is neither the flat head nor a cached delta (`flat/storage.rs:451`); reads error with `BlockNotSupported` if no path to head exists (`flat/storage.rs:70`).
- **Flat head holds.** Head cannot advance while `move_head_hold_count > 0` (`flat/storage.rs:370`); a `FlatHeadHold` increments the count on creation (`:508`) and decrements on drop (`:523`).
- **Cold storage immutability.** `ColdDB` forces refcounts to 1 and ignores/asserts-against decrements and deletes (`db/colddb.rs:9`–`:16`).
- **DB version monotonicity.** A store whose version exceeds the binary's `DB_VERSION` is refused with `DbVersionTooNew` (`node_storage/opener.rs:540`); a version below `MIN_SUPPORTED_DB_VERSION` is refused as "database version is too old and not supported" (`nearcore/src/migrations.rs:48`). Migration 49→50 creates a column family, which a read-only open cannot do, so a read-only process against a version-49 store fails to start; migrations are refused in read-only mode in any case (`node_storage/opener.rs:545` — `DbVersionMismatchOnRead`).
- **Light-client row readability.** Every `EpochLightClientBlocks` row must read whole in exactly one known layout; a row in none, or one that two layouts read differently, aborts migration 50→51 naming its epoch id instead of being silently reinterpreted (`nearcore/src/migrations.rs:342`, `:346`).
- **GC keeps up with block production.** Config validation rejects `gc_blocks_limit * min_block_production_delay < gc_step_period`, since GC never catches up and storage would grow without bound (`nearcore/src/config_validate.rs:148`).
- **Earliest servable block never precedes GC.** `get_earliest_block_hash` starts at `max(gc_stop_height, tail)`; using `tail` alone can name a block whose shard state resharding already dropped (`chain/chain/src/store/mod.rs:138`).

## Open questions

- **Cloud archival is modelled only at the blob-format level here.** The reader/writer state machines (batch bootstrapping, catch-up throttling, epoch-data completeness, cross-resharding inverse walks, credentialed state-part download) landed across ~20 commits this release and are not described. They are node-local infrastructure with no consensus effect, so no protocol behavior is missing from the model; but if a sibling spec should own the operational model, it is [sync](sync.md) (it already owns state-part transport and snapshot distribution), not this one. The blob formats themselves are frozen and are documented above because they are a storage layout.
- **Snapshot-host shard-cache bookkeeping (#15955)** lives in `chain/network/src/snapshot_hosts/mod.rs` and is *not* modelled here; it belongs to [networking-p2p](networking-p2p.md) / [sync](sync.md). Noted because the release brief routed it to this component.
- **Removal of dead per-shard persistence methods (#16001)** (`ChainStoreUpdate::save_processed_receipt_ids`, `save_outcomes_with_proofs`, `save_receipt_to_tx`) touched `chain/chain/src/store/mod.rs`, not `core/store`. It was pure dead-code removal — those columns are written directly through the store adapter by `apply_chunk_postprocessing` — so no behavior described here changed.
- Whether any node currently runs without memtries in the v87 production configuration (and thus relies on the flat/disk TTN-equivalence path) is a deployment fact not determinable from this code alone.
- The exact fleet-wide deployment ordering constraint for DB 49→50 (every hot *and* cold store must complete one read-write open before `EarlyKickout` activates at v87) is stated in the #16301 commit message; the code enforces only the per-process failure, not the fleet invariant.
- `ContinuousEpochSync` gates `DBCol::BlockHeader`'s cold-eligibility and header GC against the *binary's* `PROTOCOL_VERSION` rather than the chain's (`columns.rs:656`, `garbage_collection.rs:758`). Whether that is intentional (a build-time switch that can never disagree between hot and cold openers of the same binary) or a latent per-block gate is not determinable from the code alone; it is inert at v87 either way.
