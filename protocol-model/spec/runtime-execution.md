## Role

The runtime is the state-transition function of a single shard. `Runtime::apply` takes a chunk (transactions + incoming receipts) plus the pre-state trie and produces a new state root, outgoing receipts, execution outcomes, validator proposals, and congestion/bandwidth metadata (`runtime/runtime/src/lib.rs:1860` — `Runtime::apply`, `runtime/runtime/src/lib.rs:388` — `ApplyResult`). It validates and converts transactions into receipts, executes action receipts one action at a time, accounts gas/deposits/refunds, and commits or rolls back trie state per receipt. It sits downstream of chunk/block production and epoch management (which supplies the validator accounts update and the runtime config), invokes the [contract VM](contract-vm.md) for `FunctionCall`, routes outgoing receipts through [cross-shard congestion control](cross-shard-congestion.md), and reads/writes the shard via [state storage](state-storage.md). Fees feed [economics](economics.md); stake proposals feed [epoch, validators & staking](epoch-validators-staking.md); receipt/action wire types are documented in [data structures & serialization](data-structures-serialization.md) and account/key semantics in [accounts & keys](accounts-keys.md).

## Behavior

### 1. Ordered phases of `apply`

`Runtime::apply` (`runtime/runtime/src/lib.rs:1860`) documents four conceptual steps (validator accounts → transactions → receipts → validate/apply state). Concretely, in order:

1. **Build `ApplyProcessingState`** and **prefetch** transaction data (best-effort; failure ignored) (`runtime/runtime/src/lib.rs:1884`, `:1889`).
2. **Update validator accounts** if a `ValidatorAccountsUpdate` is supplied (`runtime/runtime/src/lib.rs:1894` → `update_validator_accounts` `:1717`). This runs first so reward/stake changes land before any tx/receipt reads balances; it commits with `StateChangeCause::ValidatorAccountsUpdate` (`runtime/runtime/src/lib.rs:1835`).
3. **Load the delayed receipt queue** (`runtime/runtime/src/lib.rs:1902`).
4. **Run the bandwidth scheduler** — for every chunk, including missing ones (`runtime/runtime/src/lib.rs:1909` — `run_bandwidth_scheduler`).
5. **Missing-chunk short-circuit**: if `!apply_state.is_new_chunk`, finalize immediately and return without processing any receipts (`runtime/runtime/src/lib.rs:1917` → `missing_chunk_apply_result` `:3064`), carrying congestion info and bandwidth requests forward unchanged and emitting no outcomes/outgoing receipts.
6. **Build the `ReceiptSink`** from own congestion info + scheduler output, then **forward buffered receipts** from prior chunks first (`runtime/runtime/src/lib.rs:1930`, `:1938`). See [cross-shard congestion](cross-shard-congestion.md).
7. **Process transactions** → local receipts / forwarded receipts (`runtime/runtime/src/lib.rs:1941` — `process_transactions` `:2011`).
8. **Process receipts** in the order local → delayed → incoming, then resolve promise-yield timeouts (`runtime/runtime/src/lib.rs:1945` — `process_receipts` `:2787`).
9. **Finalize**: `validate_apply_state_update` (`runtime/runtime/src/lib.rs:1955` / `:2852`) — persist promise-yield indices, apply delayed-receipt congestion changes and choose the allowed shard, generate bandwidth requests, commit with `UpdatedDelayedReceipts`, apply the sandbox state patch, invoke `on_post_state_ready` if set, run `state_update.finalize()`, dedup validator proposals (last proposal per account wins; iteration is reversed so the order is deterministically changed) (`runtime/runtime/src/lib.rs:2944`), and assemble `ApplyResult`.

The local → delayed → incoming order is load-bearing: local receipts (from this chunk's transactions) and the delayed backlog are drained before new incoming cross-shard receipts, so backlog is preferred over new work, and gas-limit exhaustion pushes the *newest* work onto the delayed queue rather than starving the backlog (`runtime/runtime/src/lib.rs:2799`-`:2821`).

### 2. Transaction validation and conversion (`process_transactions`, `runtime/runtime/src/lib.rs:2011`)

1. **Parallel phase** (`rayon::join`, `runtime/runtime/src/lib.rs:2022`): one arm stateless-validates every tx via `validate_transaction` (`runtime/runtime/src/verifier.rs:109`) — action validation (`validate_actions`, see §3) then `ValidatedTransaction::new` (signature, version, key-scheme admission); expired txs short-circuit to `InvalidTxError::Expired`. The other arm prefetches signer accounts, access keys and gas-key nonces into `DashMap`s (`runtime/runtime/src/lib.rs:2052`-`2104`).
2. **Sequential phase**, per tx:
   - `UniqueChunkTransactions` (v85): skip any repeat of a tx hash already seen in this chunk — a tx hash is also its outcome id, so a duplicate would commit two conflicting outcomes under one id (`runtime/runtime/src/lib.rs:2110`).
   - Stateless-validation failure → failed outcome pushed, tx skipped (`runtime/runtime/src/lib.rs:2124`).
   - `tx_cost` (`runtime/runtime/src/config.rs:464`); overflow → `CostOverflow` failed outcome (`runtime/runtime/src/lib.rs:2135`).
   - Missing signer account → `InvalidSignerId` (`runtime/runtime/src/lib.rs:2159`). Missing access key → `AccessKeyNotFound`, **unless** `is_bootstrap(account, tx)` holds (`runtime/runtime/src/lib.rs:2174`, `runtime/runtime/src/verifier.rs:200`).
   - **Charge**, by authorization kind (`runtime/runtime/src/lib.rs:2196`): no access key → `verify_and_charge_bootstrap_tx_ephemeral` (`runtime/runtime/src/verifier.rs:424`); nonce carries a `nonce_index` → `verify_and_charge_gas_key_tx_ephemeral` (`runtime/runtime/src/verifier.rs:524`); otherwise `verify_and_charge_tx_ephemeral` (`runtime/runtime/src/verifier.rs:312`). All three are pure and return a `TxVerdict`.
3. **`TxVerdict::Success`** → build the receipt with `Receipt::from_tx` at `result.receipt_gas_price` (`runtime/runtime/src/lib.rs:2281`); if `receiver_id == signer_id` it is a **local receipt**, otherwise it is handed to `ReceiptSink::forward_or_buffer_receipt` (`runtime/runtime/src/lib.rs:2317`-`2325`). Outcome status is `SuccessReceiptId`, metadata `ExecutionMetadata::V1` (transactions carry no profile).
4. **`TxVerdict::DepositFailed`** (gas-key only): gas is still burnt against the gas key, a `failed_with_gas_burnt` outcome is emitted, no receipt is created (`runtime/runtime/src/lib.rs:2258`). **`TxVerdict::Failed`**: failed outcome, tx skipped, no state change (`runtime/runtime/src/lib.rs:2329`).
5. Chunk-level `tx_burnt_amount` is accumulated; an overflow drops the tx *without* an outcome (`runtime/runtime/src/lib.rs:2354`). Gas + compute are added to the chunk totals (`runtime/runtime/src/lib.rs:2364`). **That counter is the same one the receipt loops gate on**: `ApplyProcessingState::into_processing_receipt_state` carries `total` across unchanged (`runtime/runtime/src/lib.rs:3294`, field at `:3314`), so conversion burn is metered against the chunk and a chunk full of expensive conversions leaves no room to execute receipts (`:2514`, `:2595`, `:2704`).
6. **State write-back**: `result.apply` mutates the in-memory signer account + access key (`runtime/runtime/src/lib.rs:2367`), then `set_account`, the gas-key nonce (`set_gas_key_nonce`, also refreshing the prefetch cache so later txs in the chunk see it) and `set_access_key` are written, and the update commits with `StateChangeCause::TransactionProcessing` (`runtime/runtime/src/lib.rs:2368`-`2397`). On the bootstrap path nothing is written to the key store — the key does not exist yet and the state init is what creates it.

**Failed-transaction outcomes are recorded unconditionally.** The old `register_outcome` helper and its `InvalidTxGenerateOutcomes` gate are gone; every branch pushes its outcome directly (`runtime/runtime/src/lib.rs:2125`, `:2143`, `:2332`), and a `debug_assert` requires `outcomes.len() == num_transactions - num_skipped_duplicate_txs` (`runtime/runtime/src/lib.rs:2399`).

**Send fees are burnt here, on the signer's shard, at conversion time.** `calculate_tx_cost` (`runtime/runtime/src/config.rs:481`) sets `burnt = new_action_receipt send_fee + total_send_fees(actions) + signature_verification_cost`, burnt at `current_gas_price`; `gas_remaining` (prepaid attached gas + prepaid send fees + receipt exec fee + prepaid exec fees) is attached to the receipt and purchased at `receipt_gas_price = max(current_gas_price, min_gas_purchase_price)` (`runtime/runtime/src/config.rs:532`). `sender_is_receiver` ("sir") selects the cheaper send-fee column (`runtime/runtime/src/config.rs:489`).

### 3. Action validation (`action_validation.rs`)

`validate_actions_with_mode` (`runtime/runtime/src/action_validation.rs:97`) runs on transactions (via `validate_transaction`) and on receipts (via `validate_receipt`). `ValidateReceiptMode` (`runtime/runtime/src/verifier.rs:728`) distinguishes `NewReceipt` (strict; transactions and freshly created receipts) from `ExistingReceipt` (receipts already in flight or stored as delayed). Checks, in order:

1. `max_actions_per_receipt` (`:104`).
2. Post-quantum gate: if `PostQuantumSignatures` (v85) is off, any action requiring it is rejected with `UnsupportedProtocolFeature` (`:119`). This is the **centralized** gate — it also covers actions emitted by contracts, which never pass tx admission.
3. `NewReceipt` only (`:128`): `max_deploy_actions_per_receipt`, then `validate_state_init_counts` (`:48`) — the **combined** `StateInitCounts` of *all* state-init actions in the receipt, checked against `max_state_init_entries` (1 500, `TotalNumberOfStateInitEntriesExceeded`) and `max_universal_state_init_keys` (1 024, `TotalNumberOfStateInitKeysExceeded`). Both caps are per receipt, not per action, because every action in a receipt shares its receiver and a universal state init must derive to that receiver, so a receipt can carry many byte-identical copies and pays for each.
4. `DeleteAccount` must be the final action; at most one delegate action per receipt (`:139`-`:150`).
5. Per-action validation (`validate_action_with_mode`, `:169`), then `max_total_prepaid_gas` (`:156`).

Per-action rules that matter at v88:

- `FunctionCall` must have non-zero gas and (with `RejectEmptyMethodName`, `NewReceipt` only) a non-empty `method_name` (`:344`-`:360`).
- `Transfer` is no longer unconditionally `Ok`: `validate_transfer_action` (`:236`) rejects a transfer whose receiver is a `0u` id with `ActionsValidationError::TransferToUniversalAccountNotAllowed { account_id }` while `RejectUniversalAccountTransfers` is on and `UniversalAccounts` is not — i.e. **exactly at protocol 87** — and only in `NewReceipt` mode. See §8.
- `DelegateV2` requires `DelegateV2` (v85) and, for `NewReceipt`, is refused by `reject_removed_protocol_feature` (`:516`) once `RejectDelegateV2` is on (`:196`-`:209`).
- `validate_delegate_action` (`:255`) bounds the nested action count *before* cloning the list, refuses a nested `WithdrawFromGasKey` under `RejectWithdrawFromGasKeyInDelegate` (`NewReceipt` only, `:276`), and validates the inner actions against the delegate's own `receiver_id` (`:284`-`:300`).
- `UniversalStateInit` (`validate_universal_state_init`, `:568`) requires `UniversalAccounts` (v88), pins the receiver to `derive_universal_account_id(raw bytes)` (`:584`), decodes the payload — **strictly** (canonical borsh only) when `CanonicalUniversalStateInit` is on *and* the mode is `NewReceipt`, leniently otherwise (`:596`-`:601`) — and bounds each storage key/value by the trie limits (`:608`-`:621`). The key cap moved out of this function into `validate_state_init_counts` (above) by #16415. A decode or canonicity failure is `ActionsValidationError::MalformedUniversalStateInit`, whose message is now "RawStateInit bytes are not a canonical borsh encoding of UniversalStateInit" (`core/primitives/src/errors.rs:754`).

### 4. Nonce, balance and storage checks (`verifier.rs`)

- `verify_nonce` (`runtime/runtime/src/verifier.rs:254`): `Monotonic` requires `tx_nonce > current_nonce`; `Strict` (opt-in via `NonceMode`, gated by `StrictNonce`, v85) requires `tx_nonce == current_nonce + 1`. Both enforce `tx_nonce < block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`.
- `verify_and_charge_tx_ephemeral` (`runtime/runtime/src/verifier.rs:312`): asserts the caller routed gas-key txs elsewhere; rejects a gas-key access key used without a nonce index (`InvalidNonceIndex`); checks nonce against `max(access_key.nonce, pending.max_nonce)`; checks balance (`NotEnoughBalance`); computes the new allowance (`check_and_compute_new_allowance` `:282`) — **unconditionally non-mutating**, the returned `AccessKeyUpdate` is the only carrier; checks storage staking on the post-charge amount (`check_storage_stake` `:48`); finally verifies function-call-permission constraints (`verify_function_call_permission` `:209`).
- `verify_and_charge_gas_key_tx_ephemeral` (`runtime/runtime/src/verifier.rs:524`): requires the key to be a gas key, `nonce_index < num_nonces`, a valid nonce, and gas-key balance ≥ `gas_cost`; it also pre-computes the balance left if only `burnt_amount` is charged. Then it checks the *account* balance against `deposit_cost` and storage staking — a shortfall yields `DepositFailed` (gas key charged only the conversion burn), not a hard failure.
- `verify_and_charge_bootstrap_tx_ephemeral` (`runtime/runtime/src/verifier.rs:424`): the one transaction an account can send with no access key. It re-derives authorization rather than trusting the caller: the account must carry a `bootstrap_nonce` (only uninitialized accounts do), `universal_accounts` must be on (**v88**), and `tx.is_state_init_bootstrap()` must hold — signer == receiver, no `nonce_index`, and a `UniversalStateInit` action whose derived id equals the account and whose `access_keys` contain the signing key's handle (`core/primitives/src/transaction.rs:236` — `Transaction::state_init_bootstrap`). That shape test decodes **leniently** (`core/primitives/src/transaction.rs:255`): the transaction has already been validated, and from `CanonicalUniversalStateInit` on that validation already rejected a non-canonical payload, so the lenient read cannot admit one. The nonce is checked in **`Strict` mode regardless of what the transaction asked for**, so exactly one nonce is admissible and the same signed bytes cannot replay through the ordinary key path once the state init installs the keys.
- `check_storage_stake` (`runtime/runtime/src/verifier.rs:48`): zero-balance accounts (≤ `ZERO_BALANCE_ACCOUNT_STORAGE_LIMIT = 770` bytes, `:25`) are exempt (`is_zero_balance_account` `:88`).

### 5. Action receipt execution (`apply_action_receipt`, `runtime/runtime/src/lib.rs:827`)

1. **Promise-input size check — present in the code but inert on the stable path at v88.** When `ReceiptPromiseInputSizeLimit` is on, the sizes of all `input_data_ids` are summed from state and compared with `max_receipt_total_input_size` (`runtime/runtime/src/lib.rs:847`-`:859`); if exceeded the inputs are removed from state, `promise_results` is empty, **no action runs at all**, and the receipt fails with `ActionErrorKind::TotalPromiseInputSizeExceeded { size, limit }` (`runtime/runtime/src/lib.rs:918`). That feature is **nightly-only at this release** (157, `core/primitives-core/src/version.rs:653`) and `max_receipt_total_input_size` stays at its base value `4_294_967_295` for 87 and 88 (`core/parameters/res/runtime_configs/parameters.yaml:315`; the 4 194 944 diff lives in `core/parameters/res/runtime_configs/157.yaml:17`). So on the stable path `enforce_input_size_limit` is false, the loop never runs, and **`TotalPromiseInputSizeExceeded` is unreachable**. See the de-stabilization note under *Protocol-version-gated behavior*.
2. Otherwise gather each `input_data_id` as a `PromiseResult` and remove it from state; a missing entry is `StorageInconsistentState` (`runtime/runtime/src/lib.rs:862`-`897`).
3. Commit prior updates with `ActionReceiptProcessingStarted` (`runtime/runtime/src/lib.rs:903`).
4. Load the receiver account (remembering whether it existed) and seed the receipt-level result with the `new_action_receipt` exec fee (`runtime/runtime/src/lib.rs:907`-`913`).
5. Snapshot `recorded_storage_size_upper_bound` before the receipt when `EnforcePerReceiptStorageProofLimit` (v86) is on, and compute the per-action storage-proof limit when `EnforceStorageProofLimitForAllActions` (v87) is on (`runtime/runtime/src/lib.rs:925`-`941`).
6. **Execute actions in order** (`runtime/runtime/src/lib.rs:946`): derive `action_hash` from receipt id + block height + index, call `apply_action`, and on success validate every newly created receipt with `validate_receipt(..., NewReceipt)` — a failure becomes `ActionErrorKind::NewReceiptValidationError` (`:968`-`:980`). `merge` folds the result. Then, if the receipt is still `Ok` and both storage-proof values are present, the growth attributable to this receipt is compared against `per_receipt_storage_proof_size_limit` (4 MB) and, if over, the receipt fails with `ActionErrorKind::ReceiptStorageProofSizeExceeded { limit }` (`:982`-`998`). On the first `Err` the action index is recorded and the loop breaks — **later actions do not run** (`:1000`).
7. If the receipt still succeeded, re-check receiver storage staking; a shortfall sets `LackBalanceForState`, a storage error is fatal (`runtime/runtime/src/lib.rs:1008`-`1032`).
8. **Refunds**: system-predecessor receipts (refunds) are free — no refund is generated, and a failed refund burns its deposit into `other_burnt_amount` (`runtime/runtime/src/lib.rs:1047`-`1050`). Otherwise `refund_unspent_gas_and_deposits` runs, told whether this receipt created a new account (`:1061`).
9. **Commit or rollback**: `Ok` commits with `ReceiptProcessing`; `Err` calls `state_update.rollback()`, discarding every state change made by the receipt (`runtime/runtime/src/lib.rs:1079`-`1088`).
10. **`tx_burnt_amount`** = `gas_burn_price * gas_burnt − price_deficit (+ price_surplus pre-`AccountCostIncrease`) + refund_penalty + create_account_charge + tokens_burnt` (`runtime/runtime/src/lib.rs:1093`-`1103`); refund receipts contribute zero burnt gas. The outcome's `tokens_burnt` is this pre-reward value.
11. **Function-call gas reward**: `receiver_gas_reward = gas_burnt_for_function_call * burnt_gas_reward`; if non-zero and the receiver account still exists, it is credited to the account and subtracted from `tx_burnt_amount`, committed with `ActionReceiptGasReward` (`runtime/runtime/src/lib.rs:1108`-`1139`). **From v87 on `burnt_gas_reward` is 0** (`RemoveGasRewards`, `core/parameters/res/runtime_configs/87.yaml:3`), so this branch never fires and validators keep the whole burn.
12. **Output data**: if the receipt has `output_data_receivers`, either the returned `ReceiptIndex` receipt absorbs them or `Data` receipts carrying the return value (`None` on failure) are appended (`runtime/runtime/src/lib.rs:1152`-`1190`).
13. **Emit new receipts**: assign receipt ids; record `receipt_to_tx` origins when `save_receipt_to_tx` is set; instant receipts go to the `instant_receipts` queue (drained immediately after the current receipt by `process_receipt_and_instant_receipts` `:2748`), others are forwarded/buffered via the `ReceiptSink` (`runtime/runtime/src/lib.rs:1193`-`1237`). Only action-kind children appear in the outcome's `receipt_ids`.
14. **Build the outcome** (`runtime/runtime/src/lib.rs:1240`): status is `SuccessReceiptId` / `SuccessValue` / `Failure(ActionError)`. Metadata is `ExecutionMetadata::V4` (per-action `Vec<AccountContract>`, padded with `AccountContract::None` to the action count) when `ExecutionMetadataV4` (v85) is on, else `V3` (profile only) (`runtime/runtime/src/lib.rs:1252`-`1259`).

### 6. Per-action execution (`apply_action`, `runtime/runtime/src/lib.rs:571`)

`apply_action` seeds `ActionResult` with the action's `exec_fee` (gas + compute, `runtime/runtime/src/lib.rs:588`) and captures `current_contract` before running anything. It builds `ReceiptShape { is_refund: predecessor.is_system(), is_the_only_action: actions.len() == 1 }` (`:597`), then runs `check_account_existence` (`runtime/runtime/src/actions.rs:814`) and `check_actor_permissions` (`runtime/runtime/src/actions.rs:755`); either failure returns early with the error set and the exec fee already burnt. Implicit account creation on transfer is decided by `implicit_creation_allowed` (`runtime/runtime/src/actions.rs:929`): never for a refund, never for a named id; NEAR-implicit / ETH-implicit / `0s` deterministic ids require the transfer to be the receipt's **only** action (anti-hijacking); **`0u` universal ids are the exception and may be created by a batched transfer** because a universal id commits to its own key set and cannot be hijacked by a co-batched action. `get_account_type` (`runtime/runtime/src/actions.rs:899`) resolves the account type *through the runtime config flags* (`eth_implicit_accounts`, `universal_accounts`) so a disabled type reads as `NamedAccount` rather than silently upgrading the protocol. Below v88 `universal_accounts` is off, so a `0u` id reads as `NamedAccount` here: `implicit_creation_allowed` is false, and a transfer to an absent `0u` id fails the action with `ActionErrorKind::AccountDoesNotExist` (`runtime/runtime/src/actions.rs:842`) — at v87 such a receipt can no longer be created in the first place (§8).

### 7. Gas accounting and refunds (`refund_unspent_gas_and_deposits`, `runtime/runtime/src/lib.rs:1284`)

Under NEP-536 (always on — the flag is `_DeprecatedReducedGasRefunds`, v78) gas is purchased once for the whole execution and price changes do not by themselves create refunds. The function computes `prepaid_gas` (attached gas + prepaid send fees) and `prepaid_exec_gas` (prepaid exec fees + the receipt exec fee). On failure the full deposit is refunded and `gross_gas_refund = prepaid − gas_burnt`; on success `gross_gas_refund = prepaid − gas_used` (`:1304`-`:1316`). The NEP-536 penalty `gas_penalty_for_gas_refund` is deducted (`:1319`). A deposit-refund receipt (`Receipt::new_balance_refund`, to `receipt.balance_refund_receiver()`) and/or a gas-refund receipt (`Receipt::new_gas_refund`, which also credits the signing key's allowance) are pushed to `new_receipts` (`:1400`-`:1414`).

**`AccountCostIncrease` (v85)** changes the price model: `gas_burn_price = min(gas_purchase_price, apply_state.gas_price)` instead of the current price (`runtime/runtime/src/lib.rs:1038`-`1046`); the penalty is priced at the burn price rather than the purchase price (`:1320`); the price *surplus* (purchase > burn) — `(gas_purchase_price − gas_burn_price) × result.gas_burnt`, computed at `:1346` — becomes a `burned_gas_refund` to the signer instead of being folded into `tx_burnt_amount` (`:1353`, `:1096`); and creating an account triggers `create_account_charge` — top-up to `account_creation_charge`, capped by the available burned-gas refund (`:1360`-`1393`).

### 8. Universal accounts (`0u`, `UniversalAccounts` at v88)

A `0u` account id is `SHA3-256` over the **exact wire bytes** of the state init, encoded with the UAID codec (`core/primitives/src/utils.rs:503` — `derive_universal_account_id`). The derivation deliberately takes `RawStateInit` rather than a decoded value and does not inspect it: the id commits to bytes. From `CanonicalUniversalStateInit` (v88) on, only the canonical borsh encoding is *accepted*, so each logical state init has exactly one valid encoding and therefore one account id; a non-canonical encoding still derives *an* id, but can never create the account (`core/primitives/src/universal_state_init.rs:135` — `from_raw_strict`).

#### 8.1 The two-step 87-then-88 activation

This release activates in two steps (mainnet 87 on 2026-11-04, 88 on 2026-11-06; testnet 87 on 2026-09-23, 88 on 2026-10-21 — `core/primitives/src/version.rs:60`-`:82`). The gap exists for the runtime:

- A `Transfer` action's fee depends on whether it can implicitly create its receiver. `transfer_send_fee` / `transfer_exec_fee` (`core/parameters/src/cost.rs:812`, `:775`) add the `create_account` fee for a `0u` receiver **only when `universal_accounts` is on** — the `AccountType::UniversalAccount if universal_accounts_enabled` arm. `exec_fee`'s `Transfer` arm reads that flag out of the *runtime config it is handed* (`runtime/runtime/src/config.rs:360`-`:367`). So the same transfer costs more at 88 than at 87.
- A receipt's refund is **re-derived at execution time from the then-current config**, never from what the receipt actually carries: `refund_unspent_gas_and_deposits` recomputes `prepaid_gas` and `prepaid_exec_gas` by calling `total_prepaid_send_fees` / `total_prepaid_exec_fees(config, actions, receiver)` over the receipt's action list (`runtime/runtime/src/lib.rs:1296`-`:1302`), and `config` is `&apply_state.config` — the config of the chunk that executes it (`runtime/runtime/src/lib.rs:1067`). For a transfer to a `0u` id funded at the 87 schedule but executed at 88, the re-derived `prepaid_exec_gas` is larger than what was purchased, by exactly the `create_account` exec fee. Two things then go wrong, depending on how the receipt ends:
  - **The transfer does not run** (an earlier action in the receipt failed, so the loop broke at `runtime/runtime/src/lib.rs:1000`): its exec fee is never burnt, yet `gross_gas_refund = prepaid − gas_burnt` (`:1304`-`:1316`) still credits the full 88-rate figure. The signer is refunded an exec fee nobody paid — **value created from nothing**.
  - **The transfer does run**: `apply_action` seeds `gas_burnt` from the same execution-time config (`runtime/runtime/src/lib.rs:588`), so prepaid and burnt move together and the refund stays near zero — but the receipt now burns more gas than it carries, and `tx_burnt_amount` destroys tokens that were never collected. With `AccountCostIncrease` on, the price *surplus* refund is also computed on the inflated `result.gas_burnt` (`:1346`-`:1349`), adding a second over-refund on top.

  Neither is caught: the runtime has had **no production balance checker** since `RemoveCheckBalance` (`runtime/runtime/src/balance_checker.rs` was deleted in #13209, well before this release), and the only supply reconciliation left is a test (`runtime/runtime/src/tests/apply.rs:5518`, whose comment records that subsidies and the gas deficit are minted). The mismatch would be silent, not a chunk-halting error.
- `RejectUniversalAccountTransfers` (v87) closes that window from the other side: while it is on and `UniversalAccounts` is not, **no new receipt carrying such a transfer can be created** (`runtime/runtime/src/action_validation.rs:236` — `validate_transfer_action`). Transactions are refused with `InvalidTxError::ActionsValidation(TransferToUniversalAccountNotAllowed)`; a contract-created receipt is refused by the `NewReceipt` validation in `apply_action_receipt` and surfaces as `ActionErrorKind::NewReceiptValidationError` (`runtime/runtime/src/lib.rs:970`).
- The check is `NewReceipt`-only, so receipts minted at ≤86 keep executing (failing an incoming or delayed receipt's validation is a `RuntimeError`, i.e. a chunk halt). The two-day gap is the drain window: by the time 88 arrives the delayed and buffered queues hold nothing that was funded under the cheaper schedule.

A reverted alternative is visible in the history: #16484 added a `CapRefundAtPrevEpochFees` feature that capped the refund at the cheaper of the current and previous epoch's schedule, and #16526 reverted it in full. Nothing of it survives at this commit.

#### 8.2 Creation paths

Three creation paths converge on the same account (all from v88):

1. **Transfer.** A transfer to an absent `0u` id creates an **uninitialized** account — `Account::new_uninitialized` with a bootstrap nonce seeded from the block height (`runtime/runtime/src/actions.rs:276`, `core/primitives-core/src/account.rs:283`). This may be batched with other actions (§6). An uninitialized account has no keys, code or data, and `check_account_existence` rejects every action against it except its own state init and a further transfer, with `ActionErrorKind::AccountNotInitialized` (`runtime/runtime/src/actions.rs:884`).
2. **`UniversalStateInit` action** (`runtime/runtime/src/universal_account_id.rs:22`). The account is created if absent, without changing `actor_id`, so a co-batched follow-up cannot hijack it (`:45`). Then:
   - **Already initialized** (`:52`): with `RefundRepeatedUniversalStateInitDeposit` (v88) the whole deposit is refunded with a `Receipt::new_balance_refund` to `receipt.balance_refund_receiver()` and nothing else happens (`:65`-`:71`). Below that feature the repeat instead ran `settle_state_init_deposit`, so the deposit *also* topped up the account's storage staking — and a deposit short of the missing stake failed the action with `LackBalanceForState`. The installed state is untouched either way.
   - **Not yet initialized** (`:74`): the payload is decoded — strictly from `CanonicalUniversalStateInit` on, leniently below it (`:80`-`:86`) — and a failure sets `ActionErrorKind::MalformedUniversalStateInit` on the action rather than failing the chunk, because validation of a *new* receipt already rejected it and only a pre-feature or bypassed receipt can reach here. The account is marked initialized and `install_universal_account` (`:126`) writes optional global contract code, storage entries, then full-access keys by on-trie handle. Every installed key gets nonce `max(initial_nonce_value(block_height), consumed bootstrap nonce)` (`:91`-`:92`) so the bootstrap transaction's bytes cannot replay through the key path. Storage usage is accumulated per record. Finally `settle_state_init_deposit` (`runtime/runtime/src/deterministic_account_id.rs:73`, shared with the `0s` path) tops up exactly the missing storage stake and refunds the rest, or fails with `LackBalanceForState`.
3. **Self-signed bootstrap transaction.** See §4: the account id itself is the authorization, verified by `verify_and_charge_bootstrap_tx_ephemeral`.

#### 8.3 Caps and fees

- `max_universal_state_init_keys = 1_024` and `max_state_init_entries = 1_500` are both **per-receipt totals** over all state-init actions, checked together by `validate_state_init_counts` (`runtime/runtime/src/action_validation.rs:48`) in `NewReceipt` mode only. #16415 moved the key cap here from `validate_universal_state_init`, where it had been **per action** while the entry cap was already per receipt. Every action in a receipt shares its receiver and a universal state init must derive to that receiver, so the copies have to be byte-identical — but nothing stopped a receipt from carrying up to `max_actions_per_receipt` (100) of them, each with up to 1 024 keys. The regression test records the shape that passed review: 94 copies of a 506-key payload commit 94 × 506 = **47 564 keys** against what is now a receipt cap of 1 024, and burn roughly **ten times** the per-chunk transaction gas budget at conversion (47 564 × `action_add_full_access_key` send 101 765 125 000 ≈ 4.84 Pgas, against `max_tx_gas` = 500 Tgas, `core/parameters/res/runtime_configs/68.yaml:50`) — each committed key is priced as a full `add_full_access_key` at the **send** rate (`core/parameters/res/runtime_configs/parameters.yaml:98`), all of it burnt when the transaction becomes a receipt. **That conversion burn is metered against the chunk**: `process_transactions` folds each transaction's `gas_burnt` into `processing_state.total` (`runtime/runtime/src/lib.rs:2364`), that counter is carried into the receipt phase unchanged (`runtime/runtime/src/lib.rs:3294` — `into_processing_receipt_state`, `total: self.total` at `:3314`), and all three receipt loops gate on it against `compute_limit` (`:2514`, `:2595`, `:2704`). One over-budget transaction therefore stops the shard executing *any* receipts that chunk. Asserted by `test_worst_accepted_universal_state_init_converts_within_the_tx_gas_budget` (`runtime/runtime/src/verifier.rs:2681`), which searches every split of the action budget rather than assuming one. The entry cap applies to `DeterministicStateInit` too. `max_state_init_entries` lives in `core/parameters/res/runtime_configs/87.yaml:43`; `max_universal_state_init_keys` is a base parameter (`core/parameters/res/runtime_configs/parameters.yaml:316`).
- Fees are computed by `universal_state_init_fee` (`runtime/runtime/src/config.rs:242`) on the payload's own byte length plus decoded entry/key counts, shared with the VM host function that lets a contract build the action. The counts come from `state_init_counts` (`core/primitives/src/universal_state_init.rs:168`), which **always decodes leniently** so that a receipt created under an older version is re-priced identically on every version; bytes that do not decode describe zero entries and zero keys and pay only the base and per-byte terms.
- `88.yaml` reprices the action for the canonical check it now performs: `action_universal_state_init_per_entry` send 0 → 3_100_000_000 (exec unchanged at 200 Ggas) and `action_universal_state_init_per_byte` send 72M → 78M, exec 70M → 74M (`core/parameters/res/runtime_configs/88.yaml:18`, `:38`).

#### 8.4 Host-function surface

`universal_state_init_to_account_id` (`runtime/near-vm-runner/src/logic/host.rs:3299`) hashes the bytes a contract supplies and writes the `0u` id to a register, returning an exit status. Both this and `promise_batch_action_universal_state_init` are imported only when the `universal_accounts` flag is on (`runtime/near-vm-runner/src/imports.rs:219`, `:224`), so on the stable chain they first become callable at v88 — the lenient behavior described here is what a pre-88 nightly or test config does: nothing inspects the contents, **any** byte string maps to an id and the status is always `0`. From `CanonicalUniversalStateInit` on, `Config::state_init_decode_mode` (`core/parameters/src/vm.rs:328`) is `Strict` and the function first calls `Ext::check_state_init` (`runtime/runtime/src/ext.rs:480`, i.e. `from_raw_strict`), returning `1` for bytes that do not decode and `2` for bytes that decode non-canonically, leaving the register untouched (`runtime/near-vm-runner/src/logic/host.rs:3321`-`:3325`). The per-byte fee is charged *before* the check, which is what pays for it; `88.yaml` raises `wasm_universal_state_init_to_account_id_base` 8_520_000_000 → 8_900_000_000 and `..._byte` 21_471_105 → 83_100_000 (`core/parameters/res/runtime_configs/88.yaml:67`-`:68`). The function's **signature** does not follow the protocol version — it returns a status at every version, so a contract importing the older no-return form no longer links.

`promise_batch_action_universal_state_init` (`runtime/near-vm-runner/src/logic/host.rs:3377`) still forwards the bytes verbatim and deliberately does not check the receiver; it charges the size terms before handing the payload to the host and then the content terms from `Ext::state_init_send_counts` (`runtime/runtime/src/ext.rs:484`). In `Strict` mode a payload that does not decode or is not canonical is charged the **upper bound** of entries and keys its length could hold (`upper_bound_counts`, `core/primitives/src/universal_state_init.rs:207`), because the decoder still has to walk every byte before rejecting it; in `Lenient` mode it falls back to `state_init_counts`.

### 9. Execution outcome / status

Every processed transaction and receipt yields an `ExecutionOutcomeWithId` (`runtime/runtime/src/lib.rs:1261` for receipts, `:2289` for transactions) recording `status`, `logs`, `receipt_ids`, `gas_burnt`, `compute_usage`, `tokens_burnt`, `executor_id`, `metadata`. Status is one of `SuccessValue`, `SuccessReceiptId`, or `Failure(TxExecutionError)`.

### 10. Gas/compute limit and delayed receipts

`process_receipts` sets `compute_limit = gas_limit` (`runtime/runtime/src/lib.rs:2797`; there is still no separate compute limit, TODO #8859). In each of `process_local_receipts` / `process_delayed_receipts` / `process_incoming_receipts`, before processing a receipt the loop checks `total.compute >= compute_limit || trie.check_proof_size_limit_exceed()`; if exceeded, the receipt is pushed onto the delayed queue instead of executing (local `runtime/runtime/src/lib.rs:2514`, incoming `:2704`) or the delayed loop breaks (`:2595`). Incoming receipts are `validate_receipt(..., ExistingReceipt)`-checked **before** either branch, so an invalid receipt is never stored as delayed (`runtime/runtime/src/lib.rs:2696`). Contract preparation is scheduled one receipt ahead in every loop (`schedule_contract_preparation`, `runtime/runtime/src/lib.rs:3383`). Whichever limit stopped the chunk is recorded in `CHUNK_RECEIPTS_LIMITED_BY` (`runtime/runtime/src/lib.rs:2829`).

Promise-yield timeouts are resolved last and obey the same limits (`resolve_promise_yield_timeouts`, `runtime/runtime/src/lib.rs:3113`): expired queue entries whose yield receipt is still present emit a local `PromiseResume` receipt with `data: None`, and the updated indices are persisted in `validate_apply_state_update`.

### 11. Validator accounts update (`update_validator_accounts`, `runtime/runtime/src/lib.rs:1717`)

For each validator with stake info: an **uninitialized** account is skipped, but with a defence-in-depth check that its stake/reward/proposal are all zero, else `StorageInconsistentState` (`:1730`-`:1747`). Otherwise add the reward to `locked`, assert `locked >= max_of_stakes`, compute `return_stake = locked − max(max_of_stakes, last_proposal)`, and move it from `locked` back to `amount` (`:1749`-`:1795`). A missing account with positive `max_of_stakes` is fatal (`:1796`). The protocol treasury account gets its reward if it did not already receive one as a validator (`:1807`). Commits with `ValidatorAccountsUpdate`.

## Interactions

- **Consumes**: pre-state `Trie`, `ApplyState`, incoming receipts, `SignedValidPeriodTransactions`, optional `ValidatorAccountsUpdate`, `EpochInfoProvider` (min stake, shard layout, chain id), `RuntimeConfig`. Config/fees come from [economics](economics.md); the validator update comes from [epoch, validators & staking](epoch-validators-staking.md).
- **Produces**: new state root + `TrieChanges` → [state storage](state-storage.md); outgoing receipts (via `ReceiptSink`) and bandwidth requests → [cross-shard congestion control](cross-shard-congestion.md); `ValidatorStake` proposals → [epoch, validators & staking](epoch-validators-staking.md); execution outcomes → chunk outcome root / RPC; recorded storage → [stateless validation](stateless-validation.md).
- **Invokes**: the [contract VM](contract-vm.md) for `FunctionCall`; contract preparation is pipelined (`runtime/runtime/src/pipelining.rs`) and `receipt_manager.rs` collects VM-created receipts. Wire types for receipts/actions live in [data structures & serialization](data-structures-serialization.md); account and key semantics in [accounts & keys](accounts-keys.md).

**Stable ML-DSA cost charging at 88 (the unfixed behavior).** With `fix_ml_dsa_cost_charging == false`:

1. **Gas-key transfer fees on the transaction path.** `gas_key_send_pk_len` (`runtime/runtime/src/config.rs:73`) returns `public_key.trie_id_len()`, the on-trie identifier length, for the *send* (transmission) fee of `TransferToGasKey` / `WithdrawFromGasKey` (`runtime/runtime/src/config.rs:133`, `:212`) — the same length the exec fee already uses (`:411`). An ML-DSA-65 key occupies 1953 bytes on the wire and 33 on the trie, so such a transaction is charged transmission for 33 bytes it did not transmit.
2. **Gas-key fees on the host-function path.** `gas_key_exec_pk_len` (`runtime/near-vm-runner/src/logic/logic.rs:200`) falls back to `pk_len`, the decoded key's **wire** length, for the *exec* (storage) fee of both `promise_batch_action_transfer_to_gas_key` and the `..._add_gas_key_*` family (`runtime/near-vm-runner/src/logic/host.rs:3711`, `:3788`); the send fee reads `pk_len` either way. A contract-created gas-key action is therefore charged storage for 1953 bytes it does not store. The two creation paths disagree with each other, which is what the fix was for.
3. **Meta-transaction verification compute.** `signature_verification_cost` (`runtime/runtime/src/config.rs:589`) is called with `meter_inner_verify_on_receiver == false`, so each inner `DelegateAction` signature's **compute** is charged on the signer shard at conversion, where the verification never happens, and `apply_delegate_action` (`runtime/runtime/src/actions.rs:467`) skips adding it to `result.compute_usage` on the receiver shard. The verification work therefore escapes the receiver shard's `compute_limit`.

All three are no-ops for ed25519/secp256k1, where wire and on-trie lengths coincide; they only matter for ML-DSA-65 keys, which have been admissible since `PostQuantumSignatures` (v85). The `CHANGELOG.md` entry for 2.14.0 still claims the ML-DSA charging fix shipped (`CHANGELOG.md:26`, citing #16064) — the companion entry for `ReceiptPromiseInputSizeLimit` *was* deleted in the same window, so only this one was missed. ## Invariants & failure modes

- **Gas ordering**: `merge` asserts `gas_burnt_for_function_call <= gas_burnt <= gas_used` per action (`runtime/runtime/src/lib.rs:488`).
- **Failed receipt atomicity**: a receipt whose result is `Err` triggers `state_update.rollback()`, so no state change persists except the outcome and gas accounting (`runtime/runtime/src/lib.rs:1086`). `set_error` additionally clears queued receipts, proposals and burnt/subsidized amounts (`runtime/runtime/src/lib.rs:535`).
- **A failed action stops the receipt**: the action loop breaks on the first `Err` and records the action index; subsequent actions never run (`runtime/runtime/src/lib.rs:1000`).
- **Staking invariant**: `update_validator_accounts` returns a fatal `StorageInconsistentState` if `locked < max_of_stakes`, if an account with positive stake is missing, or if an uninitialized account carries any stake/reward/proposal (`runtime/runtime/src/lib.rs:1730`, `:1762`, `:1796`).
- **Invalid txs make progress, not failure**: a chunk containing invalid transactions is not rejected; the offending txs are skipped during conversion, which pollutes the chain with junk but keeps the shard live (`runtime/runtime/src/lib.rs:1849` doc; skip sites `:2124`, `:2329`).
- **Refund receipts are free**: system-predecessor receipts burn zero gas and generate no refund; a failed refund burns its deposit into `other_burnt_amount` (`runtime/runtime/src/lib.rs:1090`, `:1050`).
- **Delayed receipts must stay valid**: a delayed receipt failing `validate_receipt` on dequeue is `StorageInconsistentState` (`runtime/runtime/src/lib.rs:2628`); an invalid *incoming* receipt is a `RuntimeError::ReceiptValidationError` and is never stored as delayed (`runtime/runtime/src/lib.rs:2696`).
- **Verification never mutates**: all three `verify_and_charge_*_ephemeral` functions are pure; `VerificationResult::apply` is the only mutation point and reports a mismatch as `StorageInconsistentState` rather than panicking, because it runs during chunk apply (`runtime/runtime/src/lib.rs:337`).
- **Pending constraints are consensus-neutral**: `PendingConstraints` is always default on the consensus path, and every use is a `saturating_sub` so the RPC / chunk-production path cannot change the result (`runtime/runtime/src/verifier.rs:353`, `:644`).
- **Storage staking**: the receiver must cover storage after execution or the receipt fails with `LackBalanceForState` (`runtime/runtime/src/lib.rs:1015`); zero-balance accounts (≤ 770 bytes) are exempt (`runtime/runtime/src/verifier.rs:25`, `:88`).
- **Uninitialized accounts are inert**: every action except `UniversalStateInit`, `DeterministicStateInit` and `Transfer` fails with `ActionErrorKind::AccountNotInitialized` (`runtime/runtime/src/actions.rs:884`), and `Account::initialize` refuses a second call (`core/primitives-core/src/account.rs:330`).
- **Bootstrap nonces do not replay**: the bootstrap nonce is consumed on the account before the state init runs, and installed keys start at `max(initial_nonce_value, consumed nonce)` (`runtime/runtime/src/lib.rs:371`, `runtime/runtime/src/universal_account_id.rs:92`).
- **One logical state init, one account id** (v88): `from_raw_strict` requires `decoded.to_raw() == raw`, so a non-canonical encoding is refused in `NewReceipt` validation and at execution, and the id derivation — which is blind to contents — can no longer be aimed at an account that would then be unreachable (`core/primitives/src/universal_state_init.rs:135`, `runtime/runtime/src/action_validation.rs:597`). Only the outer structure is checked; opaque storage values are out of the protocol's view.
- **A state-init payload is priced identically on every protocol version**: `state_init_counts` always decodes leniently, so a receipt created before `CanonicalUniversalStateInit` is re-priced for refunds exactly as it was funded (`core/primitives/src/universal_state_init.rs:168`). Only what a contract is charged *before* validation follows the mode (`state_init_send_counts`, `:184`).
- **No `0u`-funded receipt is *created* under the cheap fee schedule once 87 is live**: `RejectUniversalAccountTransfers` refuses new transfers to `0u` ids for the whole of protocol 87, and refunds re-derive the exec fee from the config current at execution (`runtime/runtime/src/action_validation.rs:236`, `runtime/runtime/src/lib.rs:1300`). That a receipt minted at ≤86 does not *survive* the whole 87 window is an operational argument about queue drain, not something any code enforces — see §8.1 and **Open questions**.
- **State-init caps are per receipt, not per action**: entries and committed keys are summed over every state-init action in the receipt, delegate payloads included, in one check (`runtime/runtime/src/action_validation.rs:48`, `core/primitives/src/action/mod.rs:518`). Enforced in `NewReceipt` mode only, so an existing receipt cannot fail validation and halt a chunk.
- **The promise-input bound is not in force on the stable chain**: `ReceiptPromiseInputSizeLimit` is nightly (157) and `max_receipt_total_input_size` is `u32::MAX` at 87 and 88, so a receipt's combined resolved promise inputs are effectively unbounded and `TotalPromiseInputSizeExceeded` cannot occur (`core/primitives-core/src/version.rs:653`, `runtime/runtime/src/lib.rs:849`).
- **Chunk work is bounded** by `compute_limit` (= gas limit) and the chunk storage-proof size limit; overflow pushes work onto the delayed queue (`runtime/runtime/src/lib.rs:2514`, `:2595`, `:2704`).
- **`CreateAccount` never targets an implicit id** — it would claim `actor_id` for an id whose private key the sender may not hold; `ActionErrorKind::OnlyImplicitAccountCreationAllowed` (`runtime/runtime/src/actions.rs:836`).

## Open questions

- **RESOLVED — `fix(gas-keys): fix gas charging issue` (#16084) is deliberately unversioned, and also shipped into the 2.13 line.** The commit (`b6612ed6` on this branch) changes the gas-key host functions from pricing on the caller-supplied `public_key_len` to pricing on the decoded key's wire length `pk_len` (`runtime/near-vm-runner/src/logic/host.rs:3681`, `:3750`, `:3818`). There is no `ProtocolFeature` variant and no `87.yaml` flag guarding it — `fix_ml_dsa_cost_charging` (`ProtocolFeature::FixMlDsaCostCharging`, added later by #16064) gates only *which* length the **exec** fee uses (`gas_key_exec_pk_len`, `runtime/near-vm-runner/src/logic/logic.rs:200`); the **send** fee reads `pk_len` unconditionally. **That feature is nightly (157) at this release**, so at 87 and 88 the exec fee on this path also reads `pk_len` — the question below is now the *whole* story for host-function gas-key pricing on the stable chain, with no version-gated counterpart beside it. The reachable behavioral surface is narrow:
  - **Memory-read calls whose key decodes** (the normal case) are unaffected: borsh `try_from_slice` rejects trailing bytes, so a successful decode implies `pk_len == public_key_len`.
  - **Register-convention calls** (`public_key_len == u64::MAX`, `get_memory_or_register`, `runtime/near-vm-runner/src/logic/host.rs:223`, reached through `get_public_key` `:624`) were a **node panic**, not a consensus outcome: the old code fed `usize::MAX` into `checked_mul(..).unwrap()` in `gas_key_transfer_send_fee` / `gas_key_add_key_exec_fee` (`core/parameters/src/cost.rs:865` — `gas_key_transfer_send_fee`, `:928` — `gas_key_add_key_exec_fee`). A panic is not a state any chain advanced through, so there is nothing to preserve.
  - **Keys that fail to decode**: the old code burnt `gas_key_byte` × `public_key_len` before returning `HostError::InvalidPublicKey`; the new code burns zero for those bytes and then returns the same error. Because a failed function call records `result.gas_burnt = outcome.burnt_gas` rather than the whole prepaid amount (`runtime/runtime/src/function_call.rs:140`), this *is* consensus-visible.
  So the change is a genuine unversioned consensus change at protocol 85/86 (gas-key host functions have been live since `gas_key_host_fns` in `core/parameters/res/runtime_configs/85.yaml:3`), and it was handled as a patch release rather than a protocol feature: `e015669d` sits directly on the `2.13-release` branch and is contained in tags 2.13.1, 2.13.2, 2.13.3 and 2.13.4, with `b6612ed6` the cherry-pick to master. The only binaries that disagree with 2.14 are 2.13.0 and its release candidates, which are superseded. **No open divergence remains between currently deployed binaries**; what remains unverifiable from code alone is whether a NEP/release note documents the unversioned fix.

- **Testnet replayability across the 87 window is unverified.** The testnet schedule in this binary votes 87 on 2026-09-23 and 88 on 2026-10-21 (`core/primitives/src/version.rs:72`-`:83`), but testnet ran protocol 87 for that whole month on the 2.14.0-rc.1…rc.3 binaries, where `UniversalAccounts` was a **87** feature and `universal_accounts: true` sat in `87.yaml`. In this binary `universal_accounts` lives in `88.yaml`, so the config computed for protocol 87 differs from the one those nodes used, and there is no testnet-specific override (`core/parameters/res/runtime_configs/parameters_testnet.yaml:324` carries the same `universal_accounts: false` base). `MIN_SUPPORTED_PROTOCOL_VERSION = 84` claims 87 blocks are replayable. Whether any `0u` account or `UniversalStateInit` actually landed on testnet in that window — and therefore whether this is a live replay divergence or only a latent one — cannot be determined from the code. Mainnet is unaffected: it had not voted 87 at this commit.
- The exact interaction between a **`0u` account created by a batched transfer** and a `UniversalStateInit` *later in the same receipt* that fails is rolled back wholesale by `apply_action_receipt`; whether an uninitialized-but-funded account can survive a chunk when the transfer and the state init arrive in *different* receipts is by design (the comment at `runtime/runtime/src/universal_account_id.rs:38` says a half-installed account cannot be observed), but no production code asserts the cross-receipt case.
- **The 87→88 drain window is an argument, not an enforced invariant.** `RejectUniversalAccountTransfers` only blocks *new* receipts (`NewReceipt` mode, `runtime/runtime/src/action_validation.rs:236`); a receipt carrying a transfer to a `0u` id that was created at protocol ≤86 and is still sitting in a delayed or outgoing-buffer queue when 88 activates would be priced wrongly, as in §8.1. Nothing in the code proves the queues drain within the two-day mainnet gap (or the one-month testnet gap); the argument rests on congestion control bounding those queues far below two days of throughput. No test or assertion covers it.
- `validate_apply_state_update` reads `processing_state.outcomes` and `processing_state.metrics` after `processing_state` is destructured with `..` (`runtime/runtime/src/lib.rs:2852`, `:2983`). This compiles as a partial move and is behaviorally fine, but the mixed style makes the field ownership hard to follow; flagged for a future reader rather than as a defect.
